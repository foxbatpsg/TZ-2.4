## 1. Пробелы в ТЗ (отсутствуют явные решения)

1. **Упаковка и дистрибуция Windows-приложения.** ТЗ жёстко фиксирует стек (Python + CustomTkinter + SQLite), но не определяет способ поставки конечному пользователю (PyInstaller / Nuitka / MSIX / portable-zip), стратегию обновления версии и подпись бинарника. Рекомендация: добавить отдельный EPIC/раздел «Packaging & Distribution» до старта GUI-задач, иначе агенты будут принимать это решение самостоятельно и непоследовательно.

   > **Статус: `REJECT-VERIFIED`** (проверено 2026-09-09, см. `REVIEW-REGISTRY.md` §D-2). Утверждение «упаковка не определена, нужен новый EPIC» — неверно: `EPIC-11 PACKAGING / PORTABLE` существует и описывает portable MVP, environment checker, dependency diagnostics, startup checks, backup/recovery и Gate `G-11` (`EPIC SPECIFICATIONS v1.0`, стр. 234–244). **Новый EPIC создавать нельзя.**
   > **Остаточная валидность принята как `ACCEPT`:** конкретный инструмент сборки (PyInstaller/Nuitka), политика обновления и подпись бинарника не зафиксированы. Это уточнение **внутри** существующего EPIC-11, а не новый раздел. См. `REVIEW-REGISTRY.md` §4 п. `S-01`.
2. **Управление локальными LLM-моделями (Model Manager).** Не описано, как приложение обнаруживает/скачивает/проверяет совместимость GGUF-моделей 12–14B, где они хранятся, как валидируется наличие Ollama/LM Studio на машине пользователя перед стартом. Рекомендация: явный компонент `ModelManager` с проверкой доступности бэкенда до `start_research_session`.

   > **Статус: `REJECT-VERIFIED`** (проверено 2026-09-09, см. `REVIEW-REGISTRY.md` §D-3). Утверждение «ModelManager отсутствует, нужен новый компонент» — неверно: `Health Monitor` (HEALTHY/DEGRADED/UNREACHABLE/RESTARTING) и `LLM Backend Router` нормативно описаны в `05_Взаимодействие с LLM и протокол MCP.md` §1–2 и EPIC-06. **Второй router создавать нельзя.**
   > **Остаточная валидность принята как `ACCEPT`:** не описан preflight выбранной модели до `start_research_session` (проверка наличия runtime, модели, объёма памяти, поддержки structured output и tool calling) и профили возможностей провайдеров. Это дополнение к существующему контуру LLM Backend. См. `REVIEW-REGISTRY.md` §4 п. `S-02`.
3. **Секреты и API-ключи внешних источников.** Академические/поисковые адаптеры (`search_academic`, `search_github` и т.д.) подразумевают использование внешних API, часть которых требует ключей/квот. ТЗ не описывает механизм хранения и ротации ключей. Рекомендация: зафиксировать конкретное хранилище (Windows Credential Manager / `keyring` / зашифрованный локальный конфиг) в отдельном нормативном разделе, чтобы агенты не «изобретали» варианты хардкода.

   > **Статус: `DEFER` → Post-MVP** (решение 2026-09-13, см. `REVIEW-REGISTRY.md` §5a). Механизм в MVP **не фиксируется**. Предложенный вариант с Windows Credential Manager отклонён: он привязан к профилю ОС, и потеря профиля (переустановка Windows, повреждение после обновления, смена учётной записи) обрушила бы все API-зависимые интеграции сразу. Вопрос вынесен в список доработок после запуска проекта, целевой раздел — `07_QA_Acceptance.md` §26 (Post-MVP). Требования к будущему решению зафиксированы там же. Общий запрет на хардкод секретов остаётся действующим (§24, A-17).
4. **CI/CD и конкретные инструменты статического анализа.** ТЗ требует «линтер в CI» для stdout-guard (раздел 5, §3.1) и «автоматические тесты для каждого компонента» (раздел 7), но не называет конкретный CI-провайдер, конфигурацию pipeline, инструменты (ruff/mypy/bandit) и пороги покрытия тестами (%). Рекомендация: зафиксировать минимальный CI-контракт (шаги, gate-квоты) как приложение к ТЗ, аналогично `BUDGET CONTRACT`.
5. **EPIC-07…EPIC-11 недоступны для полного анализа.** При выгрузке `EPIC SPECIFICATIONS v1.0 — BASELINE.md` контент детально описывает только EPIC-01…EPIC-06 (Foundation, Data Layer, State Machines, Search Core, Research Engine, LLM Backend); специфика EPIC-07 (предположительно MCP Server), EPIC-08 (GUI), EPIC-09/10/11 (Reporting/QA/Packaging?) не была полностью получена в рамках анализа. Рекомендация: перед декомпозицией TASK для GUI/MCP-слоя и отчётности явно свериться с полным текстом EPIC-07…EPIC-11 в первоисточнике — в `ARCHITECTURE.md` эти зоны реконструированы по разделам 04–07 ТЗ и MCP Tool Contracts, а не процитированы дословно из EPIC-документа.

   > **Статус: `VERIFIED / снято`** (проверено построчно 2026-09-09 по `TZ-2.4 @ f15fe9a`, см. `REVIEW-REGISTRY.md` §D-1). Утверждение неверно — **пробел выгрузки у ревьюера, а не дефект ТЗ**:
   > - `EPIC SPECIFICATIONS v1.0 — BASELINE.md` стр. **168–245** содержат полные спецификации: `§8 EPIC-07 — MCP`, `§9 EPIC-08 — GUI`, `§10 EPIC-09 — INTEGRATION & RESILIENCE`, `§11 EPIC-10 — FINAL QA / ACCEPTANCE`, `§12 EPIC-11 — PACKAGING / PORTABLE`, включая Gate `G-07…G-11`.
   > - `MASTER DEVELOPMENT ROADMAP v1.2 — BASELINE.md` стр. **341–442** дублирует те же EPIC-07…11 разделами §10–§14.
   >
   > **Реальные названия (сверено с baseline):** EPIC-07 — MCP, EPIC-08 — GUI, EPIC-09 — Integration & Resilience (**не** отчётность), EPIC-10 — Final QA / Acceptance, EPIC-11 — Packaging / Portable. **EPIC-12 не нужен** — упаковка уже в EPIC-11.
   >
   > **Следствия, требующие отдельного действия:** исправить реконструированные названия и ссылки в `ARCHITECTURE.md`; ~~отдельно исправить реальный дефект `EPIC-10` стр. 228 «морфология **если включена**» → обязательная RU-морфология по `A-13`~~ ✅ **исправлено 2026-09-13** (см. `REVIEW-REGISTRY.md` §D-1 п.3, `INDEX.md` §9 дефект `D-1`).
6. **Телеметрия/crash-report отсутствуют.** Для privacy-first локального приложения явно не описано, собирается ли диагностика сбоев (даже локально, без сети) и как она соотносится с требованием не логировать приватные пути (A-17). Рекомендация: явно зафиксировать «телеметрия отсутствует / crash-log только локальный, без PII» одним пунктом ТЗ, чтобы исключить разночтения у разных агентов.
7. **Лицензирование моделей и данных.** GGUF-модели, академические API и данные Reddit/StackOverflow могут иметь ограничения лицензий/ToS на автоматический скрейпинг. ТЗ не содержит юридического раздела. Рекомендация: как минимум пометить это как «вне рамок ТЗ, ответственность интегратора».

## 2. Потенциальные внутренние противоречия / зоны риска

1. **Семантика `Study.COMPLETED` при partial-результате.** По `STATE MACHINE SPECIFICATION v1.2 §1`, переход `FREEZE_BUDGET_EXHAUSTED → FINALIZING → COMPLETED` заканчивается статусом `COMPLETED`, при этом результат помечается как partial только через `metadata`/result status, а не через состояние. Это создаёт риск, что внешний потребитель API (GUI, экспорт отчёта, будущая интеграция) увидит `status = COMPLETED` и ошибочно расценит исследование как «полностью успешное». Рекомендация: явно закрепить в API-контракте (GUI/экспорт), что поле `result.completion_kind` (`FULL` | `PARTIAL`) обязано визуально дублироваться рядом со статусом `COMPLETED` во всех представлениях, а не только «где-то в metadata».
2. **Версионирование нормативных приложений идёт с разной скоростью.** `STATE MACHINE SPECIFICATION` уже на v1.2, `MCP TOOL CONTRACTS` на v1.1, `BUDGET CONTRACT` и `TASK EXECUTION CONTRACT` на v1.0 — при этом в текстах есть перекрёстные ссылки друг на друга («см. раздел 5 УИ v1.0», «Q-04», «A-16» и т.д.), разбросанные по нескольким независимо версионируемым документам. Риск: агент, читающий не самую свежую версию одного из документов, получит рассинхронизированный контекст. Рекомендация: завести единый `docs/adr/` или `CHANGE_LOG.md` со сквозной таблицей соответствия версий документов друг другу («какая версия X согласована с какой версией Y»).
3. **`Watchdog` как источник runtime-событий, но не как писатель в БД.** ТЗ прямо запрещает Watchdog прямую запись в SQLite (раздел 2, §3), но не определяет явно транспортный механизм «Watchdog → Core» (внутренняя очередь? прямой вызов? отдельный поток?). Рекомендация: до декомпозиции EPIC-06/EPIC-03 на TASK явно зафиксировать интерфейс `WatchdogSignal`, иначе разные агенты реализуют разные способы передачи сигнала.
4. **`independent_source_count` и `UNKNOWN` SourceRelation.** Правило «консервативное правило для UNKNOWN» (раздел 7 ТЗ, §14) описано словесно, но не формализовано численно (например, учитывается ли `UNKNOWN` как зависимый по умолчанию всегда, или это настраиваемый порог). Рекомендация: зафиксировать точную формулу/псевдокод `independent_source_count(claim)` в `BUDGET CONTRACT`-подобном отдельном контракте (аналогично тому, как формализован бюджет), а не оставлять как эвристику на усмотрение реализующего агента.
5. **Открытый блокер Q-08 (обновление URL Document).** В разделе 7 ТЗ прямо упомянуто: «обновление URL в существующем Document — блокер Q-08, открыт». Это означает, что версионирование Document при смене URL не имеет финального решения. Рекомендация: не начинать TASK, затрагивающие `Document.version`/URL update, до формального закрытия Q-08 — иначе агент будет вынужден принять архитектурное решение самостоятельно, что запрещено `TASK EXECUTION CONTRACT` (п. 19).
6. **Стоимость полной русской морфологии на CPU-only baseline.** ТЗ требует одновременно (а) обязательную полную морфологию RU для MVP (A-13) и (б) полноценную работу на CPU без GPU, включая LLM 12–14B в квантовании. На слабом CPU одновременная нагрузка (LLM-инференс + морфологический анализ большого объёма чанков) не оценена по производительности. Рекомендация: до начала EPIC-04 TASK зафиксировать нефункциональные лимиты (макс. время индексации N документов на референсном CPU), иначе Gate G-04 не будет иметь измеримого критерия «достаточно быстро».

## 3. Рекомендации по улучшению процесса нарезки TASK для агентов

1. Явно пронумеровать соответствие «раздел ТЗ → EPIC → Gate» в отдельной таблице трассируемости (Traceability Matrix), чтобы при `STOP → REPORT` агент мог сразу сослаться на конкретный пункт ТЗ, а не пересказывать его словами.
2. Для каждого EPIC перед раздачей TASK агентам зафиксировать **эталонные fixtures** (набор детерминированных документов/запросов), которые будут переиспользоваться всеми Gate-тестами — иначе разные агенты создадут несовместимые тестовые данные для одного и того же EPIC.
3. Ввести в `TASK Context Header` обязательное поле `RELATED_ADR` (ссылка на запись в `docs/adr/`) для любых TASK, которые ранее уже вызывали `BLOCKED`/`STOP`, чтобы не повторять одно и то же обсуждение с разными агентами.
4. Зафиксировать единый источник правды для схемы БД (например, `db/migrations/` как единственный place, где описана структура таблиц) и запретить агентам дублировать описание схемы в комментариях/докстрингах, которое может разойтись с реальной миграцией.
