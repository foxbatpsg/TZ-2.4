
# НАЦИОНАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ) v2.5
## Раздел 1. Слой исследовательского анализа (Research Analysis Layer)

**Статус:** Утвержденный архитектурный контракт (Финальная монолитная редакция)
**Назначение:** Определение универсального слоя анализа исследовательских задач, структурированных наблюдений и критериев достаточности исследования.

---

## 1. Назначение и рамки слоя

Research Analysis Layer определяет, какая информация требуется для ответа на исследовательский вопрос, как она должна собираться, структурироваться, проверяться и агрегироваться.

Основной архитектурный принцип слоя:

```
User Question (Вопрос пользователя)
        ↓
Research Intent (Структурированная цель)
        ↓
Analysis Strategy (Выбор стратегии анализа в Core)
        ↓
Research Plan (План исследования)
        ↓
Search Tasks (Поисковые задачи под управлением Core)
        ↓
Retrieval (Детерминированный поиск и фильтрация дублей)
        ↓
Evidence (Извлечение доказательств из контекстного окна)
        ↓
Observation / Claim (Формирование наблюдений и утверждений)
        ↓
Analysis (Семантический анализ ИИ)
        ↓
Research Gaps (Выявление пробелов в знаниях)
        ↓
Sufficiency Evaluation (Детерминированная оценка достаточности в Core)
        ↓
Report (Генерация финального/частичного отчета)
```

Поисковое ядро, хранилище доказательств (Evidence Store) и механизмы поиска (Retrieval API) остаются общими и неизменными для всех типов и режимов исследований.

## 2. Разграничение полномочий в системе

### 2.1. Локальная LLM как планировщик и аналитик

ИИ-модель является исключительно вычислительным слоем для интерпретации смыслов и текстового синтеза. LLM не является самостоятельным источником фактов и не имеет права изменять состояния процессов.

Локальная LLM отвечает строго за:

- интерпретацию и декомпозицию исходного вопроса пользователя;
- формирование предложений для ResearchIntent;
- предложение гипотез и направлений поиска для исследовательского плана;
- смысловую интерпретацию и сопоставление извлеченных доказательств (Evidence);
- выявление содержательных пробелов в материале (ResearchGap);
- текстовый синтез итогового отчета на основе предоставленной ей выжимки.

### 2.2. Программное ядро (Search Core) как контролирующий орган и валидатор

Программный код системы обладает абсолютным приоритетом над предложениями ИИ. LLM предлагает — Core валидирует, списывает бюджет и принимает окончательные решения.

Ядро Search Core отвечает строго за:

- **Управление состояниями (Конечные автоматы):** Перевод исследования, сессий и задач по строгим системным триггерам.
- **Контроль многомерного бюджета:** Ведение учета и жесткое пресечение лимитов по количеству запросов, скачиваний страниц (fetches), документов, вызовов ИИ и общего времени работы.
- **Дедупликацию и независимость:** Нормализацию URL-адресов, выявление скрытых копий документов и оценку реальной самостоятельности источников.
- **Оценку достаточности (SufficiencyEvaluator):** Детерминированный математический расчет параметров завершения или продолжения поискового цикла. ИИ не может переопределить решение Core о завершении работы.

Управление конечными автоматами состояний (запуск, пауза, переходы, обработка сбоев) осуществляется исключительно ядром через формальные машины состояний, спецификация которых определена в разделе 2.3 данного ТЗ. Ни один компонент системы, включая ИИ-модель, не имеет права выполнять перевод состояния в обход формального автомата.

### 2.3. Формальные машины состояний

Каждая ключевая сущность системы управляется явным конечным автоматом состояний. Декларативного описания статусов недостаточно — для каждого автомата обязаны быть формально определены:

- Множество допустимых состояний (STATE);
- Множество допустимых переходов (STATE → STATE);
- Триггер (событие или условие), инициирующий каждый переход;
- Компонент, имеющий исключительное право на выполнение перехода;
- Данные, фиксируемые в SQLite при каждом переходе.

Разграничение ролей при переходах (A-02): **LLM предлагает, Watchdog сигнализирует, Core выполняет переход.** Только Core исполняет бизнес-переходы; GUI, LLM, Watchdog и System инициируют лишь допустимые команды/триггеры. Каждый переход атомарен со своей audit LogRecord. Команда (SOFT_STOP, HARD_STOP, PAUSE, RESUME, CANCEL) никогда не является состоянием; PARTIAL_REPORT и REPORT_TRUNCATED_PARTIAL — метаданные результата, а не состояния. Нормативная спецификация автоматов — STATE MACHINE SPECIFICATION v1.2.

Обязательные автоматы состояний системы:

1. **Study** — жизненный цикл исследования
2. **ResearchSession** — жизненный цикл сессии взаимодействия
3. **SearchTask** — жизненный цикл поисковой подзадачи
4. **MCP Operation** — жизненный цикл операции инструмента
5. **LLM Backend** — статус ИИ-бэкенда

Критические сценарии переходов, которые обязаны быть формализованы (SOFT_STOP/HARD_STOP — команды, PARTIAL_REPORT — метаданные результата, не состояния):

**Аварийное восстановление (LLM Failure / Recovery):**
```
ResearchSession: ACTIVE → LLM_UNAVAILABLE → SESSION_RESUMING → ACTIVE
Study: RUNNING — не обязан останавливаться из-за временной недоступности LLM backend
```

**Остановка пользователем:**
```
Soft Stop:  RUNNING --SOFT_STOP--> FINALIZING → COMPLETED
Hard Stop:  RUNNING --HARD_STOP--> USER_STOPPED
            (также PAUSED → USER_STOPPED и FREEZE_BUDGET_EXHAUSTED → USER_STOPPED по HARD_STOP)
```

**Исчерпание бюджета:**
```
RUNNING → BUDGET_EXHAUSTED → FREEZE_BUDGET_EXHAUSTED → FINALIZING → COMPLETED
(PARTIAL_REPORT — метаданные результата финализации через metadata/result status, не состояние Study)
```

Межавтоматная policy при восстановлении (Q-05): после recovery timeout Core переводит ResearchSession в `CLOSED`; Study получает `FAILED`, если нет безопасного fallback. Hard Stop всегда завершает активные SearchTask/Jobs кооперативной отменой; пользовательский partial report сохраняет Study в `USER_STOPPED`, не в `COMPLETED`.

Полная спецификация каждого автомата (множество состояний, таблица переходов, триггеры, права) выносится в отдельный нормативный контракт **STATE MACHINE SPECIFICATION v1.2** и является обязательным приложением к данному ТЗ.

## 3. Структура объекта Research Intent

После запуска исследования вопрос пользователя преобразуется программным ядром в строго структурированный объект ResearchIntent. Хранение списков сущностей внутри текстовых полей или JSON-массивов как источника истины запрещено — все параметры раскладываются по связующим таблицам БД SQLite.

Минимальная структура объекта:

- **goal (Цель исследования):** Задается через строгое перечисление (Enum): SELECT, COMPARE, ESTIMATE, EXPLAIN, DISCOVER, REVIEW, SUMMARIZE, EVALUATE, IDENTIFY.
- **entities (Объекты исследования):** Перечень целевых сущностей (Enum/Справочник): PRODUCT, PERSON, ORGANIZATION, METHOD, TECHNOLOGY, PAPER, MEDICAL_INTERVENTION, EVENT, SOFTWARE.
- **information_needs (Потребности в сведениях):** Что именно ищется: PRICE, PERFORMANCE, USER_EXPERIENCE, RELIABILITY, MECHANISM, CLINICAL_EVIDENCE, EXPERIMENTAL_STATUS, ADVANTAGES, LIMITATIONS, FREQUENCY, TREND, CONTRADICTION.
- **constraints (Жесткие ограничения):** Границы поиска: DATE_RANGE, GEOGRAPHY, LANGUAGE, BUDGET_LIMITS, PRODUCT_TYPE, TECHNICAL_REQUIREMENTS, EXCLUDE_TERMS.
- **source_preferences (Предпочтения по источникам):** Веса доверия к типам сайтов: USER_REVIEWS, OFFICIAL_SOURCES, ACADEMIC, CLINICAL, PRIMARY_RESEARCH, TECHNICAL_DOCUMENTATION. Предпочтение источника не гарантирует его использование, если он заблокирован или недоступен.
- **analysis_strategy (Стратегия анализа):** Набор правил обработки данных. Допустимые базовые стратегии: REVIEW_AGGREGATION, EVIDENCE_SYNTHESIS, COMPARISON, RANKING, TREND_ANALYSIS, FACT_FINDING, TECHNICAL_ANALYSIS.
- **output_requirements (Требования к отчету):** Формат вывода: RANKED_LIST, STATISTICS, SHORT_SUMMARY, EVIDENCE_TABLE, COMPARISON_TABLE, RESEARCH_GAPS, CONFIDENCE_SCORE.

## 4. Основные типы исследовательских задач (Research Task Types)

Тип задачи является системной характеристикой текущего исследования, настраивающей веса ранжирования в Core, а не отдельным поисковым движком. Система на уровне MVP поддерживает два главных полярных класса задач:

### 4.1. Сбор и агрегация мнений (Review Research)

**Назначение:** Получение статистически и качественно обоснованного представления о массовом пользовательском опыте (например, выбор обуви на широкую стопу по отзывам).

**Требуемая цепочка данных:** Строго последовательная реляционная фиксация: Entity (Объект) → Attribute (Характеристика) → Observation (Наблюдение) → Evidence (Доказательство-цитата) → Source (Первоисточник).

**Правило агрегации:** Система обязана группировать независимые наблюдения (Observations). Допускается расчет математических величин (count, ratio, percentage, mean, median) только на основе верифицированных уникальных авторов. Один отзыв не является фактом для всей выборки.

### 4.2. Поиск жестких доказательств (Evidence Research)

**Назначение:** Формирование проверяемой, авторитетной базы первоисточников по научному или техническому вопросу (например, экспериментальные методы заживления ран).

**Шкала достоверности:** Система обязана требовать от ИИ-модели классификации найденных утверждений по жесткой шкале: ESTABLISHED (установлено), SUPPORTED (подтверждено), PROMISING (перспективно), EXPERIMENTAL (экспериментально), CONTRADICTED (противоречиво), UNKNOWN (неизвестно). Классификация базируется на типе источника и его авторитетности.

Разделение оценки качества и статуса утверждения (`A-10`): класс доказательности (ESTABLISHED…UNKNOWN) хранится как отдельное поле Claim и **не меняется** оценкой качества источника (SourceQualityAssessment). SourceQualityAssessment scope'ится к Study/domain/mode/config revision и хранится отдельно; confidence является порядковой мерой обоснованности, а не вероятностью. Оценка качества источника не пересчитывает и не переопределяет статусы утверждения (support_status).

## 5. Эпистемическая цепочка доказательности (Epistemic Chain)

Каждое аналитическое утверждение в финальном отчете должно иметь прозрачный и сквозной программный путь проверки («Эпистемическую цепочку»). Разрыв цепочки или ручное назначение ИИ связей без опоры на базу данных запрещены.

Схема сквозной связи:

```
Source (Сайт/Файл)
    ↓ [Реляционная ссылка]
Document (Скачанный текст)
    ↓ [Позиционирование: символы старт/энд]
DocumentChunk (Основной чанк поиска) + Context Chunks (Окно соседних чанков ±1)
    ↓ [Детерминированный хэш текста]
Evidence (Выделенная цитата-доказательство)
    ↓ [Извлечение структуры через ИИ]
Observation (Конкретное наблюдение: Объект + Свойство + Значение)
    ↓ [Смысловое объединение]
Claim (Итоговое аналитическое утверждение в отчете)
```

Для аналитических задач, не требующих промежуточной статистики свойств, допускается сокращенный маршрут: Evidence → Claim.

## 6. Адаптивный цикл поиска (Adaptive Research Loop)

Исследование выполняется итерационными циклами под управлением конечного автомата ядра Search Core:

```
   [ Входной вопрос ]
             ↓
 ┌──► Выполнение поиска (Retrieval)
 │           ↓
 │    Извлечение доказательств (Extract Evidence из окна чанков ±1)
 │           ↓
 │    Построение наблюдений и утверждений (Observations / Claims)
 │           ↓
 │    Анализ пробелов в знаниях (Evaluate Research Gaps через LLM)
 │           ↓
 │    Оценка достаточности (SufficiencyEvaluator в Core)
 │           │
 │           ├── [ Статус: CONTINUE ] ──► Сборка новых целевых запросов ──┐
 │           │                                                            │
 │           └── [ Статус: STOP_* ]                                       │
 │                     ↓                                                  │
 └─────────────────────◄──────────────────────────────────────────────────┘
                       ↓
            [ Синтез отчета (Report) ]
```

**Правила генерации новых запросов:**

Начальный план исследования (A-15): стартовый план обязан создавать объекты ResearchGap с reason = MISSING_DATA для всех непокрытых информационных потребностей (information_needs). Поиск первоисточника начинается с сохранённого gap; LLM не создаёт persistent SearchTask самостоятельно — только SearchTaskDraft, связанный с сохранённым gap.

Новые поисковые задачи (SearchTask) создаются ИИ-моделью только на основании зафиксированных в базе данных объектов ResearchGap (Пробел исследования). Каждый объект ResearchGap обязан содержать поля: question (целевой довыясняющий вопрос), reason (причина появления пробела), missing_evidence (чего именно не хватает) и recommended_query (вариант текстового запроса). Ядро Core проверяет этот запрос через Query Fingerprint и блокирует его выполнение при совпадении с историей поиска.

### 6a. Формализация многомерного бюджета

Бюджет исследования является многомерным объектом, каждый компонент которого контролируется независимо.

Структура бюджета:

```
ResearchBudget:
├── step_budget — лимит итераций адаптивного цикла
├── network_budget — общее число сетевых запросов
├── fetch_budget — лимит скачанных страниц
├── tool_call_budget — лимит вызовов MCP-инструментов
├── llm_call_budget — лимит вызовов ИИ-модели
├── llm_token_budget — лимит токенов контекста (суммарный)
└── time_budget — общее время исследования
```

Правила управления бюджетом (Q-04, контрактная модель BUDGET CONTRACT v1.0 — reserve → commit/release):

1. **Кто управляет:** Исключительно ядро Search Core через единый бюджетный API `reserve → commit/release` и `extend_budget`. LLM не имеет права изменять бюджет; списания в MCP adapter запрещены.
2. **Как списывается:** Перед billable операцией Core резервирует все необходимые dimensions одной SQLite-транзакцией (`reserve`). После операции фактическое потребление фиксируется через `commit`, неиспользованный резерв освобождается через `release`. Повторный вызов с тем же `operation_id`/idempotency key не создаёт второго списания.
3. **Что считается операцией:** Тарификация по 7 dimension (step, network, fetch, tool_call, llm_call, llm_token, time) — единицы списания и момент commit определяются таблицей тарификации BUDGET CONTRACT v1.0. Retry network потребляет network; cache hit сеть не потребляет; preview, read-only diagnostics, cancel и recovery reads не требуют research budget.
4. **Что происходит при available == 0:** Операция не начинается. Study проходит BUDGET_EXHAUSTED → FREEZE_BUDGET_EXHAUSTED, новые SearchTask получают REJECTED_BUDGET; при финализации формируется partial report, если доступен уже сохранённый валидный материал.
5. **Можно ли расширить:** Только по явному действию пользователя через GUI/Core command (`extend_budget`), что создаёт новую неизменяемую ResearchConfig revision и LogRecord. Никаких silent budget increases или изменения лимитов «на лету».
6. **Что сохраняется:** Состояние бюджета — в BudgetState/BudgetLedger (раздел 3 ТЗ, BUDGET CONTRACT v1.0), лимиты — в неизменяемых ревизиях ResearchConfig.

Каждое резервирование и списание бюджета обязано быть атомарной операцией в рамках единой транзакции SQLite.

## 7. Детерминированная оценка достаточности (Sufficiency Criteria)

Решение о прекращении поисковых циклов принимает строго модуль SufficiencyEvaluator, встроенный в ядро программы. Он проверяет текущие измеряемые метрики исследования и возвращает один из пяти финальных статусов:

- **CONTINUE:** Цели не достигнуты, ресурсы есть, новые уникальные данные поступают — продолжить поиск.
- **STOP_SUFFICIENT:** Набрано необходимое число уникальных подтверждений, цели исследования закрыты — успешное завершение.
- **STOP_BUDGET:** Исчерпан хотя бы один из лимитов многомерного бюджета (время, лимит вызовов ИИ, лимит скачиваний) — принудительный останов.
- **STOP_NO_INFORMATION_GAIN:** Последние поисковые циклы приносят только дубликаты текстов или похожие сайты, информационный прирост упал ниже 5% — остановить из-за бесперспективности.
- **STOP_NO_AVAILABLE_SOURCES:** Все найденные источники заблокированы, выдают ошибки доступа или защищены капчей — остановить поиск.

### Базовый strategy profile (MVP, EVIDENCE) — решение Q-03

Консервативные пороги для strategy profile EVIDENCE (MVP):

- `question_coverage = 1.0` — все информационные потребности покрыты;
- `attribute_coverage = 1.0` для обязательных attributes;
- `min_independent_sources = 2`;
- `min_verified_evidence = 3`;
- `contradiction_count = 0` — неразрешённых противоречий нет;
- `information_gain_threshold = 0.05`.

Формула прироста за итерацию:

```
gain = new_verified_evidence_count / max(1, verified_evidence_count_before_iteration)
```

Для первой итерации знаменатель равен 1. `STOP_NO_INFORMATION_GAIN` применяется после двух последовательных завершённых итераций с gain < 0.05, если нет открытого критического gap с доступным бюджетом.

Для `AGGREGATION` обязательные attributes также должны быть покрыты полностью; минимум уникальных верифицированных авторов задаётся отдельным профилем. Анонимные/неверифицированные авторы не закрывают этот минимум.

Детерминированный приоритет решения:

```
STOP_BUDGET > STOP_NO_AVAILABLE_SOURCES > STOP_NO_INFORMATION_GAIN > STOP_SUFFICIENT > CONTINUE
```

`STOP_SUFFICIENT` запрещён при неразрешённых противоречиях или если любой обязательный threshold не выполнен. Каждая проверка пишет `SufficiencyEvaluation`, snapshot metrics и `SufficiencyRuleHit` (см. раздел 3 ТЗ).

### Формальный контракт SufficiencyEvaluator

SufficiencyEvaluator является детерминированным модулем ядра и функционирует по следующей схеме:

```
Входные метрики (из CoverageCalculator):
├── independent_source_count — число независимых источников
├── attribute_coverage — покрытие целевых характеристик
├── question_coverage — покрытие информационных потребностей
├── information_gain — дельта прироста за последнюю итерацию
├── evidence_count — число верифицированных доказательств
└── contradiction_count — число неразрешённых противоречий

    ↓ [Детерминированная формула, без участия LLM]

SufficiencyEvaluator:
├── Проверка каждого порога из threshold_settings (ResearchConfig)
├── Вычисление взвешенного скоринга покрытия
└── Выбор одного из пяти решений

    ↓

Выход:
├── Решение: CONTINUE | STOP_SUFFICIENT | STOP_BUDGET |
│            STOP_NO_INFORMATION_GAIN | STOP_NO_AVAILABLE_SOURCES
├── Обоснование: структурированный список сработавших правил
└── Запись в SufficiencyEvaluation (журнал решений)
```

Критическое правило:

- LLM может запрашивать объяснение результата у ядра.
- LLM может предложить альтернативное направление поиска.
- LLM НЕ МОЖЕТ переопределить детерминированное решение ядра.
- Единственное основание для продолжения — решение CONTINUE от SufficiencyEvaluator.

### Сценарий «Низкой независимости источников» (Low-Independence Scenario)

Если система в процессе поиска обнаруживает, что несколько разных веб-страниц (URL) содержат идентичный текст или цитируют один и тот же исходный документ (например, 5 копий одного пресс-релиза), ядро Core обязано зафиксировать количество реальных независимых источников равным 1.

Если альтернативных независимых подтверждений в сети больше не найдено, поисковый цикл останавливается со следующими параметрами:

- Выставляется статус завершения: STOP_SUFFICIENT или STOP_NO_INFORMATION_GAIN (в зависимости от настроек стратегии).
- В базу данных записывается ResearchGap с обязательной пометкой reason = LOW_INDEPENDENCE.
- Для всех связанных утверждений выставляется статус достоверности INSUFFICIENT_EVIDENCE (Недостаточно доказательств).
- Программа формирует предварительный отчет (Partial Report), в котором на первой строчке выводится жесткое предупреждение для пользователя: «Внимание: Все выводы исследования базируются на одном единственном первоисточнике, обнаруженные дубликаты исключены из расчета достоверности».

### Формальная модель независимости источников

Для определения реального числа независимых подтверждений система обязана классифицировать каждую пару источников через сущность SourceRelation с использованием следующих типов связей:

- **COPY** — полное или почти полное копирование текста
- **REWRITE** — переработка/рерайт исходного материала
- **CITATION** — цитирование или ссылка на первичный источник
- **SAME_PRIMARY** — оба источника ссылаются на один первичный документ
- **UNKNOWN** — характер связи не определён

**Независимость источников на уровне Claim (Q-02):** консервативное правило подсчёта:

- Независимость оценивается на уровне `Claim`/исследовательского вывода, а не только сайта: связь, применимая к одному Claim, не превращает весь Source в зависимый для всех Claims.
- Источники со связью COPY, REWRITE, SAME_PRIMARY объединяются в один provenance cluster и считаются ОДНИМ независимым источником.
- Источник со связью CITATION считается зависимым от цитируемого первоисточника по конкретному Claim.
- Источники со связью UNKNOWN НЕ увеличивают число независимых подтверждений.
- Источник без установленной связи считается независимым только если у него иной canonical identity/domain и нет evidence of shared primary.
- При недостатке данных итоговый статус — INSUFFICIENT_EVIDENCE, а не искусственное увеличение confidence.

Формула расчёта:

```
independent_source_count(claim) =
    число provenance-кластеров, связанных с Claim,
    которые не являются COPY, REWRITE, SAME_PRIMARY,
    не являются зависимыми CITATION и не имеют UNKNOWN relation
```

Алгоритм подсчёта (S-11):

1. Для каждого Claim строятся provenance-кластеры: COPY, REWRITE и SAME_PRIMARY сливаются в один кластер вместе с их первичными источниками.
2. Зависимые CITATION сводятся к первичному подтверждению — они добавляют независимость только через первоисточник, на который ссылаются.
3. UNKNOWN не добавляет подтверждений; новое числовое значение для UNKNOWN не вводится.
4. Циклы в графе `SourceRelation` (в том числе образованные CITATION) разрешаются консервативно: все участники цикла попадают в один provenance-кластер.
5. CITATION на отсутствующий в базе первоисточник трактуется как UNKNOWN.

При неопределённости итог — `INSUFFICIENT_EVIDENCE`, а не искусственное увеличение confidence.

На этапе MVP не требуется полностью автоматическое определение независимости. Допускается консервативная эвристика с ручной верификацией через SourceRelation.

## 8. Архитектурная совместимость слоев

Слой исследовательского анализа является надстройкой над поисковым ядром и базой данных. Он обязан строго соблюдать интерфейсы и контракты нижних уровней.

Внедрение любой новой аналитической стратегии (например, добавление финансового или юридического анализа в Post-MVP) должно реализовываться исключительно как программное расширение (Extension Point) и не имеет права требовать изменения структуры таблиц хранения документов, кэша, сетевых адаптеров или базового протокола MCP.
