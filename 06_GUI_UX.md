## 9. Graceful Abort

Команды, а не состояния (A-02): `SOFT_STOP` и `HARD_STOP` являются **командами/триггерами**, отправляемыми GUI в Core, а не показателями статуса. GUI не записывает статусы напрямую — он инициирует допустимую команду, переход выполняет Core через нормативную FSM (STATE MACHINE SPECIFICATION v1.2).

### Soft Stop

- новые сетевые запросы не запускаются;
- текущие безопасно завершаются;
- разрешается финальный synthesis;
- создается partial report.

### Hard Stop

- новые операции запрещаются;
- asyncio tasks отменяются;
- cancellation является кооперативной;
- **unsafe thread kill запрещён (A-14)**: активные CPU threads не уничтожаются принудительно — они завершаются в безопасной точке через cancellation token и ограниченные батчи;
- состояние фиксируется checkpoint'ом;
- SQLite остается консистентной;
- после остановки можно сформировать partial report.

### Кооперативная отмена CPU-задач

Операции, выполняемые в CPU-потоках (чанкинг, индексация, стемминг, массовая обработка), не могут быть прерваны мгновенно через отмену асинхронных задач. Для них реализуется механизм кооперативной отмены:

1. **Cancellation token:** Каждой долгой операции передаётся cancellation token (через механизм `threading.Event`).
2. **Периодическая проверка:** Долгие циклы обязаны проверять токен на каждой итерации или после каждого ограниченного батча.
3. **Soft Stop:** Токен устанавливается, операция завершается после текущей итерации, состояние сохраняется.
4. **Hard Stop:** Токен устанавливается; операция завершается в ближайшей безопасной точке с фиксацией checkpoint. **Принудительное прерывание потока (thread kill) не применяется.**

**Неотменяемые CPU-библиотеки (A-14):** операции, использующие CPU-библиотеку, не предоставляющую точек проверки (например, монолитный нативный вызов), выполняются в **дочернем процессе без права записи в SQLite**; отмена такого процесса выполняется безопасным завершением процесса, а консистентность БД не зависит от его состояния.

**Требования к точкам проверки:**

- Чанкинг: проверка токена после каждого чанка.
- Индексация: проверка токена после каждого батча чанков.
- Стемминг: проверка токена после каждого документа.
- Перестроение индекса: проверка токена после каждого батча.

**При любом типе остановки:**

- Уже обработанные данные сохраняются.
- Консистентность гарантируется.
- Фиксируется контрольная точка.
- Поздние результаты отменённой операции отбрасываются (A-14).

## 13. Projects

GUI поддерживает:

- create;
- rename;
- archive;
- delete with confirmation;
- transfer Study.

При новом Study можно выбрать:

- текущий Project;
- отдельные Studies;
- отдельные documents;
- весь локальный архив.

Переключение проектов = переключение активной БД. GUI отображает список проектов из реестра. Создание проекта = создание нового .db файла + записи в реестре. Архивация = смена статуса в реестре, файл сохраняется на диске.
