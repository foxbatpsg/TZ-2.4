# План правок: A-22…A-25 (класс LLM, embedding-ready схема, BM25-движок, лемматизация)

**Статус:** решения согласованы с владельцем требований 2026-09-15 (обсуждение ретривал-бенчмарка и benchmark-spike). **Внесение — отдельная сессия.** До внесения в корпус правки не применяются.
**Правило исполнения:** каждая правка — замена `old_text → new_text` (НЕ `insert_line`); после каждой правки — контрольное чтение; после каждой части — валидатор (`РЕЗУЛЬТАТ: PASS`); каждая часть — отдельный коммит; push — в конце.
**Общий принцип (указание владельца):** реализацию будет вести ИИ-агент — решения, которые можно принять сейчас, фиксируются в корпусе, чтобы исключить возвраты; в формулировках не оставлять «на усмотрение исполнителя» там, где решение уже принято.

## ЧАСТЬ 1. A-22 — минимально поддерживаемый класс LLM (верхней границы нет)

**Решение владельца:** 12–14B Q4/Q5 — это **минимум**; будут запускать максимальную модель, которую потянет железо (в т.ч. GPU 22–48 ГБ); верхней границы нет.

**Норма (внести в `02_Архитектура и системные принципы.md`, конец §5.3):**

> Минимально поддерживаемый класс LLM (A-22): минимально поддерживаемый класс локальной модели — 12–14B в квантовании Q4/Q5 (GGUF); **верхней границы не устанавливается** — модели большего размера разрешены при достаточных ресурсах машины через тот же backend-контракт (OpenAI-совместимый HTTP, `05` §1–2). Бюджет контекста определяется динамически (A-12); профиль исполнения и требования к модели от её размера не зависят. Утверждённые TARGET-параметры среды — §5.3.

**Правки:**
1. `02` §5.1 (стр. ~134): «Локальная ИИ-модель класса 12–14B запускается…» → «Локальная ИИ-модель **минимально поддерживаемого класса 12–14B (A-22)** запускается…».
2. `02` §6 (стр. ~159): «Локальные ИИ-модели класса 12–14B имеют жесткие лимиты…» → «Локальные ИИ-модели (минимальный класс 12–14B, A-22) имеют жесткие лимиты…».
3. `05` §1 (стр. ~13): «Система проектируется под использование локальных ИИ-моделей класса 12–14B.» → «Система проектируется под локальные ИИ-модели: минимально поддерживаемый класс 12–14B (A-22), верхняя граница размера не нормируется.».
4. `07` §25 (стр. ~393): «локальная 12–14B LLM может выполнить исследование через MCP» → «локальная LLM минимально поддерживаемого класса 12–14B (A-22) может выполнить исследование через MCP».

## ЧАСТЬ 2. A-23 — embedding-ready схема (прistsковка без переделки)

**Решение владельца:** эмбеддинги в MVP не входят (non-goal сохраняется), но стыковка «без переделки» гарантируется корпусом, а не надеждой на интерфейс: зона риска — схема БД.

**Норма (внести в `03_Модель данных и хранение.md`, §11 DocumentChunk, после абзаца о числовых сигнатурах A-03, стр. ~370):**

> Расширяемость ретривал-хранения (A-23): векторное хранение проектируется как **боковая таблица** `ChunkEmbedding(chunk_id, model_id, vector, created_at)` рядом с `DocumentChunk` — без изменения существующих таблиц; внешний ключ к `DocumentChunk`, физическое удаление чанка каскадно удаляет запись. Подключение эмбеддингов и переранжировщиков выполняется через изолированные провайдеры (`02` §5.2, RetrievalProvider/RankingProvider) и добавляется отдельной **append-only миграцией** (`03` §21, S-17). Реализация эмбеддингов — вне MVP (`07` §26); настоящая норма гарантирует, что её добавление не потребует переделки схемы, конвейера или интерфейсов.

**Правки:**
1. `03` §11 — вставить норму (см. выше).
2. `02` §5.2 — после слов «(RetrievalProvider, RankingProvider)» добавить: «; схема хранения векторов — боковая таблица (A-23, `03` §11)».

**Синхронизация:** `INDEX.md` §5 (карта сущностей — строка `ChunkEmbedding` с пометкой «зарезервировано, вне MVP»); §3 — строка A-23. Валидатор.

## ЧАСТЬ 3. A-24 — хранимый BM25-индекс (движок выбран)

**Решение владельца:** скорость некритична, качество важнее; выбор движка принимается априори по архитектурным характеристикам, без бенчмарка: **FTS5 (персистентный индекс в Project DB) — основной путь**; rank_bm25 — запасной вариант для малых объёмов. Пересборка индекса при каждом запуске недопустима.

**Норма (внести в `04_Search Core.md`, конец §14, перед §14.1, стр. ~256):**

> Хранимый BM25-индекс (A-24): поисковый индекс строится на SQLite FTS5, персистентном в Project DB; в индексируемую колонку помещается лемматизированный токен-поток чанков (A-25), что позволяет использовать штатный tokenizer FTS5 без кастомного C-tokenizer (из Python недоступного). In-memory BM25 (rank_bm25) — запасной вариант только для малых объёмов. **Пересборка индекса при каждом запуске приложения недопустима**; жизненный цикл индекса — §14a.

**Правки:**
1. `04` §14 — вставить норму (см. выше).
2. `02` §5.1 (стр. ~133): «используется детерминированный алгоритм BM25, развернутый силами CPU (библиотека `rank_bm25` или встроенные механизмы SQLite FTS5)» → «используется детерминированный алгоритм BM25 на SQLite FTS5 — персистентный индекс в Project DB (A-24); in-memory rank_bm25 — запасной вариант для малых объёмов».

**Синхронизация:** `INDEX.md` §3 — строка A-24; §8 (карта механизмов) — строку «BM25 и RU-морфология» дополнить упоминанием A-24. Валидатор.

## ЧАСТЬ 5. Порядок исполнения и контроль

1. **Коммит 1:** Часть 1 (A-22) → валидатор → `A-22: минимально поддерживаемый класс LLM, верхняя граница снята (02 §5.3, 05 §1, 07 §25)`.
2. **Коммит 2:** Часть 2 (A-23) → валидатор → `A-23: embedding-ready схема — боковая таблица ChunkEmbedding (03 §11)`.
3. **Коммит 3:** Часть 3 (A-24) → валидатор → `A-24: персистентный BM25-индекс на FTS5 (04 §14, 02 §5.1)`.
4. **Коммит 4:** Часть 4 (A-25) → валидатор → `A-25: словарная лемматизация — реализация A-13 (04 §14.1)`.
5. **Финал:** запись в память (`.workbuddy-ai/memory/`); `git status` чистый (кроме рабочих файлов владельца: `prompt.txt`, планы); push.

**Что правки НЕ меняют:** FSM, MCP-контракты, бюджетную модель, контур безопасности (N-03/Q-10), базовую схему данных. Ретривал-бенчмарк на golden-корпусе остаётся только как приёмочный инструмент G-04 (уже нормирован S-15); отдельная бенчмарк-церемония для выбора морфологии/движка и GUI-замеры **отменены решением владельца** (обсуждение 2026-09-15). Benchmark-spike Q-12 сохраняется в объёме: два профиля (CPU-baseline и GPU-extended), результаты идут в критерии G-08/G-10/G-11.
