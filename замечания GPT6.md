## Краткий ответ

**Да, проект технически реализуем указанными средствами. Обязательной замены стека не требуется.** Python, CustomTkinter, SQLite/FTS5 и локальный GGUF-runtime подходят для offline-first Windows MVP. Но текущий набор документов ещё не стоит передавать агентам как полностью непротиворечивый исполняемый контракт.

### Что спроектировано хорошо

- Детерминированный Core отделён от недетерминированной LLM; только Core владеет бизнес-переходами.
- Изоляция по Project DB, single writer, WAL, outbox, backup и immutable Evidence уже предусмотрены — это не пропущенные технологии.
- Budget reserve → commit/release, идемпотентность, formal FSM и кооперативная отмена заданы правильно.
- BM25 + обязательная RU-морфология дают разумный CPU baseline. Векторный поиск можно оставить post-MVP.

### Три блокера до затрагивающих их TASK

1. **MCP-host и профили запуска.** MCP не заменяет HTTP-инференс. Требуется явный владелец agent loop и согласованный процессный контракт.
2. **Q-08: Document и URL.** Новая версия при смене URL конфликтует с уникальным content_hash и дедупликацией тела.
3. **SourceRelation.** Claim-specific семантика конфликтует с уникальностью только по паре Source и Study.

### Что уточнил повторный анализ

EPIC-07…11 доступны полностью: MCP, GUI, Integration & Resilience, Final QA, Packaging / Portable. Поэтому новый EPIC упаковки не нужен — расширьте EPIC-11. Правило UNKNOWN и формула независимости уже присутствуют в разделе 01 §7; уточнять нужно алгоритм и пограничные случаи. Разные версии приложений допустимы при едином baseline. EPIC-10 «морфология если включена» необходимо привести к обязательному A-13.

### Концептуальные ограничения

**LLM ≠ доказательство истинности.** JSON Schema, hash и ссылка на цитату проверяют форму и происхождение, но не гарантируют смысловую поддержку вывода. Нужны uncertain/manual review и adversarial tests. Извлечённый текст остаётся недоверенным, даже если HTML удалён.

**CPU-only ≠ быстро на любом ПК.** Для 12–14B оцените weights + KV-cache + контекст + runtime, одновременно с индексацией. 32 GB RAM и 6-ядерный CPU — лишь предложенный профиль для spike, не подтверждённые минимальные требования. Точные сроки и tokens/s без benchmark обещать нельзя.

**CustomTkinter не блокер.** Прототипируйте DPI, таблицы, evidence tree и доступность. Рассматривать PySide6 стоит лишь при измеримом несоответствии UX, иначе миграция увеличит объём.

**Не расширять MVP без причины.** Transformers, VLM/OCR, embeddings, vector DB, LangChain и микросервисы не являются недостающими обязательными технологиями. Если нужны сканы/изображения, сначала утвердите отдельный ingestion/OCR/VLM-контракт.

### Как двигаться дальше

Сначала baseline и ADR → затем согласованные API/данные → общий набор fixtures и Gate → только затем реализация. Используйте 8 подготовленных задач. Это подробные инструкции по правкам ТЗ, а не заявление, что исходные файлы уже исправлены.

Карточки в каталоге Research_Prompt_Suite_Task_Cards_Astra1 не включены в этот снимок и требуют отдельной сверки при передаче конкретной TASK. Код Windows-приложения и аппаратные benchmark не проверялись. Новые ADR, инструменты поставки и целевые метрики — предложения архитектора, а не действующие нормы ТЗ.

## N-01 [P0] Явно определить MCP-host и контур LLM

Источник: 05_Взаимодействие с LLM и протокол MCP.md · §2–3 · EPIC-07

### Наблюдение
Схема «LLM → MCP → Core» пропускает host/client: модель возвращает tool calls через HTTP, но сама не является stdio-клиентом. Для автономного GUI не определён владелец агентного цикла. Ограничение единого процесса требует согласованной схемы запуска.

### Предлагаемая правка
ADR-001 (предложение): в desktop-профиле Application Orchestrator вызывает LLM по HTTP и передаёт проверенные tool calls в единый ToolDispatcher/Application API. MCP stdio — внешний адаптер для Cline/OpenCode, а не протокол инференса. Ввести отдельный headless-профиль --mcp-stdio; исключить одновременное владение одной Project DB двумя Core. Это изменение требования «строго через MCP», поэтому сначала согласовать разделы 02/05 и EPIC-07. Если строгость MCP сохраняется, требуется отдельный утверждённый host и пересмотр границы процессов.

### Приёмка
Диаграмма содержит host, client, server, HTTP и stdio; указан владелец процесса/БД. Один end-to-end tool call проходит validation, budget, idempotency и Core. Повторный запуск не создаёт второго владельца Project DB.

## S-12 [P0] Закрыть версионирование документов — Q-08

Источник: 03_Модель данных и хранение.md · §9, 9a · QA §17

### Наблюдение
A-21 требует новый Document при смене URL, но content_hash уникален и тело должно храниться один раз. Новый URL с прежним текстом не может породить новый уникальный content_hash. В QA Q-08 прямо помечен открытым.

### Предлагаемая правка
ADR-002 (предложение): идентичность Document определяется очищенным содержимым. Новый URL при прежнем hash добавляет DocumentSourceOccurrence, не меняет тело, document_id и Evidence. Новый текст создаёт новый Document; для истории при необходимости ввести нормализованную связь ревизий отдельной миграцией. Исправить формулировку A-21 одновременно в разделах 03, 07 и зависимых TASK. Не подменять content_hash хешем URL.

### Приёмка
Тесты: тот же текст/другой URL → 1 Document, 2 происхождения; изменённый текст → новый Document; прежние Evidence и chunk_id неизменны; retry не дублирует происхождение. Q-08 закрыт только после утверждения ADR.

## N-02 [P0] Согласовать уникальность SourceRelation с Claim

Источник: 03_Модель данных и хранение.md · §8a · Q-02

### Наблюдение
SourceRelation допускает claim_id, однако уникальность задана только по (study_id, source_source_id, target_source_id). Для одной пары источников невозможно сохранить разные отношения по двум Claim. claim_id также описан без явного FOREIGN KEY.

### Предлагаемая правка
ADR-003: определить направленность пары и политику одной текущей связи на область действия. Ввести два частичных UNIQUE-индекса: для claim_id IS NOT NULL — (study_id, source_source_id, target_source_id, claim_id); для claim_id IS NULL — исходная тройка. Добавить FK на Claim и проверку принадлежности Claim/Source к той же Study. Утвердить приоритет claim-specific связи над общей. Миграция предварительно проверяет дубликаты и не удаляет их молча.

### Приёмка
Два Claim одной пары хранят разные отношения; дубликат в одной области отклоняется; глобальный NULL не позволяет дублирование; ссылка на чужой Claim отклоняется. Проверены global/specific override и откат миграции.

## S-10 [P1] Типизировать события Watchdog → Core

Источник: 02_Архитектура и системные принципы.md · §3 · EPIC-03/06

### Наблюдение
Запрет Watchdog писать в БД ясен; транспорт, дедупликация, backpressure и завершение очереди не определены.

### Предлагаемая правка
