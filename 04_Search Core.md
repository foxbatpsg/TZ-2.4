# НАЦИОНАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ) v2.4
## Раздел 4. Поисковое ядро (Search Core)

**Статус:** Утвержденный архитектурный контракт (Финальная монолитная редакция)
**Назначение:** Определение архитектуры детерминированного информационного слоя, алгоритмов нормализации, дедупликации, фильтрации и ранжирования источников данных.

---

## 1. Назначение

Поисковое ядро (Search Core) является строго детерминированным информационным слоем системы, написанным на языке Python.

Оно функционирует независимо, не может быть подменено или модифицировано эвристиками ИИ-модели на ходу. Search Core осуществляет жесткий контроль за тем, чтобы ИИ не имел прямого доступа к сырому массиву данных из сети Интернет и получал исключительно безопасную, очищенную, отфильтрованную и строго сфокусированную текстовую информацию.

---

## 2. Основной конвейер обработки данных (Pipeline)

Движение и трансформация информации в поисковом ядре выполняются по строго заданной цепочке шагов:

```
Research Intent (Цель исследования)
        ↓
Search Task (Поисковая подзадача с query_fingerprint)
        ↓
Candidate Retrieval (Сбор кандидатов через SourceAdapter)
        ↓
URL Normalization (Нормализация адресов)
        ↓
Deduplication (Трехуровневое удаление дубликатов)
        ↓
Candidate Ranking (Раздельное ранжирование релевантности и качества)
        ↓
Top-K Selection (Отбор лучших кандидатов для скачивания)
        ↓
Document Fetch (Скачивание полных страниц с rate limiting)
        ↓
Clean & Extract (Очистка от HTML-мусора и разметка)
        ↓
Deterministic Chunking (Нарезка на чанки с overlap_group_id)
        ↓
Local Retrieval (Локальный поиск по чанкам через BM25)
        ↓
Evidence Extraction (Извлечение цитат с окном контекста ±1 чанк)
        ↓
Observation / Claim Extraction (Структурирование данных)
        ↓
Coverage / Gap / Contradiction Evaluation (Анализ покрытия и пробелов)
```

---

## 3. Интерфейс SourceAdapter

Каждое внешнее поисковое направление или веб-ресурс подключается к системе через стандартизированный интерфейс SourceAdapter.

**Базовый программный контракт адаптера обязан реализовывать следующие методы:**

- `search(query, filters, limit) -> List[Candidate]` — поиск кандидатов по заданному текстовому запросу.
- `fetch(url) -> RawDocument` — скачивание полного содержимого целевого документа по его веб-адресу.
- `capabilities() -> AdapterCapabilities` — возврат поддерживаемых адаптером типов данных, фильтров и ограничений.
- `health() -> AdapterHealthStatus` — диагностика доступности целевого шлюза или сервиса.

Компонент SourceAdapter является исполнительным механизмом и категорически не должен содержать в себе бизнес-логику исследования (Study), управления состояниями сессий или лимитов общего бюджета.

---

## 4. Интерфейс RetrievalProvider

Компонент RetrievalProvider инкапсулирует в себе конкретную реализацию движка локального поиска по уже скачанным и нарезанным материалам текущего исследования.

**Обязательный интерфейс провайдера:**

- `name() -> str` — уникальное имя провайдера.
- `capabilities() -> ProviderCapabilities` — поддерживаемые режимы фильтрации и поиска.
- `search(study_id, query, filters, limit) -> List[DocumentChunk]` — выполнение поиска по локальным чанкам с жесткой изоляцией контекста исследования.
- `index(chunks: List[DocumentChunk]) -> bool` — добавление новых нарезанных чанков в локальный поисковый индекс.
- `delete(document_id) -> bool` — удаление кусков документа из локального поискового индекса.
- `is_available() -> bool` — проверка работоспособности локального движка.

**Требование к MVP:** На этапе MVP обязательной к реализации является модель BM25RetrievalProvider, функционирующая исключительно за счет мощностей центрального процессора (CPU-Only). В качестве расширений на этапах Post-MVP через этот же неизменный интерфейс могут подключаться EmbeddingRetrievalProvider (векторный поиск), HybridRetrievalProvider (гибридный поиск) и RerankingProvider (нейросетевой переранжировщик), что гарантирует стабильность внешнего Study API.

## 5. Поиск кандидатов (Candidate Retrieval)

На этапе первичного поиска сетевой адаптер SourceAdapter возвращает в ядро строго компактные карточки кандидатов, а не полные тексты страниц.

**Карточка кандидата содержит:**

- `url` — исходный веб-адрес страницы;
- `title` — заголовок страницы из поисковой выдачи;
- `snippet` — короткий ознакомительный фрагмент текста;
- `source` — идентификатор поисковой системы или площадки;
- `identifiers` — уникальные постоянные ключи при наличии (DOI, PMID, arXiv);
- `date` — дата публикации материала;
- `metadata` — неструктурированные сопутствующие метаданные.

Стандартный лимит выборки составляет от 5 до 10 кандидатов на один поисковый вызов. Массовая автоматическая загрузка полных текстов документов на данном этапе категорически запрещена.

Нормализация и фильтрация (`A-03`): фильтрация, дедупликация и JOIN выполняются Core по нормализованным реляционным таблицам и не требуют разбора сериализованных списков/JSON. Никакой этап конвейера не извлекает связи из текстовых полей с разделителями или JSON-массивов — все связи выбираются через классические JOIN по внешним ключам (см. раздел 3 ТЗ, §2).

## 6. Генератор ознакомительных фрагментов (Snippetizer)

В случае отсутствия или недостаточной информативности сырого поискового фрагмента, ядро системы задействует детерминированный алгоритм Keyword-Density Snippetizer. При наличии текста документа алгоритм выполняет следующие шаги:

1. Выполняет разбиение доступного текста на отдельные предложения.
2. Рассчитывает плотность совпадения и частоту вхождения ключевых слов исходного поискового запроса для каждого предложения.
3. Выбирает предложение (или группу предложений) с наивысшим показателем смысловой плотности.
4. Добавляет к выбранному предложению минимальный окружающий контекст (соседние слова слева и справа).
5. Жестко ограничивает итоговую длину фрагмента.

Максимальный лимит длины сниппета должен быть строго конфигурируемым в настройках ядра (значение по умолчанию — 200 символов). Сниппет используется исключительно для первичной оценки релевантности и ни при каких условиях не может быть признан системой в качестве валидного фактологического доказательства (Evidence).

## 7. Нормализация URL-адресов (URL Normalization)

Для исключения повторного скачивания одних и тех же страниц под разными ссылками, каждый входящий URL-адрес проходит обязательную детерминированную процедуру приведения к каноничному виду.

**Алгоритм нормализации учитывает и обрабатывает:**

- `scheme` — приведение протокола к нижнему регистру, явная обработка дефолтных портов (усечение :80, :443);
- `host` — перевод имени хоста в нижний регистр, очистка от дублирующих точек;
- `path` — раскрытие относительных элементов пути (/./, /../), удаление двойных слэшей;
- `query & fragment` — сортировка параметров запроса по алфавиту для исключения фактора разного порядка ключей;
- `tracking parameters` — принудительное вырезание известных маркетинговых и аналитических трекеров (utm_*, yclid, gclid, fbclid и т.д.);
- `trailing slash` — унификация конечного слэша в путях каталогов;
- `encoding` — декодирование и единообразное кодирование спецсимволов (Percent-Encoding в верхнем регистре).

## 8. Дедупликация данных

Программное ядро реализует обязательную жесткую трехуровневую систему дедупликации для исключения замусоривания контекста ИИ и предотвращения ложного завышения доверия к информации:

**Уровень URL:** Блокировка кандидатов, чьи каноничные адреса после прохождения шага нормализации полностью совпадают с уже обработанными или находящимися в очереди ссылками.

**Уровень постоянных идентификаторов:** Блокировка по совпадению метаданных научных и академических публикаций при точном совпадении ключей DOI, PMID или идентификатора arXiv.

**Уровень отпечатков содержимого (Content Fingerprint):** После скачивания текста страницы рассчитывается хэш-функция SHA256 от очищенного текстового тела. При совпадении хэша с документом, уже хранящимся в БД, новый документ отбрасывается. Практически идентичные документы или полные текстовые перепечатки юридически связываются в базе данных и не могут быть засчитаны системой как независимые источники информации.

## 9. Ранжирование кандидатов (Candidate Ranking)

Оценка релевантности (Relevance) и оценка качества источника (Source Quality) являются принципиально разными, независимыми друг от друга показателями и рассчитываются поисковым ядром раздельно.

**Базовые факторы формулы релевантности (Relevance Score):**

- Плотность и точность совпадения токенов поискового запроса с заголовком кандидата (Title Match).
- Частота вхождения ключевых терминов в текстовый сниппет (Snippet Match).
- Авторитетность конкретного домена относительно заданной темы исследования (Domain Match).
- Свежесть материала (фактор даты публикации Freshness).
- Соответствие расширения и структуры файла ожидаемому типу данных (Expected Material Type).

**Базовые факторы формулы качества источника (Source Quality Score):**

- Базовый тип площадки (Source Type).
- Происхождение и проверяемость данных (Provenance).
- Наличие автора или контролирующей редакционной коллегии (Editorial Control).
- Статус первоисточника или вторичного агрегатора (Primary/Secondary Status).
- Наличие верифицированных научных или государственных идентификаторов.

Итоговые веса и коэффициенты влияния каждого фактора выносятся в файлы конфигурации и должны быть настраиваемыми. Изменение настроек профиля качества не имеет права хаотично или непредсказуемо ломать работу базового алгоритма релевантности.

## 10. Политика оценки источников по предметным областям (Domain-Specific Policy)

Профиль качества источника (quality_profile) рассчитывается строго индивидуально, исходя из текущей тематики (domain) и режима исследования (research_mode). Единая универсальная шкала авторитетности для всей системы запрещена.

**Примеры распределения приоритетов качества:**

- **Тематика «Потребительские отзывы» (Consumer Review):** Тексты на форумах и специализированных сайтах отзывов от обычных пользователей (user-generated content) получают наивысший коэффициент ценности для анализа реального опыта эксплуатации. Академические научные статьи в этом режиме переводятся в статус материалов вторичной ценности.

- **Тематика «Медицинские исследования» (Medical Evidence):** Клинические испытания, мета-анализы и систематические обзоры в рецензируемых журналах получают максимальный балл качества. Маркетинговые описания и отзывы на форумах переводятся в категорию низшего уровня доказательности и не могут служить опорой для подтверждения научных фактов.

Система не разделяет источники на «плохие и хорошие вообще», а оценивает пригодность типа данных для ответа на конкретный класс вопросов.

Разделение оценки качества и достоверности (`A-10`): класс достоверности материала (ESTABLISHED…UNKNOWN) отделён от оценки качества источника (SourceQualityAssessment). Профиль качества влияет на приоритетность кандидатов при поиске и ранжировании, но не пересчитывает и не переопределяет классы доказательности утверждений.

## 11. Скачивание документов (Fetch)

Загрузка полных текстов документов из сети Интернет запускается строго после этапа ранжирования кандидатов и применяется только к ограниченному списку лидеров (Top-K).

**Программный модуль Fetch обязан поддерживать и контролировать следующие параметры:**

- `timeout` — жесткое ограничение времени ожидания ответа сервера;
- `concurrency limit` — лимит одновременно запущенных потоков скачивания;
- `retry policy` — правила повторных попыток с экспоненциальной задержкой (exponential backoff);
- `error classification` — строгая классификация причин сбоев (ошибки сети, таймауты, ответы 4xx/5xx);
- `cache integration` — обязательная проверка наличия документа в локальном кэше перед отправкой сетевого запроса;
- `content size limit` — жесткое отсечение скачивания файлов, чей размер превышает установленный лимит безопасности.

Сбой, зависание или долгий ответ от одного веб-сайта ни при каких условиях не должны приводить к блокировке или остановке скачивания материалов с других независимых доменов.

---

## 12. Ограничения сетевого доступа и политика вежливости

Система при осуществлении сетевой активности обязана строго соблюдать правила rate limiting, задержки между запросами к одному хосту и ограничения на количество одновременных подключений к одному домену (per-domain concurrency).

Перед скачиванием страница проверяется на предмет ограничений в `robots.txt` целевого хоста: запреты для используемого агента соблюдаются; обход `robots.txt` приравнивается к обходу систем защиты и запрещён. Проверка robots.txt кэшируется по хосту в пределах TTL кэша (§25).

Программное ядро системы принципиально не содержит функционала для обхода систем защиты сайтов: механизмов разгадывания CAPTCHA, систем взлома платных ограничений (paywall), средств подмены сессий для обхода систем контроля доступа или иных защитных экранов источника.

**При столкновении с блокировкой или ограничением доступа ядро системы обязано:**

- немедленно прекратить попытки обращения к ресурсу и зафиксировать структурированный код ошибки;
- временно исключить данный домен из списка обработки в рамках текущей сессии;
- автоматически инициировать подбор альтернативного кандидата из очереди результатов поиска;
- вывести развернутую диагностическую информацию о блокировке в лог-файл и системный поток для информирования пользователя.

## 13. Обработка документов (Document Processing)

Процесс обработки каждого успешно скачанного текстового массива выполняется по строгому детерминированному конвейеру:

1. **Fetch:** Получение сырого бинарного тела ответа (HTML, Plain Text).
2. **Extract:** Извлечение полезного текстового содержимого, отделение смысловых блоков от навигационных панелей, подвалов сайтов, рекламных блоков и сайдбаров с помощью легковесного экстрактора.
3. **Clean:** Очистка от остаточных тегов разметки, скриптов, служебных стилей и нормализация кодировки текста в формат UTF-8.
4. **Normalize:** Приведение структуры текста (абзацы, списки) к единому системному виду.
5. **Hash:** Расчет контрольного цифрового отпечатка content_hash для проверки уникальности.
6. **Chunk:** Детерминированная нарезка монолитного текста на изолированные чанки с фиксацией overlap-границ и присвоением overlap_group_id.
7. **Index:** Передача нарезанных фрагментов в поисковый индекс провайдера RetrievalProvider.

## 14. Локальный текстовый поиск (BM25)

Алгоритм BM25 является фундаментальным базовым механизмом локального поиска системы на этапе MVP и функционирует строго за счет вычислительных ресурсов центрального процессора (CPU-Only).

Поиск по ключевым словам выполняется непосредственно по базе данных нарезанных фрагментов документов (DocumentChunk).

**Контракт выполнения поиска:**

```
Текстовый запрос (Query)
        ↓
Модуль локального поиска BM25
        ↓ [Фильтрация по study_id, document_id, типу материала, флагу local/external]
Список наиболее релевантных фрагментов (Top Chunks)
        ↓
Формирование пула кандидатов в доказательства (Evidence Candidates)
```

Алгоритм локального поиска обязан корректно поддерживать обработку текстов на русском языке (включая стемминг/лемматизацию для учета морфологии), безошибочно распознавать специфичные технические термины, аббревиатуры и коды. Работа алгоритма должна оставаться стабильной и детерминированной даже в условиях передачи пустых или некорректных поисковых строк.

Хранимый BM25-индекс (A-24): поисковый индекс строится на SQLite FTS5, персистентном в Project DB; в индексируемую колонку помещается лемматизированный токен-поток чанков (`A-25`), что позволяет использовать штатный tokenizer FTS5 без кастомного C-tokenizer (из Python недоступного). In-memory BM25 (rank_bm25) — запасной вариант только для малых объёмов. **Пересборка индекса при каждом запуске приложения недопустима**; жизненный цикл индекса — §14a.

### 14.1. Морфологическая обработка русского текста

Для обеспечения корректного поиска по русскому языку система обязана реализовать прикладной стемминг-пайплайн, не полагаясь исключительно на встроенные механизмы токенизации СУБД.

**Архитектура пайплайна:**

**1. Индексация:**

- Оригинальный текст сохраняется в DocumentChunk.text без изменений.
- Параллельно создаётся поисковый индекс со стеммированными токенами.
- Маппинг между стеммированными токенами и chunk_id обеспечивает связь с реляционной моделью.
- Стеммер применяется детерминированно при каждом добавлении чанка.

**2. Поиск:**

- Поисковый запрос проходит через тот же стеммер, что и при индексации.
- Поиск выполняется по стеммированным токенам.
- Результаты связываются с DocumentChunk через chunk_id.

**3. Требования к стеммеру:**

- Единый алгоритм для индексации и поиска.
- Поддержка русского языка.
- Детерминированность (одинаковый вход → одинаковый выход).
- Обработка стоп-слов (исключение из индекса).
- Версионирование (см. раздел 14a: normalizer_version).

Конкретный алгоритм стемминга/лемматизации является реализационным решением и выносится в конфигурацию. ТЗ фиксирует требование детерминированности, воспроизводимости и обязательной обработки русской морфологии.

Обязательность морфологии (A-13): полная морфологическая обработка русского языка является **обязательным требованием MVP**. Упрощённый BasicNormalizer допускается только как явно диагностируемый degraded fallback (с фиксацией в логах и диагностике); работа в режиме BasicNormalizer «по умолчанию» или «если включена морфология» не допускается. Recall ≥ 0.9 для нормативных запросов является критерием приёмки (раздел 7 ТЗ).

Словарная лемматизация — реализация A-13 (A-25): нормативной реализацией полной морфологической обработки русского языка (A-13) является **словарный лемматизатор** (pymorphy3 или совместимый); стемминг применяется только как явно логируемая деградация (A-13/D-1). Кэш лемм обязателен. Словарь анализатора входит в состав portable-сборки (EPIC-11). Нормализованный токен-поток используется поисковым индексом (`A-24`).

### 14a. Жизненный цикл BM25-индекса

Поисковый индекс обязан поддерживать воспроизводимость результатов и корректное управление жизненным циклом.

**Версионирование индекса:**

Каждый экземпляр индекса обязан хранить метаданные версии:

- `normalizer_version` — версия алгоритма токенизации/стемминга
- `index_version` — порядковый номер перестроения
- `language` — целевой язык обработки
- `stopword_version` — версия списка стоп-слов

**Операции жизненного цикла:**

1. `document added → index(chunks)` — добавление чанков документа в индекс
2. `document changed → reindex(chunks)` — удаление старых и добавление новых чанков
3. `document deleted → delete(document_id)` — удаление всех чанков документа из индекса
4. `tokenizer changed → rebuild_all()` — полное перестроение индекса с новым токенизатором
5. `study deleted → cleanup(study_id)` — удаление изолированных данных индекса

**Правила:**

- Результаты поиска обязаны быть воспроизводимыми при одинаковой версии индекса.
- Смена токенизатора или версии стемминга требует обязательного перестроения индекса.
- Перестроение индекса является долгой операцией и выполняется через Job-механизм (см. раздел 28).
- Rebuild выполняется через **staging generation** (`A-21`): новый индекс строится параллельно, затем выполняется атомарное переключение активной версии; читатели не видят промежуточных состояний.
- Изменение `chunk_size` и параметров нарезки не перезаписывает существующие чанки — оно создаёт только новые версии разбиения (A-07); Evidence, ссылающиеся на старые chunk_id, остаются валидными.

## 15. Извлечение доказательств и контекстный коридор (Evidence Retrieval)

Локальная ИИ-модель лишена возможности читать документ целиком. Она получает для анализа исключительно точечные вырезки — доказательства (Evidence), извлеченные поисковым ядром из базы чанков.

**Правило контекстного коридора (Chunk Context Window):**

При передаче релевантного чанка, найденного алгоритмом BM25, в ИИ-модель для извлечения доказательств, программное ядро обязано автоматически расширить контекст за счет включения соседних фрагментов текста.

**Конфигурационный параметр по умолчанию:**

```
chunk_context_window = 1
```

Это означает, что в ИИ-модель передается монолитный блок текста, состоящий из: `[ Предыдущий соседний чанк (-1) ] + [ Целевой чанк поиска (Target) ] + [ Следующий соседний чанк (+1) ]`.

Данное расширение контекста является строго обязательным для сохранения семантической непрерывности повествования, удержания логики повествования автора и своевременного обнаружения локальных уточнений, опровержений или скрытых условий внутри текста. Математический поисковый скор релевантности при этом рассчитывается исключительно по целевому (Target) чанку. Каждое извлеченное доказательство Evidence обязано сохранить в своей реляционной структуре как жесткий ID целевого чанка, так и перечень ID всех контекстных чанков, использованных в коридоре.

Порядок дедупликации при извлечении (`A-05`): при создании Evidence поиск существующей цитаты выполняется **по позиции** (Study + document identity + полуоткрытый интервал `[char_start, char_end)` + точный текст) **до** проверки `evidence_hash`; hash является совместимым контрактом, а не единственным критерием.

### 15.1. Устранение дублирования при сборке контекстного коридора

Перекрытие чанков (50–100 токенов) означает, что соседние чанки частично дублируют текст. При сборке контекстного блока [-1] + [target] + [+1] система обязана устранить дублирование.

**Алгоритм склейки (A-06 — по интервалам исходного документа):**

1. Склейка выполняется по интервалам `[char_start, char_end)` в исходном `Document.content`, а не по флагу `is_overlap`: сосед определяются по смежности интервалов (± 1 позиция).
2. Если соседние чанки пересекаются по интервалам:
   - Найти точку перекрытия (повторяющийся текст между чанками).
   - Удалить дублирующуюся часть при конкатенации.
3. Если соседи не пересекаются — конкатенация с маркером разрыва.
4. Край документа (отсутствие соседа -1 или +1) **не является ошибкой** — коридор собирается из доступных чанков.

`overlap_group_id` и `is_overlap` являются вспомогательными признаками; уникальная неперекрывающаяся часть overlap-чанка не теряется из анализа (A-06).

**Требования:**

- Алгоритм удаления дублей должен быть детерминированным и воспроизводимым.
- Фактический размер собранного контекста в токенах логируется для аудита.
- Удаление дублей не должно нарушать смысловую целостность текста.

## 16. Специфика режима агрегации мнений (Aggregation / Review Mode)

При работе в режиме сбора отзывов поисковое ядро перестраивает внутренние конвейеры на массовое извлечение и последующий расчет статистических параметров:

```
Кандидаты отзывов (Review Candidates)
        ↓
Извлечение текстов индивидуальных отзывов (Review Extraction)
        ↓
Фиксация цитат-доказательств (Evidence)
        ↓
Выделение структурированного факта (Observation: Объект + Характеристика + Тональность)
        ↓
Дедупликация на основе уникальности авторов / текста
        ↓
Математическая агрегация данных в Core
        ↓
Формирование результирующего вывода (Claim)
```

Для обеспечения проверяемости статистики поисковое ядро собирает и рассчитывает следующий минимальный набор метрик (при условии их физического наличия в источнике):

- общее количество обработанных текстовых отзывов;
- количество уникальных идентифицированных авторов или независимых площадок;
- частота упоминания конкретных свойств объекта (Attribute);
- соотношение и распределение положительных и отрицательных паттернов;
- выделенные изолированные аспекты эксплуатации;
- устойчивые повторяющиеся проблемы или дефекты;
- выявление аномальных всплесков или скоординированных групп отзывов;
- маркеры потенциально стимулированных или накрученных мнений.

Программное ядро строго соблюдает правило: один изолированный отзыв на сайте никогда не может быть приравнен к общему статистическому факту. Система обязана четко разграничивать в структурах данных количество единичных веб-публикаций, количество уникальных авторов текста, общую частоту текстовых упоминаний и количество независимых корневых доменов.

### 16a. ReviewExtractor (доменный адаптер для режима агрегации)

Для режима агрегации мнений (AGGREGATION / REVIEW) система предоставляет специализированный доменный адаптер, который преобразует разнообразные форматы страниц с отзывами в каноническую структурированную модель.

**Важное архитектурное разделение:**

- Общий Search Core НЕ содержит знаний о специфических полях отзывов (рейтинг, автор, дата отзыва).
- ReviewExtractor является ДОМЕННЫМ АДАПТЕРОМ, подключаемым через интерфейс, аналогичный SourceAdapter.
- ReviewExtractor является опциональным компонентом и не блокирует работу общего конвейера Evidence Research.

**Каноническая модель отзыва:**

```
CanonicalReview:
├── reviewer_id (TEXT) -- Идентификатор автора
├── reviewer_name (TEXT) -- Имя автора
├── rating (REAL) -- Числовая оценка
├── review_date (TIMESTAMP) -- Дата отзыва
├── review_text (TEXT, NOT NULL) -- Текст отзыва
├── platform (TEXT) -- Площадка/источник
└── is_verified_purchase (BOOLEAN) -- Маркер верифицированной покупки
```

**Применение:**

- Для режима AGGREGATION: ReviewExtractor активируется и передаёт канонические отзывы в конвейер извлечения наблюдений.
- Для режима EVIDENCE: ReviewExtractor не требуется, используется стандартный конвейер извлечения доказательств.
- Для режима COMPARISON: ReviewExtractor может активироваться для каждого сравниваемого объекта.

Подключаемые площадки (расширяемый список): маркетплейсы, форумы, сайты отзывов, Reddit, сайты производителей.

**Политика верификации авторов и статистики (Q-09):**

1. **Platform-scoped identity:** автор идентифицируется в пределах площадки (`reviewer_id` + `platform`); объединение одного человека между площадками — только по явному user-binding (e-mail/аккаунт); без него это разные авторы.
2. **Знаменатель** всех процентных показателей — количество верифицированных авторов (не отзывов и не URL). Авторы со статусом UNKNOWN/неверифицированные в знаменатель не входят и минимум авторов профиля AGGREGATION (`01` §7, Q-03) не закрывают.
3. **Минимальная выборка** для итоговых статистических выводов (baseline, конфигурируемая): не менее 5 верифицированных авторов и не менее 10 отзывов; ниже вывод помечается `INSUFFICIENT_SAMPLE`, а не формулируется как статистический факт.
4. **Анонимные отзывы** учитываются отдельно и не смешиваются с верифицированными; стимулированные отзывы при наличии маркера подлежат обязательной маркировке.
5. **Anomaly policy:** аномальный всплеск — статистический сигнал, но **не** доказательство накрутки; маркировка накрутки допускается только при верифицированном признаке (совпадение source, времени или содержимого сверх порога).

## 17. Специфика режима поиска доказательств (Evidence Research Mode)

При переключении исследования в режим поиска научных или технических доказательств, ядро Search Core активирует специализированные изолированные потоки поисковых задач по следующим независимым направлениям:

- поиск прямых подтверждений выдвинутой гипотезы;
- целевой поиск опровергающих фактов и альтернативных точек зрения;
- выделение явных ограничений, рамок и условий применимости метода;
- обнаружение альтернативных технологических или научных подходов;
- приоритетный сбор первичных экспериментальных исследований;
- сбор вторичных обзорных и систематических материалов;
- фильтрация и приоритетный вывод наиболее свежих публикаций;
- выделение экспериментальных и малоизученных направлений.

При обработке материалов из академических баз данных поисковое ядро берет на себя обязательство по полному извлечению, валидации и сохранению в реляционных полях БД постоянных научных идентификаторов DOI, PMID, arXiv ID и иных специализированных метаданных публикаций.

## 18. Контроль и поиск первоисточников (Primary Source Search)

В случае если в процессе анализа извлеченное существенное утверждение или цитата были обнаружены во вторичном материале (новостная статья, обзорный агрегатор, пресс-релиз), поисковое ядро обязано автоматически сформировать и запустить внутреннюю целевую задачу по поиску оригинального первоисточника публикации (Primary Source).

Запуск через gap (`A-15`): поиск первоисточника начинается с сохранённого ResearchGap (reason = PRIMARY_SOURCE_PENDING либо аналогичный классификатор причины) — Core создаёт SearchTask, связанный с gap через `gap_id`. LLM **не создаёт persistent SearchTask** самостоятельно: она лишь предлагает SearchTaskDraft, который Core валидирует, сохраняет и исполняет.

**По результатам выполнения этой задачи система фиксирует один из трех статусов верификации происхождения:**

- **PRIMARY_FOUND** — оригинальный первоисточник успешно обнаружен, скачан, связан реляционной ссылкой и добавлен в базу исследования.
- **PRIMARY_UNAVAILABLE** — первоисточник однозначно идентифицирован (например, найдено название научного доклада), но физический доступ к нему заблокирован, отсутствует в открытой сети или защищен paywall.
- **PRIMARY_NOT_IDENTIFIED** — вторичный текст содержит абстрактную ссылку на автора или событие без возможности точной идентификации конкретного документа-источника.

Данный статус происхождения в обязательном порядке передается на уровень синтеза отчета и напрямую влияет на итоговый показатель достоверности утверждения.

## 19. Поиск логических и числовых противоречий (Contradiction Search)

Процедура обнаружения конфликтов в собранных данных реализуется как обособленная, независимая поисковая задача ядра Search Core.

Для оптимизации вычислительных ресурсов и исключения перегрузки локального ИИ, процесс разделен на два этапа:

**Детерминированный этап (Core):** Программа сканирует базу данных чанков текущего исследования, используя поле `numeric_signatures` (числовые подписи), выявляя явные математические расхождения (например, разная цена одного товара на разных сайтах, разные числовые показатели скорости или дозировок в соседних документах).

**Семантический этап (LLM):** Только над узким списком предварительно отобранных программой кандидатов-противоречий локальная ИИ-модель выполняет смысловое сравнение для подтверждения логического конфликта.

Система поддерживает выявление и классификацию следующих типовых конфликтов: явные числовые расхождения, временные несоответствия (устаревшие данные против свежих), прямые фактологические противоречия, методологические конфликты в исследованиях, несовпадающие финальные рекомендации, расхождения в технических параметрах и радикальные отличия в пользовательском опыте эксплуатации.

## 20. Защита от дублирования поисковых запросов и Query Fingerprint

ИИ-модель полностью лишена права отправлять произвольные текстовые строки напрямую в сетевые интерфейсы. Любой предложенный запрос проходит обязательную стадию валидации и расчета цифрового отпечатка в ядре Core.

**Формула расчета Query Fingerprint:**

При получении предложения о поиске, ядро генерирует уникальный хэш по следующей жесткой структуре параметров:

```
query_fingerprint = SHA256(
    normalized_query_text +
    source_scope +
    task_purpose +
    applied_filters +
    exclusion_terms +
    time_range_constraint +
    geography_constraint +
    expected_material_type
)
```

Перед запуском сетевой задачи программа сверяет полученный хэш с глобальной историей запросов текущего исследования в БД. По результатам проверки ядро имеет право заблокировать выполнение задачи, выставив один из следующих системных статусов отказа:

- **QUERY_ALREADY_EXECUTED** — данный точный запрос уже выполнялся ранее в этой сессии.
- **QUERY_TOO_SIMILAR** — запрос имеет критическую степень сходства и пересечения значимых токенов с уже выполненными задачами, информационный прирост от него признан нулевым.
- **QUERY_COVERAGE_ALREADY_EXISTS** — целевой семантический узел и информационная потребность, ради которой ИИ сгенерировал запрос, уже полностью закрыты имеющимися в базе документами.
- **QUERY_REJECTED** — запрос отклонен ядром из-за нарушения жестких системных ограничений или выхода за рамки бюджета исследования.

При отклонении запроса ядро Core возвращает на уровень ИИ детальную структурированную причину отказа и выдает детерминированное разрешенное направление для модификации поисковой строки.

### 20.1. Многофакторная защита от дублирования запросов

Помимо точного совпадения query_fingerprint (SHA256), система обязана реализовывать многофакторную проверку сходства запросов.

**Структура проверки:**

**1. Exact Match:** Полное совпадение SHA256 fingerprint → статус `QUERY_ALREADY_EXECUTED`.

**2. Similarity Match:** Оценка сходства с уже выполненными запросами.

- Интерфейс: `QuerySimilarityProvider.similarity(query_a, query_b) -> float [0.0, 1.0]`
- Конкретный алгоритм (MinHash, Jaccard, SimHash или иной) определяется конфигурацией и НЕ фиксируется в ТЗ как единственный.
- Порог сходства задаётся в `ResearchConfig.threshold_settings.query_similarity_threshold`.
- При превышении порога → статус `QUERY_TOO_SIMILAR`.

**3. Coverage Match:** Проверка, не покрыта ли уже информационная потребность запроса имеющимися документами.

- Оценка через анализ покрытия целей и атрибутов.
- При полном покрытии → статус `QUERY_COVERAGE_ALREADY_EXISTS`.

**Факторы, учитываемые при оценке сходства:**

- Нормализованный текст запроса и значимые токены (стоп-слова исключаются)
- Область источников (source_scope)
- Цель подзадачи (task_purpose)
- Применённые фильтры и исключения
- Временной диапазон и география
- Ожидаемый тип материала

Конкретный алгоритм оценки сходства является реализационным решением и выносится в конфигурацию. ТЗ фиксирует контракт интерфейса и требование многофакторности, но не привязывает к единственному алгоритму.

Область владения (`A-04`): вся защита от дублирования действует в пределах текущего Study/Project. Повтор запроса в другом Study не блокируется по чужой истории и не раскрывает чужие данные — история запросов, fingerprint-индексы и сходство считаются в рамках области владения (см. раздел 3 ТЗ, §6/§23).

## 21. Адаптивный поиск и логика итераций

Процесс сбора информации функционирует строго пошагово. Запуск каждой следующей поисковой итерации признается легитимным исключительно в том случае, если ядро Core подтверждает наличие весомого информационного повода.

**Допустимые системные поводы для продолжения адаптивного поиска:**

- необходимость закрытия критического открытого пробела в знаниях (Research Gap);
- целевая проверка и сбор данных для разрешения обнаруженного логического или числового конфликта;
- необходимость повышения коэффициента независимости источников при обнаружении скрытого копирования информации;
- требование по смене класса источников (например, переход от чтения обзоров к поиску первичных документов);
- необходимость расширения временного или географического охвата данных при явном указании в целях исследования.

Генерация ИИ-моделью новой текстовой строки запроса сама по себе, в отрыве от зафиксированных в БД операционных причин, категорически не является основанием для инициации очередного поискового цикла.

## 22. Условия детерминированной остановки поиска (Stop Conditions)

Поисковая активность по конкретному направлению немедленно и принудительно прекращается программным ядром при наступлении любого из следующих условий:

**Достаточное покрытие (Sufficient Coverage):** Все цели, характеристики и информационные потребности исследования полностью закрыты верифицированными данными.

**Отсутствие информационного прироста (No Information Gain):** Последние поисковые циклы приносят в базу исключительно дубликаты текстов, ранее известные ссылки или материалы с околонулевым скором релевантности. Информационный прирост упал ниже установленного порога (5%).

**Исчерпание лимитов бюджета:** Достигнута жесткая верхняя граница любого из измеряемых параметров многомерного бюджета.

**Тотальная недоступность ресурсов:** Все подобранные поисковые кандидаты последовательно выдают сетевые ошибки, недоступны или заблокированы системами защиты.

**Команда пользователя:** Получен явный ручной сигнал на остановку исследования со стороны интерфейса.

**Параметры жестких системных ограничений бюджета:**

- `step_budget` — лимит на максимальное количество шагов/итераций адаптивного цикла;
- `network_budget` — ограничение на общее число отправленных запросов к поисковым системам;
- `fetch_budget` — лимит на максимальное количество скачанных полных веб-страниц;
- `tool_call_budget` — жесткая верхняя граница на суммарное количество вызовов ИИ-моделью любых MCP-инструментов;
- `llm_call_budget` / `llm_token_budget` / `time_budget` — полная тарификация по 7 dimension определяется BUDGET CONTRACT v1.0 (раздел 5 ТЗ, §6a).

Бюджетная модель исполнения (`Q-04`): все billable операции проходят `reserve → commit/release`. Retry network потребляет `network`; cache hit сеть не потребляет; preview, cancel, read-only diagnostics и recovery reads не требуют research budget. Zero available → операция не начинается (BUDGET_EXHAUSTED → FREEZE_BUDGET_EXHAUSTED; новые SearchTask → REJECTED_BUDGET).

Strategy profiles (Q-03): пороги остановки задаются strategy profile в `ResearchConfig.threshold_settings`. Базовый профиль EVIDENCE: question_coverage=1.0, attribute_coverage=1.0, min_independent_sources=2, min_verified_evidence=3, contradiction_count=0, information_gain_threshold=0.05; приоритет STOP_BUDGET > STOP_NO_AVAILABLE_SOURCES > STOP_NO_INFORMATION_GAIN > STOP_SUFFICIENT > CONTINUE (полный контракт — раздел 1 ТЗ, §7). Для **AGGREGATION действует отдельный профиль**: обязательные attributes должны быть покрыты полностью; минимум уникальных верифицированных авторов задаётся профилем; анонимные/неверифицированные авторы не закрывают этот минимум. Каждая проверка пишет SufficiencyEvaluation + SufficiencyMetric + SufficiencyRuleHit.

Границы ответственности (A-16): Search Core предоставляет чистые типизированные primitives (coverage, sufficiency, budget); Research Engine вызывает их и не реализует второй evaluator. G-04 проверяется на fixtures без реальной LLM, G-05 — через FakeLLM.

## 23. Валидация объектов Research Gap

Объект пробела исследования (ResearchGap) генерируется ИИ-моделью при анализе текущей полноты данных, но приобретает статус законного операционного документа только после прохождения структуры проверок в ядре Core.

Каждый объект пробела обязан содержать строгое реляционное наполнение: точный довыясняющий вопрос, развернутое обоснование причины появления пробела, перечень недостающих элементов доказательной базы, рекомендованный вариант строки запроса, приоритет важности и статус жизненного цикла.

ИИ-модель полностью лишена технической возможности инициировать сетевую активность в обход создания и последующей валидации объекта ResearchGap через структуры ядра Search Core.

## 24. Особенности работы локального режима EXPAND

При активации пользователем режима расширения накопленного архива (EXPAND), конвейер ядра Search Core принудительно выстраивает жесткую последовательность действий:

**Локальный этап:** Система выполняет сканирование, индексацию и глубокий текстовый поиск с помощью локального движка BM25 по всем материалам прошлых исследований и документов, добавленных в выбранный проект.

**Аналитический этап:** ИИ-модель проводит детальный анализ полноты поднятых из базы данных цитат и выявляет точечные, незакрытые пробелы в знаниях.

**Сетевой этап:** Программное ядро разрешает активацию внешних сетевых адаптеров и отправку поисковых запросов в сеть Интернет строго и исключительно для закрытия конкретных выявленных пробелов, категорически блокируя любые попытки повторного сбора или скачивания информации, которая уже физически присутствует в локальном репозитории системы.

## 25. Модуль сетевого кэширования (Cache)

Любой успешный сетевой HTTP-ответ, полученный адаптерами из внешних источников, подлежит обязательному детерминированному сохранению в системной таблице кэша.

Ключ уникальности кэша формируется как жесткая комбинация: каноничный URL страницы + хэш-префикс параметров сетевого запроса.

**Система поддерживает и протоколирует следующие состояния модуля кэширования:**

- **CACHE_HIT** — документ обнаружен в кэше, имеет валидный срок жизни, сетевой запрос блокируется, данные мгновенно отдаются из локальной БД.
- **CACHE_MISS** — документ отсутствует в хранилище, ядро разрешает физическое выполнение сетевого запроса.
- **CACHE_EXPIRED** — документ найден, но срок его хранения превысил установленный лимит, система инициирует фоновое или прямое обновление данных.
- **FORCED_REFRESH** — принудительное игнорирование кэша с обязательным обновлением данных. Инициируется двумя каналами: (а) прямая команда пользователя из GUI с перезаписью устаревших данных в базе; (б) MCP-вызов `read_url_content(refresh=true)` (Q-08, ADR-002). При совпадении нового `content_hash` с существующим новая версия Document **не создаётся** (согласно правилу «При совпадении content_hash документ не сохраняется повторно», `03` §9); обновляется только кэш-запись, инструмент возвращает `CONTENT_UNCHANGED`.

Бюджетная аспект кэша (`Q-04`): `CACHE_HIT` не потребляет `network` и `fetch` dimensions; сетевой запрос при `CACHE_MISS`/`CACHE_EXPIRED` потребляет `network` согласно тарификации BUDGET CONTRACT v1.0.

Точные параметры времени жизни кэшированных записей (TTL) индивидуально настраиваются в конфигурационных файлах для каждого подключенного источника или домена.

## 26. Системные метрики и аудит

Для обеспечения возможности проведения глубокого технического аудита, оптимизации алгоритмов и контроля за расходованием ресурсов компьютера, программное ядро Search Core в автоматическом режиме осуществляет непрерывный сбор и реляционную запись следующих операционных показателей:

- суммарное количество сгенерированных и отправленных поисковых запросов;
- количество успешно завершенных сетевых вызовов;
- количество зафиксированных сетевых и программных ошибок;
- процентное соотношение попаданий и промахов в модуле кэширования (Cache hit/miss ratio);
- общее число обнаруженных поисковых кандидатов;
- количество уникальных отфильтрованных корневых доменов;
- количество заблокированных дубликатов ссылок и текстов;
- суммарное число успешно скачанных и очищенных полных документов;
- количество созданных детерминированных чанков;
- объем сформированной доказательной базы (Evidence Store);
- количество извлеченных атомарных наблюдений (Observations);
- число сформулированных итоговых утверждений (Claims);
- количество выявленных числовых и логических конфликтов данных;
- число созданных и закрытых пробелов исследования (Research Gaps);
- количество жестко отклоненных ядром дублирующих запросов ИИ;
- точное время, затраченное на выполнение каждого этапа конвейера обработки данных.

## 27. Фильтрация контекста на входе ИИ-модели

Программное ядро выполняет роль жесткого шлюза безопасности конвейера данных. Передача на уровень локальной ИИ-модели любых элементов сырого HTML-кода, полных страниц сайтов, избыточных списков заблокированных дубликатов, детальных стеков системных ошибок или неструктурированного технического мусора категорически запрещена.

На вход ИИ подаются исключительно высококачественные, предварительно обработанные текстовые выжимки, релевантные цитаты с жестко заданным коридором контекста, актуальные операционные статусы выполнения задач, наполнение рабочей памяти и строго валидированные таблицы пробелов данных.

## 28. Job-механизм для долгих операций

Для операций, которые гарантированно не укладываются в стандартный синхронный таймаут MCP-инструмента, система предоставляет механизм фоновых задач (Jobs).

**Важное ограничение:** Job-механизм является ДОПОЛНИТЕЛЬНЫМ слоем и НЕ заменяет атомарные синхронные MCP-инструменты. Стандартные операции (search_web, read_url_content, search_within_document и т.д.) остаются синхронными с жёстким таймаутом.

**Операции, выполняемые через Job-механизм:**

- Массовая индексация большого набора документов
- Перестроение BM25-индекса при смене токенизатора
- Импорт крупного набора локальных файлов
- Длительная пакетная обработка

**Структура Job:**

```
Job:
├── job_id (TEXT, PRIMARY KEY, UUID)
├── job_type (TEXT, NOT NULL) -- INDEX_REBUILD, BULK_IMPORT, BULK_PROCESSING
├── status (TEXT, NOT NULL) -- QUEUED, RUNNING, COMPLETED, FAILED, CANCELLED
├── progress (REAL) -- Прогресс выполнения от 0.0 до 1.0
├── operation_id (TEXT) -- Ссылка на операцию, инициировавшую Job
├── created_at (TIMESTAMP)
├── started_at (TIMESTAMP)
├── completed_at (TIMESTAMP)
└── error (TEXT) -- Описание ошибки при статусе FAILED
```

**Дополнительные MCP-инструменты для управления Job:**

- `get_job_status(job_id)` — получение текущего статуса и прогресса
- `cancel_job(job_id)` — запрос на кооперативную отмену (через threading.Event, см. Раздел 06)

**Правила:**

1. Job не блокирует транспортный слой MCP.
2. Job поддерживает кооперативную отмену через механизм, описанный в Разделе 06.
3. Результат Job фиксируется в SQLite атомарно по завершении.
4. При падении системы незавершённые Job переводятся в статус FAILED с возможностью ручного перезапуска.
5. Кооперативная отмена (A-14): `cancel_job` сначала устанавливает cancellation request; фактический переход в `CANCELLED` выполняет runner после **безопасной точки** и commit checkpoint. Unsafe thread kill запрещён. Поздние результаты отменённой операции отбрасываются и не записываются в базу. Переход `QUEUED → CANCELLED` по `CANCEL_CONFIRMED` от Job runner входит в нормативную FSM (STATE MACHINE SPECIFICATION v1.2, §6).
