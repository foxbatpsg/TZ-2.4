# НАЦИОНАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ) v2.4

## Раздел 3. Модель данных и хранение

**Статус:** Утвержденный архитектурный контракт (Финальная монолитная редакция)
**Назначение:** Определение полной структуры реляционных данных, схемы таблиц, правил индексации, изоляции и обеспечения целостности хранилища.

## 1. Общие правила

Основное хранилище системы — база данных SQLite, функционирующая в режиме WAL (Write-Ahead Logging) для обеспечения параллельного бесконфликтного чтения и надежной записи.

Все операции модификации, вставки и удаления данных выполняются исключительно через изолированный программный компонент — единый DB-write layer.

Сущность **Study** (Исследование) является логически изолированным контекстом исследования. Сущность **Project** (Проект) объединяет под собой несколько Studies.

Сущность Document является глобальным объектом в рамках проекта и может одновременно использоваться несколькими Studies без физического дублирования текста на диске.

### 1a. Идентификация операций и идемпотентность

Система обязана различать три типа идентификаторов для обеспечения идемпотентности операций и безопасных повторных попыток:

1. **operation_id** — уникальный идентификатор конкретной операции MCP или внутреннего действия ядра. Генерируется при создании операции. Используется для логирования, трассировки и связи с ошибкой.

2. **request_id** — уникальный идентификатор конкретного внешнего сетевого запроса (один fetch = один request_id). Используется для кэширования, дедупликации сетевых вызовов и rate limiting.

3. **idempotency_key** — детерминированный ключ, гарантирующий, что повторное выполнение операции не создаст дублирующихся сущностей. Формируется из семантического содержания операции (например, SHA256 от параметров запроса для SearchTask, SHA256 от content для Document).

**Правила применения:**

- Каждая запись в таблицах, создаваемая в результате операции, обязана ссылаться на `operation_id`, который её создал.
- Повторный вызов операции с тем же `idempotency_key` не создаёт новую сущность, а возвращает ссылку на существующую.
- При восстановлении после сбоя (`SESSION_RESUMING`) ядро проверяет `idempotency_key` для предотвращения дублирования.

**Критическое правило реляционной целостности:** Использование JSON-массивов, текстовых списков с разделителями или сериализованных строк в качестве источника истины для связей между сущностями (например, Claim ↔ Evidence, Evidence ↔ Chunk и т.д.) категорически запрещено. Все связи реализуются исключительно через классические нормализованные связующие таблицы (M2M/O2M) со строгим контролем внешних ключей (FOREIGN KEY). JSON допускается к использованию только в полях с наименованием `metadata` или `config` для хранения неструктурированных справочных данных, не участвующих в фильтрации и JOIN-операциях.

## 11. DocumentChunk

```
DocumentChunk
├── chunk_id (TEXT, PRIMARY KEY, UUID) -- Стабильный, воспроизводимый хэш от текста и позиции
├── document_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Document ON DELETE CASCADE)
├── text (TEXT, NOT NULL)
├── token_estimate (INTEGER, NOT NULL)
├── char_start (INTEGER, NOT NULL)
├── char_end (INTEGER, NOT NULL)
├── heading_path (TEXT) -- Иерархия заголовков Markdown (например, "H1 > H2")
├── page_number (INTEGER)
├── position_index (INTEGER, NOT NULL)
├── overlap_group_id (TEXT, NOT NULL) -- UUID группы пересекающихся чанков
├── is_overlap (BOOLEAN, DEFAULT FALSE) -- Флаг исключения из агрегации при пересечении
├── numeric_signatures (TEXT) -- Извлеченные числа для быстрого поиска противоречий
└── metadata (TEXT, JSON)
```

Поле `numeric_signatures` хранит нормализованные числовые данные в формате JSON-массива для детерминированного выявления противоречий без участия LLM.

**Структура каждого элемента массива:**

```json
{
    "value": 1500.0,
    "unit": "RUB",
    "raw": "1500 рублей",
    "type": "PRICE"
}
```

Допустимые типы (`type`): `PRICE`, `PERCENT`, `DATE`, `DOSAGE`, `SPEED`, `COUNT`, `OTHER`.

**Правила сравнения противоречий:**

- Сравниваются только записи с одинаковыми `type` и `unit`.
- Сравнение выполняется детерминированно на уровне ядра без вызова LLM.
- LLM привлекается только для семантического подтверждения конфликта на втором этапе (см. Раздел 04, секция 19).

## 12. Chunking

Система на уровне MVP реализует следующий контракт детерминированного разбиения документов:

**Тип разбиения:** Детерминированный, структурный, опирающийся на логические границы текста (абзацы, списки, элементы разметки Markdown).

**Диапазон размера чанка:** Настраиваемый начальный диапазон в 400–700 токенов.

**Перекрытие (Overlap):** Фиксированное перекрытие в диапазоне 50–100 токенов с обязательным присвоением одинакового `overlap_group_id` для всех пересекающихся фрагментов.

**Сохранение контекста:** При нарезке чанка алгоритм обязан наследовать и записывать в поле `heading_path` текущую цепочку заголовков, а также сохранять целостность списков. Текстовые таблицы преобразуются парсером в читаемый построчный вид.

Сложные семантические алгоритмы чанкинга (semantic chunking) переносятся в категорию Post-MVP задач. Параметры нарезки должны быть полностью вынесены в файлы конфигурации. Крупные форматы документов (PDF/EPUB) архитектурно поддерживаются базовой схемой, но глубокие специализированные парсеры под них могут дорабатываться на этапах после MVP.

### Правило защиты статистики от overlap

При агрегировании наблюдений (Observations) и подсчёте статистических метрик система обязана учитывать флаг `is_overlap` в таблице `DocumentChunk`.

1. Чанки с `is_overlap = TRUE` исключаются из подсчёта уникальных наблюдений, если их текст уже учтён через основной чанк той же overlap-группы.
2. При извлечении Evidence из чанка с `is_overlap = TRUE` система обязана проверить, не было ли аналогичное Evidence уже извлечено из другого чанка той же overlap-группы (через `evidence_hash`).
3. Поле `overlap_group_id` используется для группировки пересекающихся чанков и предотвращения многократного учёта одного и того же текста в статистике.

## 13. Evidence

Сущность цитаты-доказательства. Контекст извлечения цитаты расширяется за пределы одного целевого чанка.

```
Evidence
├── evidence_id (TEXT, PRIMARY KEY, UUID)
├── study_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Study)
├── document_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Document)
├── target_chunk_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES DocumentChunk) -- Основной чанк
├── text (TEXT, NOT NULL) -- Точный текст цитаты из первоисточника
├── evidence_hash (TEXT, NOT NULL) -- SHA256 от (text + target_chunk_id + document_id), обеспечивает уникальность
├── location (TEXT) -- Строковое или числовое позиционирование внутри документа
├── extraction_time (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
├── task_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES SearchTask)
├── operation_id (TEXT) -- UUID операции, создавшей доказательство
├── evidence_type (TEXT, NOT NULL)
└── metadata (TEXT, JSON)
```

Evidence всегда жестко связан реляционными ключами со своим источником и конкретным местом внутри документа.

### Правило уникальности Evidence

Поле `evidence_hash` вычисляется как SHA256 от конкатенации: точный текст цитаты + `target_chunk_id` + `document_id`.

При попытке создать Evidence с уже существующим `evidence_hash` система обязана:

1. Не создавать дублирующую запись.
2. Вернуть ссылку на существующий Evidence.
3. Зафиксировать факт дублирования в логах.

Контекстный чанк (переданный через `EvidenceContextChunk` с `is_target = FALSE`) **НЕ является самостоятельным Evidence** только потому, что был передан в LLM для понимания контекста.

### 13a. EvidenceContextChunk (Связующая таблица контекстного окружения)

Обеспечивает явную реляционную фиксацию всех чанков (включая соседние ±1), которые были переданы в ИИ-модель для сохранения смысловой непрерывности в момент извлечения доказательства.

```
EvidenceContextChunk
├── evidence_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Evidence ON DELETE CASCADE)
├── chunk_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES DocumentChunk ON DELETE RESTRICT)
└── is_target (BOOLEAN, NOT NULL) -- TRUE для основного чанка, FALSE для соседнего (контекстного)

PRIMARY KEY (evidence_id, chunk_id)
```

Промежуточная сущность слоя анализа, извлекаемая ИИ из тела Evidence. Служит атомарным элементом для вычисления частот и построения сравнений.

Наличие сущности Observation не замещает собой и не приводит к удалению оригинального объекта Evidence.

## 17. ResearchGap

## 21. DB-write layer

Все воркеры, сетевые адаптеры и аналитические компоненты системы полностью лишены права прямой записи в базу данных SQLite.

**Схема организации записи:**

```
Сетевые/Аналитические воркеры (Workers)
         ↓ [Поток объектов данных]
Единая очередь результатов (Result Queue)
         ↓
Изолированный диспетчер записи (DB Writer Thread)
         ↓ [Последовательные транзакции]
База данных SQLite (Режим WAL)
```

Ни один сетевой или поисковый воркер не должен напрямую конкурировать за блокировку файла базы данных. Любые транзакции на запись выполняются строго последовательно в один поток внутри выделенного диспетчера.

## 22. Индексы

Для обеспечения высокой скорости выполнения JOIN-операций и выборок на локальном процессоре (CPU), база данных обязана содержать следующие индексы:

- **Индексы по одиночным внешним ключам:** `study_id`, `project_id`, `document_id`, `chunk_id`, `evidence_id`, `task_id`, `source_id`.

## 23. Изоляция данных

Локальный контекстный поиск в рамках исследования (Study) жёстко ограничен документами текущего проекта через StudyDocumentLink. Глобальный поиск допускается только в режиме EXPAND или GLOBAL_ARCHIVE и выполняется в границах текущего проекта. Кросс-проектный поиск доступен как отдельная операция через реестр.

Выход за границы изоляции и проведение глобального сквозного поиска по всему репозиторию документов системы категорически запрещены. Глобальный поиск допускается к выполнению только в том случае, если пользователь перед стартом сессии явно активировал системный режим `EXPAND` или `GLOBAL_ARCHIVE`.

## 24. Жизненный цикл и консистентность SQLite

Работа с СУБД SQLite строится на основе жестких правил обеспечения целостности данных:

- Режим WAL является строго обязательным системным требованием.
- Любая логически связанная группа изменений (например, сохранение документа с одновременным созданием чанков и обновлением статуса задачи) обязана оборачиваться в единую транзакцию с поддержкой автоматического отката (ROLLBACK) при возникновении ошибок.
- Система обязана регулярно проводить программные проверки целостности структуры базы данных (`PRAGMA integrity_check`).
- В ядре реализуются процедуры создания контрольных точек (`PRAGMA wal_checkpoint(PASSIVE)`), механизмы резервного копирования на лету и сценарии автоматического восстановления консистентности сессий из логов после аварийного отключения питания компьютера. Жизненный цикл подключений к БД (connection lifecycle) полностью контролируется ядром Core и изолирован от ИИ-модели.

При записи Document или Source в проектную БД —
обновлять соответствующую запись в реестре.
Операция атомарная, через DB-write layer.

### 25.4. Кросс-проектный поиск
Уровень 1 (простой, для малого числа проектов):
  Перебор проектных БД по очереди.

  Поиск в реестре → определение проектов с совпадениями
  → ATTACH только нужных .db файлов → поиск внутри.

## 26. Конфигурация подключений к SQLite

Все подключения к базе данных (чтение и запись) обязаны проходить через единую фабрику подключений, которая применяет следующий набор PRAGMA на каждое соединение:

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA foreign_keys=ON;
PRAGMA busy_timeout=5000;
PRAGMA journal_size_limit=67108864;
PRAGMA wal_autocheckpoint=1000;
```

**Критические правила:**

1. `PRAGMA foreign_keys=ON` не сохраняется между подключениями и обязана выставляться на каждом новом соединении. Без неё внешние ключи не работают.
2. `PRAGMA busy_timeout` предотвращает немедленные ошибки `SQLITE_BUSY` при параллельных чтениях.
3. `PRAGMA journal_size_limit` ограничивает рост WAL-файла.
4. Единая фабрика подключений является единственным способом получения соединения с БД. Прямое создание подключений в обход фабрики запрещено.
