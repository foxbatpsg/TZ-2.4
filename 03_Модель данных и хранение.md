**Назначение:** Определение полной структуры реляционных данных, схемы таблиц, правил индексации, изоляции и обеспечения целостности хранилища.

## 1. Общие правила

Основное хранилище системы — база данных SQLite, функционирующая в режиме WAL (Write-Ahead Logging) для обеспечения параллельного бесконфликтного чтения и надежной записи.

Все операции модификации, вставки и удаления данных выполняются исключительно через изолированный программный компонент — единый DB-write layer.

Сущность **Study** (Исследование) является логически изолированным контекстом исследования. Сущность **Project** (Проект) объединяет под собой несколько Studies.

Сущность Document является глобальным объектом в рамках проекта и может одновременно использоваться несколькими Studies без физического дублирования текста на диске.

### 1a. Идентификация операций и идемпотентность

Система обязана различать три типа идентификаторов для обеспечения идемпотентности операций и безопасных повторных попыток:

1. **operation_id** — уникальный идентификатор конкретной операции MCP или внутреннего действия ядра. Генерируется при создании операции. Используется для логирования, трассировки и связи с ошибкой.

2. **request_id** — уникальный идентификатор конкретного внешнего сетевого запроса (один fetch = один request_id). Используется для кэширования, дедупликации сетевых вызовов и rate limiting.

3. **idempotency_key** — детерминированный ключ, гарантирующий, что повторное выполнение операции не создаст дублирующихся сущностей. Формируется из семантического содержания операции (например, SHA256 от параметров запроса для SearchTask, SHA256 от content для Document).

**Правила применения:**

- Каждая запись в таблицах, создаваемая в результате операции, обязана ссылаться на `operation_id`, который её создал.
- Повторный вызов операции с тем же `idempotency_key` не создаёт новую сущность, а возвращает ссылку на существующую.
- При восстановлении после сбоя (`SESSION_RESUMING`) ядро проверяет `idempotency_key` для предотвращения дублирования.

## 6. SearchTask

Каждая поисковая подзадача содержит обязательный уникальный цифровой отпечаток `query_fingerprint` для предотвращения дублирования запросов.

```
SearchTask
├── task_id (TEXT, PRIMARY KEY, UUID)
├── study_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Study)
├── purpose (TEXT, NOT NULL)
├── query (TEXT, NOT NULL)
├── query_fingerprint (TEXT, NOT NULL) -- SHA256 от параметров запроса; уникален в пределах Study
├── gap_id (TEXT) -- Связь с породившим ResearchGap (A-15); NULL для системных задач
├── source_scope (TEXT, NOT NULL)
├── filters (TEXT)
├── exclusions (TEXT)
├── expected_material_type (TEXT)
├── priority (INTEGER, DEFAULT 0)
├── status (TEXT, NOT NULL) -- Контролируется автоматом состояний SearchTask
├── operation_id (TEXT) -- UUID операции, создавшей задачу
├── idempotency_key (TEXT) -- Детерминированный ключ для предотвращения дублей при повторе
├── created_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
└── completed_at (TIMESTAMP)
```

Область уникальности (A-04): `query_fingerprint` уникален **в пределах Study** — составной уникальный индекс `(study_id, query_fingerprint)`. Идемпотентность включает тип операции и область Project/Study: одинаковая цитата или запрос в разных Studies не блокируются и не раскрывают чужие данные. Каждый SearchTaskDraft связан с сохранённым ResearchGap через `gap_id` (A-15); LLM не создаёт persistent SearchTask в обход Core.

Поле `status` управляется формальным автоматом состояний SearchTask. Допустимые переходы и триггеры определены в контракте «State Machine Specification» (Раздел 01, секция 2.3). Прямое изменение статуса в обход автомата запрещено.

```
Source
├── source_id (TEXT, PRIMARY KEY, UUID)
├── canonical_url (TEXT, NOT NULL, UNIQUE)
├── domain (TEXT, NOT NULL)
├── source_type (TEXT, NOT NULL)
├── quality_profile (TEXT, NOT NULL)
├── provenance (TEXT)
├── identifiers (TEXT)
└── metadata (TEXT, JSON)
```

Оценка качества источника (`A-10`): детализированная оценка хранится в отдельной таблице `SourceQualityAssessment` с областью видимости (scope) Study/domain/research_mode/config revision, а не в поле Source. Поле `quality_profile` сохраняется как совместимая агрегированная ссылка. Идентификаторы источника (DOI/PMID/arXiv и др.) хранятся как источник истины в нормализованной таблице `SourceIdentifier` (source_id, identifier_type, identifier_value); поле `identifiers` — совместимая сериализация.

Параметр `quality_profile` динамически рассчитывается и оценивается программным ядром относительно текущей предметной области (domain) и установленного режима исследования (research_mode).

canonical_url уникален в рамках проектной БД. Глобальная уникальность обеспечивается через GlobalSourceIndex в реестре.

### 8a. SourceRelation (Связи и генеалогия источников)

Сущность для фиксации заимствований, копирований и вычисления реальной независимости информационных узлов.

```
SourceRelation
├── relation_id (TEXT, PRIMARY KEY, UUID)
├── study_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Study)
├── source_source_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Source) -- Откуда скопировано
├── target_source_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Source) -- Куда скопировано
├── claim_id (TEXT, FOREIGN KEY REFERENCES Claim) -- Связь с конкретным Claim (Q-02); NULL, если связь общая для источников
├── relation_type (TEXT, NOT NULL) -- Enum: COPY, REWRITE, CITATION, SAME_PRIMARY, UNKNOWN
├── confidence (REAL, NOT NULL)
├── detected_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
└── metadata (TEXT, JSON)
```

Уровень независимости (`Q-02`): связи независимости оцениваются на уровне `Claim`, а не только сайта. Отношение, применимое к одному Claim (например, CITATION), не превращает весь Source в зависимый для всех Claims — для этого заполняется `claim_id`. Одна связь не делает весь Source зависимым.

Уникальность SourceRelation (N-02, ADR-003): уникальность обеспечивается двумя частичными индексами — для claim-specific связей `UNIQUE (study_id, source_source_id, target_source_id, claim_id) WHERE claim_id IS NOT NULL`; для общих связей `UNIQUE (study_id, source_source_id, target_source_id) WHERE claim_id IS NULL`. Обязательна проверка принадлежности Claim и обоих Source одной Study. При конфликте claim-specific связь переопределяет общую связь той же пары. Миграция обязана проверить существующие дубликаты до применения и не удалять их молча.

### 8b. Entity (Слой нормализации объектов исследования)

Детерминированный справочник для предотвращения фрагментации структурированных наблюдений и исключения семантических ошибок ИИ при склейке сущностей.

```
Entity
├── entity_id (TEXT, PRIMARY KEY, UUID)
├── study_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Study)
├── type (TEXT, NOT NULL) -- Enum: PRODUCT, PERSON, ORGANIZATION и т.д.
├── canonical_name (TEXT, NOT NULL) -- Официальное единое имя
├── normalized_key (TEXT, NOT NULL) -- Ключ для точного совпадения (lowercase, без спецсимволов)
├── normalization_method (TEXT, NOT NULL) -- EXACT_ALIAS_MATCH, METADATA_MATCH и т.д.
└── created_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
```

Синонимы (`A-03`): список алиасов хранится как источник истины в нормализованной таблице `EntityAlias` (entity_id, alias, normalized_alias); текстовое поле `aliases` в Entity запрещено как источник истины (исключено из схемы) и допускается только как API-сериализация.

Обязателен уникальный индекс на составной ключ `(study_id, normalized_key)`.

## 9. Document

```
Document
├── document_id (TEXT, PRIMARY KEY, UUID)
├── source_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Source)
├── content_hash (TEXT, NOT NULL, UNIQUE) -- SHA256 от сырого очищенного текста
├── title (TEXT)
├── content (TEXT, NOT NULL)
├── content_type (TEXT, NOT NULL)
├── language (TEXT)
├── fetched_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
├── published_at (TIMESTAMP)
├── operation_id (TEXT) -- UUID операции, создавшей документ
├── metadata (TEXT, JSON)
└── processing_status (TEXT, NOT NULL)
```

При совпадении content_hash документ не сохраняется повторно в рамках данного проекта.

Неизменяемость Document (A-21): Document, на который ссылается Evidence, является неизменяемым. Обновление содержимого или URL не перезаписывает Document — создаётся **новая версия Document** (новый document_id/content_hash); снятие связи StudyDocumentLink не является физическим удалением документа.

#### 9b. Механизм версионирования Document (Q-08)

**Механизм версионирования Document (Q-08):** операционализация нормы A-21 — настоящий подраздел определяет механизм создания новых версий Document, который не был специфицирован в A-21 (ADR-002, принят 2026-09-14).

**Идемпотентное окно.** Для каждого Document существует окно идемпотентности длительностью **24 часа** с момента последнего успешного чтения (baseline; может быть изменено конфигурацией). Внутри окна повторное чтение того же URL возвращает существующую версию Document. По истечении окна разрешается новое получение содержимого.

**Принудительное обновление (refresh).** Явный механизм обновления — флаг `refresh=true` в инструменте `read_url_content`. При включённом флаге ядро игнорирует идемпотентное окно и выполняет новое получение содержимого. Отдельный `refresh`-tool **не вводится** — флаг в существующем `read_url_content` сохраняет MCP-поверхность.

**Правила выбора версии.**

- Study «замораживает» версию Document, на которую уже сослался Evidence (неизменяемость из A-21): Evidence всегда указывает на конкретную версию Document (`document_id`), и обновления не меняют уже собранные Evidence.
- EXPAND и операции добавления новых материалов используют последнюю доступную версию Document (через `DocumentSourceOccurrence` JOIN).
- Если `refresh` получает содержимое с тем же `content_hash`, что и существующая версия, новая версия Document **не создаётся** (согласно правилу «При совпадении content_hash документ не сохраняется повторно»). Обновляется только кэш-запись. Ответ инструмента: `CONTENT_UNCHANGED`.

**Следствие для кэша (`04` §25).** Состояние `FORCED_REFRESH` расширяется на MCP-трафик: `read_url_content(refresh=true)` инициирует принудительное обновление аналогично GUI-команде. При `content_hash` = existing кэш обновляется, новая версия Document — нет.

**Применение к локальным документам.** Механизм распространяется на локальные документы: повторный импорт изменённого файла через `add_local_document` даёт новый `content_hash` и создаёт **новую версию Document** (A-21); Evidence, сославшийся на старую версию, сохраняет на неё ссылку. Автоматическое отслеживание изменений файлов на диске (mtime-наблюдение) **не вводится** — обнаружение изменения выполняется только явным повторным импортом; совпадение `content_hash` при повторном импорте возвращает существующий Document (`MCP TOOL CONTRACTS` §4, IDEMPOTENCY).

### 9a. DocumentSourceOccurrence (Происхождения документа — A-08)

**Одно очищенное тело документа (A-08):** Один Document хранит очищенное тело ровно один раз (по `content_hash`). Каждое обнаруженное происхождение (URL/Source, по которому найден тот же контент) фиксируется отдельной строкой:

```
DocumentSourceOccurrence
├── occurrence_id (TEXT, PRIMARY KEY, UUID)
├── document_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Document ON DELETE CASCADE)
├── source_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Source)
├── url (TEXT) -- Конкретный URL происхождения, если применимо
├── first_seen_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
└── metadata (TEXT, JSON)
```

Первоначальный `source_id` в таблице Document сохраняется как совместимая ссылка на первое происхождение и **не считается полным списком происхождений** — полный список восстанавливается JOIN по `DocumentSourceOccurrence`.

Локальное происхождение (`A-17`): для локальных документов (MATERIALS_ONLY / локальные материалы) запрещено выдумывать URL/DOI/PMID — происхождение фиксируется внутренним source reference, `file_ref`, `content_hash` и координатами в документе; приватные абсолютные пути не передаются в LLM и не попадают в публичный отчёт.

## 10. StudyDocumentLink

Связующая таблица для обеспечения явной реляционной связи и изоляции документов между исследованиями.

```
StudyDocumentLink
├── study_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Study ON DELETE CASCADE)
├── document_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Document ON DELETE RESTRICT)
├── relation_type (TEXT, NOT NULL) -- Enum: RETRIEVED, USER_ADDED, PROJECT_CONTEXT, IMPORTED
└── added_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
```

**Строгое правило изоляции:** Изоляция локального поиска по материалам конкретного исследования обязана реализовываться исключительно через операцию JOIN по таблице `StudyDocumentLink`. Категорически запрещено использовать JSON-массивы вида `study_ids` внутри таблицы Document в качестве источника истины для разграничения прав доступа. Обязателен составной первичный уникальный ключ `(study_id, document_id)`.

Снятие связи (`A-21`): удаление записи из `StudyDocumentLink` означает отвязку документа от исследования, но **не** физическое удаление Document, если на него ссылается Evidence другого активного исследования. Удаление Study не удаляет общий Document.

## 11. DocumentChunk

```
├── char_end (INTEGER, NOT NULL)

├── page_number (INTEGER)
├── position_index (INTEGER, NOT NULL)
├── overlap_group_id (TEXT, NOT NULL) -- UUID группы пересекающихся чанков (вспомогательный признак)
├── is_overlap (BOOLEAN, DEFAULT FALSE) -- Флаг пересечения; НЕ удаляет уникальную часть чанка из анализа
└── metadata (TEXT, JSON)
```

Стабильные идентификаторы (A-07): используется поле `DocumentChunk.text` (не `content`). `chunk_id` детерминирован относительно document identity, версии chunker и позиции; поисковый normalized text никогда не заменяет исходный текст цитаты. Смена версии разбиения не ломает доказательную базу — изменение chunk_size/параметров создаёт только новые версии разбиения (новые chunk_id), не перезаписывая существующие.

Числовые сигнатуры (`A-03`): извлечённые числа хранятся как источник истины в нормализованной таблице `ChunkNumericSignature` (chunk_id, value, unit, raw, type); поле `numeric_signatures` исключено из схемы как источник истины и допускается только как API-сериализация.

Поле `numeric_signatures` хранит нормализованные числовые данные в формате JSON-массива для детерминированного выявления противоречий без участия LLM.

Расширяемость ретривал-хранения (A-23): векторное хранение проектируется как **боковая таблица** `ChunkEmbedding(chunk_id, model_id, vector, created_at)` рядом с `DocumentChunk` — без изменения существующих таблиц; внешний ключ к `DocumentChunk`, физическое удаление чанка каскадно удаляет запись. Подключение эмбеддингов и переранжировщиков выполняется через изолированные провайдеры (`02` §5.2, RetrievalProvider/RankingProvider) и добавляется отдельной **append-only миграцией** (`03` §21, S-17). Реализация эмбеддингов — вне MVP (`07` §26); настоящая норма гарантирует, что её добавление не потребует переделки схемы, конвейера или интерфейсов.

**Структура каждого элемента массива:**

```json
{
    "value": 1500.0,
    "unit": "RUB",
    "raw": "1500 рублей",
    "type": "PRICE"
}
```

Допустимые типы (`type`): `PRICE`, `PERCENT`, `DATE`, `DOSAGE`, `SPEED`, `COUNT`, `OTHER`.

**Правила сравнения противоречий:**

- Сравниваются только записи с одинаковыми `type` и `unit`.
- Сравнение выполняется детерминированно на уровне ядра без вызова LLM.
- LLM привлекается только для семантического подтверждения конфликта на втором этапе (см. Раздел 04, секция 19).

## 12. Chunking

Система на уровне MVP реализует следующий контракт детерминированного разбиения документов:

**Тип разбиения:** Детерминированный, структурный, опирающийся на логические границы текста (абзацы, списки, элементы разметки Markdown).

**Диапазон размера чанка:** Настраиваемый начальный диапазон в 400–700 токенов.

**Перекрытие (Overlap):** Фиксированное перекрытие в диапазоне 50–100 токенов с обязательным присвоением одинакового `overlap_group_id` для всех пересекающихся фрагментов.

**Интервалы (A-06):** все координаты чанков и цитат трактуются как полуоткрытые интервалы `[char_start, char_end)` по исходному `Document.content`. `overlap_group_id` является вспомогательным признаком группировки; `is_overlap = TRUE` не удаляет уникальную неперекрывающуюся часть чанка из анализа — уникальная часть overlap-чанка не теряется.

**Сохранение контекста:** При нарезке чанка алгоритм обязан наследовать и записывать в поле `heading_path` текущую цепочку заголовков, а также сохранять целостность списков. Текстовые таблицы преобразуются парсером в читаемый построчный вид.

Сложные семантические алгоритмы чанкинга (semantic chunking) переносятся в категорию Post-MVP задач. Параметры нарезки должны быть полностью вынесены в файлы конфигурации. Крупные форматы документов (PDF/EPUB) архитектурно поддерживаются базовой схемой, но глубокие специализированные парсеры под них могут дорабатываться на этапах после MVP.

### Правило защиты статистики от overlap

При агрегировании наблюдений (Observations) и подсчёте статистических метрик система обязана учитывать флаг `is_overlap` в таблице `DocumentChunk`.

1. Чанки с `is_overlap = TRUE` исключаются из подсчёта уникальных наблюдений, если их текст уже учтён через основной чанк той же overlap-группы.
2. При извлечении Evidence из чанка с `is_overlap = TRUE` система обязана проверить, не было ли аналогичное Evidence уже извлечено из другого чанка той же overlap-группы (через `evidence_hash`).
3. Поле `overlap_group_id` используется для группировки пересекающихся чанков и предотвращения многократного учёта одного и того же текста в статистике.

## 13. Evidence

Сущность цитаты-доказательства. Контекст извлечения цитаты расширяется за пределы одного целевого чанка.

```
Evidence
├── evidence_id (TEXT, PRIMARY KEY, UUID)
├── study_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Study)
├── document_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Document)
├── target_chunk_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES DocumentChunk) -- Основной чанк
├── text (TEXT, NOT NULL) -- Точный текст цитаты из первоисточника
├── evidence_hash (TEXT, NOT NULL) -- SHA256 от (text + target_chunk_id + document_id), обеспечивает уникальность
├── location (TEXT) -- Строковое или числовое позиционирование внутри документа
├── extraction_time (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
├── task_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES SearchTask)
├── operation_id (TEXT) -- UUID операции, создавшей доказательство
├── evidence_type (TEXT, NOT NULL)
└── metadata (TEXT, JSON)
```

Evidence всегда жестко связан реляционными ключами со своим источником и конкретным местом внутри документа.

### Правило уникальности Evidence (A-05)

**Правило уникальности Evidence (A-05):** Поле `evidence_hash` вычисляется как SHA256 от конкатенации: точный текст цитаты + `target_chunk_id` + `document_id`. Контрактный `evidence_hash` сохраняется для совместимости.

Каноническая дедупликация **не ограничивается** проверкой `evidence_hash` — дополнительно проверяется:

1. Принадлежность одному Study (область владения);
2. Неизменяемая версия Document (document identity);
3. Полуоткрытый интервал позиций `[char_start, char_end)` в исходном документе;
4. Точный текст цитаты.

Одинаковый текст в разных позициях документа **не объединяется автоматически**. История извлечений (extraction history) ведётся отдельно и не влияет на каноническую дедупликацию.

При попытке создать дубликат (совпадение по канонической проверке) система обязана:

1. Не создавать дублирующую запись.
2. Вернуть ссылку на существующий Evidence.
3. Зафиксировать факт дублирования в логах.

Контекстный чанк (переданный через `EvidenceContextChunk` с `is_target = FALSE`) **НЕ является самостоятельным Evidence** только потому, что был передан в LLM для понимания контекста.

### 13a. EvidenceContextChunk (Связующая таблица контекстного окружения)

Обеспечивает явную реляционную фиксацию всех чанков (включая соседние ±1), которые были переданы в ИИ-модель для сохранения смысловой непрерывности в момент извлечения доказательства.

```
EvidenceContextChunk
├── evidence_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES Evidence ON DELETE CASCADE)
├── chunk_id (TEXT, NOT NULL, FOREIGN KEY REFERENCES DocumentChunk ON DELETE RESTRICT)
└── is_target (BOOLEAN, NOT NULL) -- TRUE для основного чанка, FALSE для соседнего (контекстного)

PRIMARY KEY (evidence_id, chunk_id)
```

```
├── canonical_url (TEXT, NOT NULL)

├── response (BLOB, NOT NULL) -- Полное бинарное или текстовое тело ответа сетевого запроса
├── created_at (TIMESTAMP, DEFAULT CURRENT_TIMESTAMP)
├── expires_at (TIMESTAMP, NOT NULL)
└── metadata (TEXT, JSON)
```

Время жизни записи (TTL) настраивается гибко в зависимости от конфигурации конкретного сетевого источника.

## 21. DB-write layer

Все воркеры, сетевые адаптеры и аналитические компоненты системы полностью лишены права прямой записи в базу данных SQLite.

**Схема организации записи:**

```
Сетевые/Аналитические воркеры (Workers)
         ↓ [Поток объектов данных]
Единая очередь результатов (Result Queue)
         ↓
Изолированный диспетчер записи (DB Writer Thread)
         ↓ [Последовательные транзакции]
База данных SQLite (Режим WAL)
```

Ни один сетевой или поисковый воркер не должен напрямую конкурировать за блокировку файла базы данных. Любые транзакции на запись выполняются строго последовательно в один поток внутри выделенного диспетчера.

**Миграции — единственный источник физической схемы (S-17).** Каталог `db/migrations/` — единственный исполняемый источник физической схемы Project DB и `registry.db`; ветки миграций двух баз раздельные. Нормативное ТЗ задаёт семантику сущностей и ограничений (UNIQUE, FK, индексы — §22 и разделы сущностей), но не дублирует DDL. Второй ручной `CREATE TABLE` в коде, fixtures или репозиториях запрещён; его обнаружение блокирует сборку тестом. Документация схемы генерируется из мигрированной тестовой БД, а не пишется вручную.

## 23. Изоляция данных

Локальный контекстный поиск в рамках исследования (Study) жёстко ограничен документами текущего проекта через StudyDocumentLink. Глобальный поиск допускается только в режиме EXPAND или GLOBAL_ARCHIVE и выполняется в границах текущего проекта. Кросс-проектный поиск доступен как отдельная операция через реестр.

Выход за границы изоляции и проведение глобального сквозного поиска по всему репозиторию документов системы категорически запрещены. Глобальный поиск допускается к выполнению только в том случае, если пользователь перед стартом сессии явно активировал системный режим `EXPAND` или `GLOBAL_ARCHIVE`.

Меж-Study изоляция (`A-04`): повтор запроса или цитаты в другом Study не раскрывает чужие данные — уникальность/идемпотентность scoped к Study/Project; отсутствие доступа между Project является обязательным свойством, а stale-состояние глобального реестра допустимо и восстанавливается через outbox reconciliation (§25.3).

## 24. Жизненный цикл и консистентность SQLite

Работа с СУБД SQLite строится на основе жестких правил обеспечения целостности данных:

- Режим WAL является строго обязательным системным требованием.
- Любая логически связанная группа изменений (например, сохранение документа с одновременным созданием чанков и обновлением статуса задачи) обязана оборачиваться в единую транзакцию с поддержкой автоматического отката (ROLLBACK) при возникновении ошибок.
- Система обязана регулярно проводить программные проверки целостности структуры базы данных (`PRAGMA integrity_check`).
- Гарантии durability (A-11): `PRAGMA synchronous=FULL` для записей; `PRAGMA foreign_keys=ON` на каждом соединении; резервное копирование выполняется через **SQLite Backup API** (безопасное консистентное копирование работающей БД).
- Мониторинг (`A-11`): ядро отслеживает размер WAL-файла и свободное место на диске; превышение порогов формирует диагностическое событие. `journal_size_limit` не является жёстким пределом и не гарантирует размер файла.
- В ядре реализуются процедуры создания контрольных точек (`PRAGMA wal_checkpoint(PASSIVE)`), механизмы резервного копирования на лету и сценарии автоматического восстановления консистентности сессий из логов после аварийного отключения питания компьютера. Жизненный цикл подключений к БД (connection lifecycle) полностью контролируется ядром Core и изолирован от ИИ-модели.

## 25. Изоляция по проектам и глобальный реестр

### 25.1. Единица изоляции БД
Каждый Project хранится в отдельном файле базы данных:
  data/projects/{project_id}.db

Переключение активного проекта = переключение файла БД.
Внутри проектной БД действует полная текущая схема таблиц.

### 25.2. Глобальный реестр (registry.db)
Отдельный файл, хранит только метаданные. Глобальные identity и locations хранятся **отдельными строками** (`A-09`): один content_hash/canonical_url может иметь несколько мест хранения (locations) в разных проектах. Между файлами БД (проектной и реестром) FOREIGN KEY запрещены — целостность обеспечивается приложением и синхронизацией (§25.3).

ProjectRegistry:
├── project_id (UUID)
├── name (TEXT)
├── db_path (TEXT) — путь к .db файлу проекта
├── status (TEXT) — active / archived
└── created_at (TIMESTAMP)

GlobalDocumentIndex:
├── content_hash (TEXT)
├── project_id (UUID)
├── document_id (UUID) — локальный в проекте
└── title (TEXT)
(уникальность по паре (content_hash, project_id, document_id); identity не PRIMARY KEY — несколько locations на один hash)

GlobalDocumentLocation:
├── content_hash (TEXT)
├── project_id (UUID)
└── document_id (UUID)

GlobalSourceIndex:
├── canonical_url (TEXT)
├── project_id (UUID)
├── source_id (UUID) — локальный в проекте
└── domain (TEXT)
(уникальность по паре (canonical_url, project_id, source_id))

Границы доступа (A-09): реестр содержит только идентичность и расположение; он **не даёт доступа к содержимому** другого Project. Наличие записи в реестре не раскрывает данные чужого проекта.

### 25.3. Правило синхронизации (Q-01 — transactional outbox)

**Синхронизация Project DB → registry.db через transactional outbox (Q-01):** Project DB является **источником истины**. Межфайловая атомарность SQLite (Project DB + registry.db) не поддерживается — согласованность обеспечивается transactional outbox:

```
DB Writer (одна SQLite-транзакция):
  запись Document/Source в проектную БД
  + запись OutboxEvent (event_id, тип, project_id, identity, payload hash, schema version, retry state)
       ↓
Registry Writer (отдельный процесс/поток):
  идемпотентное применение события к registry.db (по event_id)
       ↓
Reconciliation worker:
  повтор неподтверждённых событий; alert после исчерпания retry
```

До применения события Project считается сохранённым, а global registry может быть временно stale — это допустимое состояние. Повтор события не создаёт дубликатов (идемпотентность по `event_id`). После исчерпания retry событие помечается `FAILED` и формируется alert.

Snapshot нескольких файлов фиксирует общий snapshot manifest и версии всех БД; multi-file snapshot **не объявляется crash-atomic** — восстановление проверяет manifest и выполняет outbox reconciliation.

### 25.4. Кросс-проектный поиск
Уровень 1 (простой, для малого числа проектов):
  Перебор проектных БД по очереди.
Уровень 2 (масштабируемый):
  Поиск в реестре → определение проектов с совпадениями
  → ATTACH только нужных .db файлов → поиск внутри.

## 26. Конфигурация подключений к SQLite

Все подключения к базе данных (чтение и запись) обязаны проходить через единую фабрику подключений, которая применяет следующий набор PRAGMA на каждое соединение:

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=FULL;
PRAGMA foreign_keys=ON;
PRAGMA busy_timeout=5000;
PRAGMA journal_size_limit=67108864;
PRAGMA wal_autocheckpoint=1000;
```

**Критические правила:**

1. `PRAGMA foreign_keys=ON` не сохраняется между подключениями и обязана выставляться на каждом новом соединении. Без неё внешние ключи не работают.
2. `PRAGMA synchronous=FULL` обязательна для соединений записи (A-11); NORMAL допустима только для read-only соединений, если это явно разрешено конфигурацией.
3. `PRAGMA busy_timeout` предотвращает немедленные ошибки `SQLITE_BUSY` при параллельных чтениях.
4. `PRAGMA journal_size_limit` — рекомендация по усечению WAL, не жёсткий предел (A-11); рост WAL контролируется мониторингом (§24).
5. Единая фабрика подключений является единственным способом получения соединения с БД. Прямое создание подключений в обход фабрики запрещено.
