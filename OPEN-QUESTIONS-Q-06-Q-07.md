## Q-06 — Контекст извлечения Evidence через MCP

### Проблема (черновик v1.1, §2)

> **Проблема:** `search_within_document` не гарантирует LLM полный контекстный коридор ±1 (соседние чанки, offsets, ID соседей). `save_study_material` ограничен 4 KiB; ответа 8 KiB может не хватить для коридора. Запрещено молча добавлять скрытый 24-й tool.

### Предложение — вариант A (рекомендуемый)

> - Расширить контракт `search_within_document`: добавить read-опцию `include_evidence_context: boolean` (default `true`), гарантированный вывод: версия документа, номера/ID соседних чанков, отрезки `[char_start, char_end)` основного и соседних чанков, точный текст.
> - Пересмотреть лимиты: для `search_within_document` с контекстом — ответ, достаточный для коридора (черновик: 32 KiB), для `save_study_material` — 4 KiB остаётся как ограничение на метаданные (без претензии нести полный коридор).
> - LLM не вводит «теневой» tool: весь доступ — через заявленные контрактные tool-ы.

### Вариант B (альтернатива)

> зарегистрировать официальный 24-й tool (`search_within_document_context`). Требует явного решения, т.к. расширяет публичную поверхность MCP.

**Что нужно утвердить:** вариант A или B; точные лимиты; является ли коридор обязательным в каждом ответе или по запросу.
**Не блокируется:** локальная сборка и валидация коридора в Core; пред-извлечённые Evidence ±0; всё, что не требует передачи контекста через MCP.
**Затрагиваются:** `MCP TOOL CONTRACTS v1.2` (§3 `search_within_document`, §5 `save_study_material`), `04_Search Core.md` §15, `05_Взаимодействие с LLM и протокол MCP.md`.

### Решение архитектора (файл «Архитектурное решение по Q-06 — Q-13», раздел Q-06)

> **Решение: Вариант A.**
>
> Не вводить отдельный «теневой» 24-й tool. Расширить существующий `search_within_document`.
>
> Добавить опцию: `include_evidence_context: boolean`. Рекомендуемый default: `true`.
>
> При включении контекста MCP обязан возвращать: идентификатор и версию документа; основной chunk и соседние chunks коридора ±1; ID соседних chunks; offsets `[char_start, char_end)`; точный текст соответствующих фрагментов.
>
> Лимит ответа должен быть увеличен настолько, чтобы гарантированно вместить требуемый коридор. Черновые 32 KiB можно принять как стартовое значение, но окончательный лимит должен быть подтверждён тестами.
>
> `save_study_material` не должен использоваться как механизм передачи полного Evidence Context.
>
> **Причина:** это сохраняет существующую MCP-поверхность, не создаёт скрытого интерфейса и делает получение доказательного контекста явной частью контракта `search_within_document`.
>
> **Статус:** утвердить как A; точный лимит определить тестами.

## Q-07 — Provenance локальных Evidence

### Проблема (черновик v1.1, §3)

> **Проблема:** `Evidence.task_id NOT NULL`, но `save_study_material` / `add_local_document` не дают task_id. Не к чему привязать локальные Evidence. Недопустимо подставлять фиктивный сетевой task_id.

### Предложение — вариант A (рекомендуемый)

> - Ввести «локальную аналитическую SearchTask»: task с типом/purpose=`local_analysis`, создаваемая Core при локальном импорте/сохранении; на неё ссылаются локальные Evidence. Provenance: внутренний source reference (`file_ref`, `content_hash`, координаты), без выдуманных URL/DOI/PMID (см. A-17).
> - `add_local_document`/`save_study_material` получают этот `task_id` из Core и сохраняют связь.

### Вариант B

> ослабить схему (`task_id` NULLABLE) с запретом на удаление локальных материалов, подтверждённых Evidence.

**Что нужно утвердить:** вариант A или B; признак «локальности» в схеме (отдельная колонка/тип задачи).
**Не блокируется:** импорт, индексирование, локальный поиск (BM25), MATERIALS_ONLY — реализуемы заранее.
**Затрагиваются:** `03_Модель данных и хранение.md` §6 (SearchTask), §13 (Evidence), `MCP TOOL CONTRACTS v1.2` (§4 `add_local_document`, §5 `save_study_material`).

### Решение архитектора (файл «Архитектурное решение по Q-06 — Q-13», раздел Q-07)

> **Решение: Вариант A.**
>
> Ввести специальный тип `SearchTask`:
>
> `purpose = local_analysis`
>
> Core создаёт такую задачу при обработке локального материала. Локальные Evidence получают настоящий `task_id`, а не фиктивный сетевой идентификатор.
>
> Provenance локального Evidence должен хранить: `file_ref`; `content_hash`; координаты/чанки исходного материала; другие необходимые локальные идентификаторы.
>
> Нельзя создавать фиктивные URL/DOI/PMID.
>
> `add_local_document` и `save_study_material` должны получать `task_id` от Core.
>
> **Причина:** сохраняется инвариант `Evidence.task_id NOT NULL`, а происхождение локальных доказательств становится таким же формальным и трассируемым, как у внешних.
>
> **Статус:** утвердить A.
