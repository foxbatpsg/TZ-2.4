## 3. Принятые блокеры (P0) — детально

### N-01 · Не определён MCP-host и владелец агентного цикла — `ACCEPT`

| Поле | Значение |
|---|---|
| **Источник** | `замечания GPT6.md` §N-01 (стр. 63–78); ТЗ `05` §2–3; EPIC-07 |
| **Суть** | Схема «LLM → MCP → Core» пропускает звено host/client. Модель возвращает tool calls по HTTP, но сама не является stdio-клиентом. Для автономного GUI-приложения владелец агентного цикла не назначен. |
| **Подтверждение** | ARCHITECTURE §1.4 п.1 требует «единый процесс, один активный MCP stdio-сервер на процесс», а §4.1 объявляет MCP **единственным** каналом LLM→Core. Одновременно §1.2 указывает для LLM «OpenAI-compatible HTTP API». Эти два положения не сведены в единую процессную схему. |
| **Риск** | Агент-исполнитель самостоятельно изобретёт схему запуска → расхождение реализаций у разных исполнителей; риск одновременного владения одной Project DB двумя Core. |
| **Рекомендация** | Оформить ADR с двумя явными профилями: **desktop orchestration** (Application Orchestrator вызывает LLM по HTTP, проверенные tool calls идут в единый ToolDispatcher/Application API) и **headless `--mcp-stdio`** (внешний адаптер для Cline/OpenCode). Явно зафиксировать: MCP — не протокол инференса. Описать владельца процесса и Project DB, project lock, lifetime единственного Core. |
| **Зависимые блокировки** | Любые TASK по EPIC-05/06/07 до принятия ADR должны быть `BLOCKED`. |

### S-12 · Q-08: Document identity vs `content_hash` — `ACCEPT`

| Поле | Значение |
|---|---|
| **Источник** | `замечания GPT6.md` §S-12 (стр. 80–95); `SUGGESTIONS.md` §2.5; ТЗ `03` §9 (стр. 291), §9a, `07` §17 (стр. 249) |
| **Суть** | Прямое противоречие в тексте ТЗ. A-21 требует создавать **новую версию Document** при смене URL, но поле `content_hash` объявлено `UNIQUE` (ТЗ `03`, стр. 277: «SHA256 от сырого очищенного текста») и тело документа должно храниться один раз. |
| **Подтверждение** | Логическая неустранимость: если URL изменился, а текст — тот же, новый Document не может получить уникальный `content_hash`. Если текст изменился — это уже другой документ, и A-21 здесь ни при чём. Сформулированное правило нереализуемо в текущей схеме. |
| **Статус в ТЗ** | Дефект **признан открытым самим ТЗ**: `07_QA_Acceptance.md` стр. 249 — «обновление URL в существующем Document — блокер Q-08, открыт». |
| **Рекомендация** | Разделить **content identity** и **URL provenance**: идентичность Document определяется очищенным содержимым. Новый URL при прежнем hash → добавляется запись `DocumentSourceOccurrence`, тело, `document_id` и Evidence не меняются. Изменённый текст → новый Document. Не подменять `content_hash` хешем URL. Переписать формулировку A-21 синхронно в разделах `03`, `07` и зависимых TASK. |
| **Зависимые блокировки** | TASK, затрагивающие `Document.version` / URL update, — `BLOCKED` до закрытия Q-08. |

## 5a. Отложенные до Post-MVP (`DEFER`)

> Замечание принято как валидное, но сознательно вынесено за рамки MVP: механизм требует собственного решения и не должен задерживать запуск. Фиксируется явно, чтобы не всплывало повторно и не блокировало MVP-задачи.

### S-03 · Хранилище API-ключей — `DEFER` (решение принято 2026-09-13)

**Что предлагал ревьюер:** Windows Credential Manager через `keyring` как **единственный** production-механизм; запрет plaintext-fallback; в SQLite только `credential_ref`; env — только для dev/CI; fail-closed при недоступном хранилище.

**Почему отклонено в исходной редакции.** Механизм привязан к системному хранилищу учётных данных Windows, которое живёт в профиле пользователя и привязано к ключам этого профиля. Последствия для продукта признаны недопустимыми: переустановка Windows, повреждение профиля после обновления или смена учётной записи приводят к **потере доступа ко всей группе внешних интеграций одновременно** — пользователь получает не отказ одного источника, а отказ всех API-зависимых адаптеров, без возможности штатного восстановления. Дополнительно такая норма непереносима на другие ОС и создаёт долг при портировании.

**Решение пользователя (2026-09-13):**
- В MVP **не фиксировать** механизм хранения API-ключей нормативно.
- Вопрос **вынести в список доработок после запуска проекта** (Post-MVP), где механизм будет спроектирован отдельно с учётом требования устойчивости к переустановке ОС и переносимости между машинами.
- Общий запрет на хардкод секретов и утечку ключей в логи/отчёт **сохраняется** — он уже покрыт действующими нормами (`A-17` приватность, `07` §24 Security), отдельная норма не требуется.

**Что должно быть учтено при проектировании Post-MVP-механизма:**
1. Хранение не должно зависеть от профиля ОС и её обновлений.
2. Переносимость между ОС и машинами.
3. Восстановление доступа без обращения к внешней службе.
4. Защита от попадания ключей в логи, отчёт и диагностический архив.

**Целевой раздел при возврате к вопросу:** `07_QA_Acceptance.md` §26 (Post-MVP).

**Следствие для §4:** позиция `S-03` удалена из таблицы «Принятые P1/P2 — сводно», так как правка сейчас не вносится.
