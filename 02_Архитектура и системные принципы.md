**Статус:** Утвержденный архитектурный контракт (Финальная монолитная редакция)
**Назначение:** Определение глобальной структуры системы, зон ответственности компонентов, базовых режимов работы и условий аппаратной совместимости.

## 1. Назначение и классы задач

Research Prompt Suite — это локальная исследовательская система, предназначенная для управляемого сбора, обработки, сопоставления и анализа информации из веб-источников и локальных материалов пользователя без передачи конфиденциальных данных на внешние сервера.

Система на уровне архитектурного ядра обязана поддерживать два полярных класса задач:

- **Сбор и агрегация мнений (Aggregation / Review)** — обработка большого массива однотипных пользовательских или технических наблюдений для получения математически обоснованной картины (статистика упоминаний, распределение похвалы и жалоб).
- **Поиск жестких доказательств (Evidence Research)** — построение проверяемой и трассируемой базы первоисточников, научных публикаций и документов по сложному исследовательскому вопросу.

Оба класса задач используют общее поисковое ядро и единую базу данных, но переключают логику оценки достаточности данных, модели доверия к сайтам и финальные алгоритмы синтеза отчета.

## 2. Главный архитектурный закон системы

Локальная ИИ-модель (LLM) является управляющим и аналитическим слоем. Программное ядро (Search Core) является фактическим информационным и исполнительным слоем.

### 2.1. Обязанности ИИ-модели (LLM)

ИИ-модель выступает в роли «мыслящего сотрудника», который работает внутри жестких программных рамок. Модель отвечает за:

- смысловое понимание исследовательской задачи пользователя;
- выдвижение поисковых гипотез и направлений для сбора данных;
- логическую декомпозицию сложного вопроса на точечные запросы;
- смысловой анализ и сопоставление извлеченных цитат (Evidence);
- выявление текстовых противоречий в материалах;
- формулирование пробелов в знаниях (Research Gaps);
- написание понятного человеку финального отчета.

### 2.2. Обязанности программного ядра (Search Core)

Программное ядро (написанное на чистом Python) выступает в роли «жесткого контроллера и архивариуса». Оно обладает абсолютным авторитетом, не зависит от «мнения» ИИ и отвечает за:

- детерминированный поиск страниц, их скачивание, очистку от мусора и нарезку на куски (чанкинг);
- программную блокировку повторных запросов ИИ через систему цифровых отпечатков (Query Fingerprint);
- оценку качества, авторитетности сайтов и вычисление их реальной независимости друг от друга;
- надежное ведение истории исследования, контроль и принудительное списание многомерного бюджета (время, лимиты сети, лимиты вызовов ИИ);
- управление конечными автоматами состояний (запуск, пауза, переходы, обработка сбоев);
- Окончательное решение о завершении или продолжении циклов поиска. ИИ не имеет права самостоятельно решать, что данных уже достаточно.

Управление конечными автоматами состояний (запуск, пауза, переходы, обработка сбоев) осуществляется исключительно ядром через формальные машины состояний, спецификация которых определена в разделе 2.3 Раздела 01 данного ТЗ. Ни один компонент системы, включая ИИ-модель, не имеет права выполнять перевод состояния в обход формального автомата (`A-02`): LLM предлагает, Watchdog сигнализирует, Core выполняет переход. Runtime-переходы LLM backend (HEALTHY/DEGRADED/UNREACHABLE/RESTARTING), инициируемые Watchdog, **не дают Watchdog права прямой записи в SQLite** — все записи выполняются только через Core/DB Writer; Watchdog лишь передаёт команды и события.

Контроль многомерного бюджета осуществляется по формальному контракту, определённому в разделе 6a Раздела 01 данного ТЗ. Каждый компонент бюджета контролируется независимо, списание выполняется атомарно, расширение допускается только по явному действию пользователя.

**Архитектурное правило:** ИИ предлагает и анализирует — программа проверяет, списывает ресурсы и принимает исполнительные решения.

## 3. Архитектурные слои системы

Взаимодействие компонентов системы жестко разграничено по следующей схеме:

```
   Интерфейс пользователя (GUI на CustomTkinter)
                         ↓
          Менеджер промптов и сессий
                         ↓
   Владелец агентного цикла (02 §3a):
   • профиль 1 — Orchestrator в процессе приложения (по умолчанию);
   • профиль 2 — внешний MCP-клиент [stdio / JSON-RPC].
                         ↓
             Единый ToolDispatcher
      (вызов инструментов по MCP-контракту)
                         ↓
           Локальное программное ядро (Search Core)
                         │
 ┌───────────────────────┴───────────────────────┐
 ▼                                               ▼
Инструменты Core (Поиск, Fetch)          Локальный ИИ (Local LLM)
│                                   (Ollama / LM Studio / GGUF)
▼
Компоненты ядра:
├── Сетевые адаптеры источников (Source Adapters)
├── Модуль удаления дублей сайтов и текстов
├── Локальный поиск по ключевым словам (BM25)
├── Хранилище документов и цитат (SQLite WAL)
├── Контроллер многомерного бюджета и кэша
└── Оценщик достаточности (SufficiencyEvaluator)
▼
Внешний веб / Локальные папки / Академические базы данных
```

Хранилище данных изолировано по проектам: каждый Project — отдельный файл БД. Глобальный реестр обеспечивает кросс-проектный поиск и дедупликацию.

### 3a. Профили исполнения и владелец агентного цикла (N-01, ADR-001)

**Владелец агентного цикла** — сторона, которая принимает решение о следующем шаге исследования и инициирует вызовы инструментов ядра. Система поддерживает два профиля исполнения. Профиль выбирается **флагом запуска**; состав инструментов, поведение ядра и модель данных от выбора профиля не зависят.

**Профиль 1 — desktop orchestration (по умолчанию).** Агентный цикл ведёт Orchestrator внутри процесса приложения. Обращение к LLM выполняется по HTTP (`05` §1–2). Вызовы инструментов исполняются в том же процессе и проходят через **единый ToolDispatcher** — единственную точку исполнения инструментов.

**Профиль 2 — headless `--mcp-stdio`.** Приложение запускается как MCP-сервер по stdio; агентный цикл ведёт внешний MCP-клиент. Stdio-адаптер транслирует его вызовы в **тот же** ToolDispatcher. Набор инструментов — те же 23 инструмента (`05` §4); вторая реализация инструментов запрещена.

**MCP — не протокол инференса.** Утверждение «стыковка ИИ-модели с программными функциями ядра … осуществляется строго по открытому протоколу MCP» (`05` §3) означает: любой вызов инструмента ядра проходит через MCP-контракт инструмента — независимо от профиля. Оно **не** означает, что LLM обращается к ядру через MCP: MCP описывает вызов инструментов, а не вывод модели. Обращение к LLM идёт отдельным каналом (`05` §1–2) и через MCP не выполняется.

**Одно ядро на проект.** На один файл Project DB приходится ровно один процесс ядра. Попытка второго запуска на том же проекте — в любом профиле и с любым владельцем цикла — завершается типизированной ошибкой `PROJECT_LOCKED`; второй процесс не открывает базу. Блокировка снимается при штатном завершении и при восстановлении после сбоя (`02` §7).

**Граница ответственности.** Ядро **не запускает** LLM как дочерний процесс и не управляет её жизненным циклом: обращение к модели — только к внешнему HTTP-сервису. Установка, запуск и остановка LLM-бэкенда — вне обязанностей ядра.

## 4. Базовые режимы исследования

Каждое новое исследование (Study) настраивается через параметр `research_mode` в объекте цели. Переключение режима меняет только внутренние веса и правила проверок в ядре, но оставляет неизменным внешний программный интерфейс (API):

- **EVIDENCE** — фокус на проверке авторитетности документов, поиске первоисточников и исключении копирования информации.
- **AGGREGATION** — фокус на массовом извлечении структурированных параметров и расчете их частоты/распределения.
- **COMPARISON** — фокус на параллельном сборе равного объема данных для нескольких заданных объектов по одинаковым критериям.
- **EXPAND** — работа в режиме накопления: система сначала поднимает и анализирует все прошлые исследования из локального архива, выявляет точечные пробелы и только ради них делает короткие запросы в сеть.
- **MATERIALS_ONLY** — полностью автономный режим: работа ведется строго по папкам с локальными документами пользователя, сетевые адаптеры физически блокируются ядром.

Приватность локальных источников (A-17): локальные материалы имеют собственное проверяемое происхождение (внутренний source reference, `file_ref`, `content_hash`, координаты в документе) вместо выдуманных URL/DOI/PMID. Приватные абсолютные пути к локальным файлам **не передаются в LLM и не попадают в публичный отчёт** — для LLM и отчёта используются обезличенные локальные идентификаторы источников.

## 5. Аппаратная независимость и требования к железу

Главный принцип проектирования: MVP-версия системы обязана полноценно функционировать в условиях полного отсутствия мощной видеокарты (GPU-Independent).

### 5.1. Базовый режим (CPU-Only)

Система по умолчанию настраивается на работу на стандартном центральном процессоре компьютера. В этом режиме:

- Для локального текстового поиска по скачанным материалам используется детерминированный алгоритм BM25 на SQLite FTS5 — персистентный индекс в Project DB (A-24); in-memory rank_bm25 — запасной вариант для малых объёмов.
- Локальная ИИ-модель **минимально поддерживаемого класса 12–14B (A-22)** запускается в сильном квантованном формате (рекомендуется GGUF с квантованием Q4_K_M или Q5_K_M) через движки Ollama или llama.cpp, оптимизированные под процессорные инструкции.

### 5.2. Режим расширения (GPU-Ready)

Архитектура системы проектируется как модульный конструктор. Подключение в Post-MVP версии векторных баз данных (ChromaDB, FAISS), моделей векторных эмбеддингов или нейросетевых переранжировщиков (Rerankers) должно происходить через изолированные интерфейсы-провайдеры (RetrievalProvider, RankingProvider); схема хранения векторов — боковая таблица (A-23, `03` §11) и не имеет права требовать переписывания логики ведения исследования, интерфейса или структуры таблиц базы данных.

### 5.3. Целевая среда и performance budget (Q-12 — TARGET, не обещание)

**Целевая среда и performance budget (Q-12):** значения настоящей матрицы — TARGET-цели для приёмки (G-10/G-11), подлежащие подтверждению benchmark-spike'ом (S-13). До измерений на реальном baseline-железе они **не являются объявленной производительностью** и не используются как критерий приёмки.

| Параметр | Минимум | Рекомендуемая |
|---|---|---|
| Windows | 10 22H2 x64 / 11 23H2 x64 | 11 23H2+ x64 |
| RAM | 16 GB | 32 GB |
| Свободный диск | 20 GB | 50 GB |
| CPU | x64, 4 ядра, AVX2 | 8 ядер, AVX2 |
| GPU | не обязателен | — |
| Модель LLM | 12B Q4/Q5 | 14B Q4/Q5 |

Performance budgets (TARGET): старт GUI ≤ 5 с; отклик UI на событие ≤ 100 мс; сигнал кооперативной отмены ≤ 1 с; бюджеты генерации и обработки задаются отдельно по типу операции. Численные критерии приёмки фиксируются только по результатам измерений; до этого значения помечаются `TARGET`, а не `RESULT` (S-13).

Минимально поддерживаемый класс LLM (A-22): минимально поддерживаемый класс локальной модели — 12–14B в квантовании Q4/Q5 (GGUF); верхней границы не устанавливается — модели большего размера разрешены при достаточных ресурсах машины через тот же backend-контракт (OpenAI-совместимый HTTP, `05` §1–2). Бюджет контекста определяется динамически (A-12); профиль исполнения и требования к модели от её размера не зависят. Утверждённые TARGET-параметры среды — §5.3.

## 6. Контекстная защита ИИ и работа в условиях ограничений

Локальные ИИ-модели (минимальный класс 12–14B, A-22) имеют жесткие лимиты скорости и склонны терять информацию в середине длинных текстов («Lost in the Middle»). Архитектура системы обязана защищать контекстное окно ИИ от перегрузки мусором.

**Правила защиты контекста:**

- **Запрет на передачу сырых данных:** Программному ядру категорически запрещено передавать в ИИ-модель полные HTML-страницы, объемные куски скачанных сайтов или длинные системные логи.
- **Точечная передача:** В ИИ-модель отправляются исключительно: компактные сниппеты результатов поиска, строго отфильтрованные цитаты-доказательства (Evidence), текущее краткое состояние исследования и список зафиксированных пробелов (Research Gaps).
- **Короткие вызовы инструментов:** Каждый вызов инструмента со стороны ИИ через протокол MCP должен быть атомарным (один вызов — одна короткая операция). Запрещено создавать комбайны вида `search_and_read_everything`. ИИ обязан сначала сделать поиск, получить список кандидатов, выбрать точечную ссылку и только затем вызвать инструмент её чтения.

### 6a. Управление бюджетом контекста (TokenBudgetManager)

Система обязана динамически рассчитывать доступный бюджет контекста для каждого вызова LLM, учитывая модель, бэкенд и конфигурацию. Модели, бэкенды и аппаратные условия могут меняться — жёстко фиксировать бюджет контекста в коде запрещено.

**Источники данных о контексте (по приоритету):**

1. **Backend API (best effort):** Если бэкенд отдаёт данные о максимальном контексте — использовать. Не все локальные серверы надёжно отдают это значение.
2. **Конфигурация оператора (обязательный fallback):** Параметры из `ResearchConfig.llm`. Если автоопределение недоступно или сомнительно — использовать значение из конфигурации.
3. **Наблюдаемая статистика:** Фактические `prompt_tokens` / `completion_tokens` из ответов бэкенда для диагностики и калибровки.

**Формула расчёта (по режиму — решение A-12):**

```
mode = fixed:
    effective_context = значение из конфигурации

mode = auto:
    effective_context = backend_reported, если значение надёжно получено;
                        иначе fallback_context_tokens

mode = auto_with_config_cap (рекомендуемый дефолт):
    auto = backend_reported, иначе fallback_context_tokens
    effective_context = min(auto, max_allowed_context_tokens)

usable_prompt = effective_context - output_reserve - safety_margin
```

Дополнительные правила расчёта (A-12):

1. **Неизвестный backend limit ≠ 0:** если бэкенд не отдал значение максимального контекста, оно трактуется как «неизвестно» (используется fallback), а не как 0. Обнуление бюджета контекста из-за отсутствия данных запрещено.
2. **Надёжность значения от backend:** если backend периодически отдаёт противоречивые или недостоверные значения, приоритет отдаётся конфигурации оператора; наблюдаемая статистика (`prompt_tokens`/`completion_tokens`) используется для калибровки.
3. **Отрицательный `evidence_budget` → `CONFIG_CONTEXT_INSUFFICIENT`:** если после вычитания fixed_sections и резервов объём для Evidence отрицательный или нулевой, вызов не выполняется и возвращается `CONFIG_CONTEXT_INSUFFICIENT` с рекомендациями.

**Распределение квот:**

```
fixed_sections = system_prompt + dashboard + working_memory + research_gaps + tool_instructions
evidence_budget = usable_prompt - fixed_sections
```

`evidence_budget` — это объём, доступный для передачи доказательств (Evidence), контекстных чанков (±1) и метаданных источников.

**Режимы работы:**

- **auto:** Автоопределение из бэкенда, fallback на `fallback_context_tokens`.
- **fixed:** Всегда использовать значение из конфигурации (самый предсказуемый режим для MVP).
- **auto_with_config_cap:** Автоопределение, но не выше операторского лимита `max_allowed_context_tokens` (рекомендуемый дефолт).

**Конфигурация:**

```yaml
llm:
  context:
    mode: auto_with_config_cap
    fallback_context_tokens: 4096
    max_allowed_context_tokens: 8192
    output_reserve_tokens: 1024
    safety_margin_tokens: 128
```

**Триггеры пересчёта:**

- Старт приложения / старт Study
- Смена бэкенда / модели / порта / конфигурации сервера
- Переход `HEALTHY → DEGRADED → UNREACHABLE → RESTARTING`
- Восстановление сессии через `SESSION_RESUMING`

**Важное правило:** Если исследование уже идёт, нельзя незаметно поменять правила посреди пути. Текущий эффективный профиль сохраняется в `ResearchSession.budget_state` или `ResearchConfig`. При изменении бэкенда после перезапуска система фиксирует новый профиль и проверяет совместимость.

**Поведение при нехватке контекста:**

1. Сначала уменьшать эластичные части: число Evidence в одном вызове, размер чанков для новых документов, список второстепенных gaps, объём dashboard.
2. Нельзя молча ломать контракт: убирать обязательный контекстный коридор ±1, выбрасывать Evidence без статуса, обрезать отчёт без `REPORT_TRUNCATED_PARTIAL`.
3. Если минимальный контекст не собирается — вернуть `CONFIG_CONTEXT_INSUFFICIENT` с рекомендациями (уменьшить `chunk_size`, увеличить контекст в сервере, выбрать другую модель).

## 7. Отказоустойчивость и сохранение состояния (Resilience)

ИИ-модель и транспортный слой MCP признаются нестабильными компонентами, которые могут зависнуть, выдать ошибку формата или аварийно завершить работу. ИИ не является точкой хранения состояния системы.

**Правила обеспечения живучести:**

- Каждое изменение в ходе исследования (успешный скачанный документ, извлеченное доказательство, списание бюджета, смена фазы автомата) мгновенно записывается ядром Core в базу данных SQLite в режиме WAL с фиксацией транзакции.
- При внезапном падении, таймауте локального ИИ-бэкенда или перезагрузке компьютера программа обязана выполнить процедуру спасения: текущие сетевые задачи ставятся на паузу, накопленный массив данных фиксируется контрольной точкой (Checkpoint).
- После восстановления связи или перезапуска бэкенда система инициирует режим `SESSION_RESUMING`, поднимает из SQLite точный статус исследования и продолжает работу с того места, где произошел сбой, без потери уже собранных материалов.

**Приватная диагностика сбоев (S-06):** по умолчанию система не ведёт телеметрию и не выполняет сетевую отправку crash-report ни при каких обстоятельствах, включая offline-сбои. Диагностика существует исключительно как локальный структурированный журнал.

Правила:

- **Локальный журнал.** Структурированные записи только в локальный файл с ротацией и явным сроком хранения. Срок хранения отображается пользователю; пользователь может удалить диагностические данные в любой момент.
- **Redaction обязательна.** В журнал не попадают: абсолютные пути к приватным файлам, промпты и их фрагменты, текст локальных документов, credentials/токены/API-ключи. Вместо них — обезличенные идентификаторы и категории событий.
- **Никакой сетевой отправки.** Отправка диагностики за пределы машины не является частью штатного поведения системы. Режим `MATERIALS_ONLY` дополнительно гарантирует это физической блокировкой сетевых адаптеров.
- **Диагностический архив — только по действию пользователя.** Формируется по явному запросу, с предварительным preview состава (что именно войдёт в архив) и повторной очисткой на выходе. Автоматическая упаковка и выгрузка архива запрещены.

**Критерий приёмки:** canary-данные (тестовые пути, промпты, текст документа, секреты) не появляются ни в журнале, ни в диагностическом архиве; offline-сбой не инициирует ни одного сетевого запроса; пользователь видит срок хранения и может удалить диагностику.

**Транспорт Watchdog → Core (S-10).** Сигналы Watchdog типизированы и неизменяемы: `WatchdogSignal(event_id, backend_id, observed_state, observed_at, generation)`. Из worker-потока Watchdog выполняет только `loop.call_soon_threadsafe` постановку сигнала в bounded `asyncio.Queue`; прямое обращение к `asyncio.Queue` из чужого потока запрещено. Все FSM-переходы и записи в SQLite выполняет бизнес-обработчик Core; Watchdog не пишет в БД и не выполняет переходы. Транспорт обязан обрабатывать: coalesce одинаковых сигналов, политику переполнения очереди, отбрасывание сигналов с устаревшим `generation` (stale), упорядоченный shutdown/drain.

## 8. Единая конфигурация системы (Configuration Contract)

Все настраиваемые параметры системы консолидируются в единый объект `ResearchConfig`, структура которого обязана быть версионируемой и валидируемой.

**Структура конфигурации:**

```
ResearchConfig:
├── search — параметры поисковых запросов, лимиты выборки
├── retrieval — настройки RetrievalProvider, параметры BM25
├── ranking — веса релевантности и качества
├── deduplication — пороги дедупликации, алгоритмы сходства
├── sufficiency — пороги SufficiencyEvaluator
├── budget — лимиты многомерного бюджета
├── llm — параметры ИИ-бэкенда, контекст, таймауты
├── mcp — настройки MCP-сервера, лимиты вывода
├── sources — конфигурация SourceAdapter, TTL кэша
├── chunking — параметры нарезки, overlap, контекстный коридор
├── reporting — формат отчётов, требования к валидации
└── storage — параметры SQLite, лимиты размера, кэш
```

**Обязательные требования:**

1. Каждый параметр имеет значение по умолчанию (default), задокументированное в ТЗ.
2. Конфигурация проходит обязательную валидацию при загрузке (типы, диапазоны, зависимости между параметрами).
3. Версия конфигурации фиксируется в `ResearchConfig.config_version` для обеспечения воспроизводимости.
4. Изменение конфигурации во время активного исследования допускается только через явный механизм расширения бюджета (см. раздел 6a Раздела 01).
5. Конфигурация сохраняется в SQLite и привязывается к конкретному Study через таблицу `ResearchConfig`.

**Административный диагностический доступ (Q-13, закрыт 2026-09-13).** Привилегированный administrator diagnostic token в MVP **не вводится**. Локальная диагностика работает без специального скрытого доступа. Любой будущий привилегированный или удалённый механизм диагностики вводится отдельным архитектурным решением с полным контрактом: кто выдаёт, кто может использовать, срок действия, область полномочий, хранение, отзыв, аудит. Механизм скрытого административного доступа не создаётся только потому, что он присутствовал в раннем roadmap. Приватная диагностика сбоев (S-06) — §7 настоящего раздела.
