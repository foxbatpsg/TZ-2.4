# Обслуживание индексного слоя ТЗ v2.4

## Назначение

Управление нормативным корпусом ТЗ v2.4 «Research Prompt Suite» (~340 КБ, 14 файлов) через
навигационный слой `INDEX.md`. Индекс существует по одной причине: **корпус достиг объёма, при
котором последовательное чтение неприемлемо**, а адресный поиск без карты приводит к ошибкам —
именно так возник дефект, где ревьюер объявил EPIC-07…11 «отсутствующими», хотя они есть в
`EPIC SPECIFICATIONS v1.0` стр. 168–245.

Скилл решает три задачи:

1. **Найти** норму/сущность/Gate, не читая корпус целиком.
2. **Проверить** корректность ссылок и полноту реестра перед коммитом правки.
3. **Оценить последствия** правки — что ещё затронуто, какие задачи блокируются.

## Когда применять

- Любая правка файлов `01`–`07`, приложений в `приложения к ТЗ/`, `ARCHITECTURE.md`.
- Перед навигацией по корпусу: сначала `INDEX.md`, потом адресное чтение.
- При разрешении противоречий между нормами (например, `A-13` против `EPIC-10`).
- При написании TASK-карточки — чтобы ссылаться на нормы по ID, а не по номерам разделов.
- Перед коммитом: обязателен прогон валидатора.

## Ключевые факты о корпусе

**Система ID норм уже существует и нормативна.** Не изобретать свои идентификаторы.

| Класс | Диапазон | Смысл |
|---|---|---|
| `A-01`…`A-21` | Архитектурные нормы | Утверждённые изменения (УИ) к ТЗ |
| `Q-01`…`Q-08` | Решения по открытым вопросам | Q-08 открыт, Q-06/Q-07 — пропуск нумерации |
| `G-01`…`G-11` | Gate приёмки | Определены в `EPIC SPECIFICATIONS` стр. 26–244 |

**Формат нормативного определения в ТЗ единообразен:**
`Название нормы (A-N): текст правила`

Именно по этому шаблону валидатор отличает **определение** от **упоминания**. Соблюдать его при
добавлении новой нормы обязательно.

## Рабочий процесс

### Шаг 1. Найти норму по индексу

Читать `INDEX.md`, не корпус. Разделы индекса:

| Вопрос | Раздел INDEX.md |
|---|---|
| Где лежит правило? | §3 Реестр норм A-xx |
| Какая норма за что отвечает? | §3 + §4 (Q-xx) |
| Где описана сущность? | §5 Карта сущностей |
| Где Gate? | §6 Карта Gate |
| Какой EPIC? | §7 Карта EPIC |
| Где механизм (pipeline, FSM, бюджет)? | §8 Карта механизмов |
| Известные дефекты | §9 |

Затем читать **только** целевой фрагмент — файл плюс указанную строку.

### Шаг 2. Проверить статус нормы и связанные решения

Ключевое поле реестра — `canonical` (первичный источник). Оно критично, потому что значительная
часть норм определена **несколько раз** в разных файлах с разными акцентами. Зафиксированный
масштаб: `A-03` — 9 определений, `A-11` и `A-16` — по 5, ещё 18 норм — от 2 до 4.

При работе с нормой, у которой больше одного определения:
1. Взять формулировку из `canonical` как основную.
2. Сверить остальные вхождения (`mentions`) на расхождение.
3. Обнаруженное расхождение внести в поле `conflicts` и в §9 индекса.

Не выбирать удобное определение произвольно — это создаёт вторую «истину».

### Шаг 3. Внести правку

Шесть правил, нарушение которых ломает корпус:

1. **Сохранять формат определения** `Название (A-N): текст` — иначе норма выпадет из реестра.
2. **Не менять нормативные ID.** `A-13` остаётся `A-13`. Перенумерация ломает ~90 перекрёстных
   ссылок в приложениях и все TASK-карточки.
3. **Обновлять `INDEX.md` тем же изменением**, что и нормативный текст. Индекс, отставший от
   корпуса, хуже отсутствующего.
4. **Не дублировать текст нормы в индексе.** Индекс хранит адрес и связи (`canonical`, `mentions`,
   `conflicts`, `gates`, `epics`), не формулировку.
5. **Не разрешать противоречие самостоятельно.** При конфликте норм — зафиксировать в §9 и в
   `REVIEW-REGISTRY.md`, затем `STOP → REPORT`.
6. **Правки P0-блокеров** (`N-01` MCP-host, `S-12`/`Q-08` Document identity, `N-02` SourceRelation)
   вносить только после принятия соответствующего ADR. До этого зависимые TASK — `BLOCKED`.

### Шаг 4. Обязательная валидация

Перед завершением работы запустить валидатор:

```bash
python .workbuddy-ai/skills/tz-index-maintenance/scripts/validate_index.py
```

Скрипт проверяет шесть вещей: разрешимость ссылок на файлы, полноту реестра норм, отсутствие
фантомных записей, дубли определений, нормы без определения, покрытие Gate.

**Успех — код возврата 0 и `РЕЗУЛЬТАТ: PASS`.** Предупреждения не блокируют, но требуют проверки
поля `canonical` и внесения подтверждённых расхождений в `conflicts`. Ошибка (код 1) означает, что
индекс и корпус разошлись — правку нельзя считать завершённой.

## Разбор типовых ситуаций

### Добавление новой нормы

1. Выбрать следующий свободный ID в диапазоне (`A-22`, `Q-09`).
2. Сформулировать по шаблону `Название (A-N): текст` в соответствующем разделе ТЗ.
3. Внести запись в `INDEX.md` §3 (или §4): ID, название, `canonical`, `mentions`.
4. Если норма меняет существующее поведение — проверить, не конфликтует ли она с действующими.
5. Прогнать валидатор.

### Пропуск в нумерации

Если идентификатор отсутствует в корпусе намеренно (как `Q-06`/`Q-07`), пометить в `INDEX.md`
значением `status: gap` со ссылкой на запись в §9. Валидатор допускает такие записи через
список `ALLOWED_GAPS`. Молчаливый пропуск недопустим — приоритет имеет явное указание, а не
порядковый номер.

### Норма без определения

Если идентификатор используется, но определения нет — это **дефект корпуса**, а не повод придумать
формулировку. Не спешить классифицировать как «утрату данных»: проверенный случай `A-01` оказался
**дефектом миграции** — правило сохранилось в старых файлах проекта, но при переносе в приложения
было свёрнуто до проекции с потерей источника, обоснования и критерия приёмки.

**Порядок действий:**

1. **Поискать формулировку в старых файлах проекта** (проверенный приём, давший результат для A-01).
   Искать по названию нормы, её теме и по фрагментам применений — не только по идентификатору.
2. Сверить найденный текст с применениями в корпусе: совпадают ли, нет ли противоречий.
3. Если формулировка найдена — зафиксировать в `REVIEW-REGISTRY.md` §D-4 как `RESOLVED`, указав
   диагноз (дефект миграции / утрата данных), потерянные составные части и требуемое действие.
4. Если не найдена — пометить `status: defect` и представить на утверждение человеку.

**Не изобретать нормативный текст.** Восстановленная формулировка вносится в корпус только после
утверждения, и вносится дословно, без редактуры.

**Проверять у восстановленной нормы наличие трёх частей:** источник правила, обоснование,
критерий приёмки. Именно их теряют при свёртке в Change Log — и без них норма становится
непроверяемой.

### Написание TASK-карточки

Ссылаться на нормы по ID: `REQUIREMENTS: A-13, Q-02, N-01`. **Не** по номерам разделов
(`ALLOWED_FILES: Разделы 02 и 05`) — такие ссылки ломаются при любой перенумерации. Для
P0-блокеров указывать `BLOCKED_BY` с идентификатором ADR.

## Границы применимости

- Скилл управляет **нормативным корпусом**. Код приложения, TASK-карточки Astra1 и файлы
  замечаний (`SUGGESTIONS.md`, `замечания GPT6.md`) в область индекса не входят — они производные
  и меняются вслед за нормами.
- `ARCHITECTURE.md` — производный документ, не нормативный. При конфликте приоритет имеет ТЗ.
- Иерархия приоритетов: **ТЗ → State Machine Spec / MCP Tool Contracts / Budget Contract →
  MASTER ROADMAP → EPIC Specifications → ARCHITECTURE.md**.
- Скилл не принимает архитектурных решений. При конфликте норм или неутверждённом ADR —
  `STOP → REPORT`, а не самостоятельное разрешение.

## Справочные материалы

- `references/corpus-map.md` — карта корпуса: назначение каждого файла, области ответственности,
  где какая категория норм живёт. Читать при необходимости понять структуру корпуса.
- `references/canonical-table.md` — зафиксированное соответствие «норма → первичный источник» для
  всех `A-xx` и `Q-xx`. Читать при работе с конкретной нормой.
