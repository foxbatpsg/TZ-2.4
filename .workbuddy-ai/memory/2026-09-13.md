## ⚠ ИНЦИДЕНТ: СЛОМАННЫЙ REF-NAMESPACE В `.git` (важно на будущее)

**Дата:** 2026-09-13. **Push выполнен успешно**, но обнаружился дефект локального репозитория.

### Симптомы
После `git push origin master` команда `git status` показала:
```
On branch master
Your branch is based on 'origin/master', but the upstream is gone.
```
`git branch -vv` → `master 2f03b93 [origin/master: gone]`.

### Диагностика (порядок, который сработал)
1. `git ls-remote --heads origin` → `refs/heads/master` = `2f03b93…` — **remote в порядке, push прошёл**.
2. `git rev-parse HEAD` = `git ls-remote origin refs/heads/master` — **SHA совпадают побайтно**.
3. `git fetch -v origin` → рапортует `* [new branch] master -> origin/master`, **exit 0**, но `git show-ref | grep origin` — пусто.
4. `ls .git/refs/remotes/origin/` → **No such file or directory** — файл ref не создаётся, хотя fetch «успешен».
5. `git update-ref refs/remotes/origin/master <sha>` → **exit 0, но ref не появляется**.

### Корень проблемы
В `.git/refs/` присутствует **посторонний namespace `refs/cline/checkpoints/1788902633788_60tw5/*`** (6 ref-файлов) — следы работы Cline в этом репозитории. ### Решение (сработало)
Обойти git и создать ref-файл напрямую:
```bash
mkdir -p .git/refs/remotes/origin
printf '2f03b93799284f4b7767374dc1d789685d7f7784\n' > .git/refs/remotes/origin/master
```
После этого: `## master...origin/master` без `[gone]`, `git branch -vv` → `[origin/master]`.

- **Не паниковать и не делать повторный push / force-push.** Данные на remote не пострадали.
- Причина, вероятно, в namespace `refs/cline/` — если Cline работал в этом репо, он мог повредить `refs/remotes`. При следующем сбое: проверить `find .git/refs -type d` на посторонние namespace.
- Обходной путь — писать ref-файл вручную (`printf <sha> > .git/refs/remotes/origin/<branch>`). Это безопасно: ref-файл содержит просто SHA.

## `push.bat` — обёртка для Windows (20:47)

**Зачем:** двойной щелчок по `.sh` в Windows не работает — нужен bash. `push.bat` находит bash и прокидывает все аргументы в `push.sh`.

**Использование:** `push` или `push -m "сообщение"` — из любого терминала (PowerShell, cmd) или двойным щелчком.

### Что выяснилось при проверке (важно)

1. **`where bash` НЕ находит `bash.exe`.** В `C:\Program Files\Git\cmd` лежит только `git.exe`, `git-gui.exe`, `gitk.exe` и т.п. — **bash там нет**. Реальный `bash.exe` находится в:
   - `C:\Program Files\Git\bin\bash.exe` (47 КБ — враппер)
   - `C:\Program Files\Git\usr\bin\bash.exe` (2.4 МБ — настоящий)
   Поэтому в батнике сначала идёт `for /f ... in ('where bash')`, а за ним **явные фолбэки** на `%ProgramFiles%\Git\bin`, `usr\bin`, `%ProgramFiles(x86)%`, `%LOCALAPPDATA%`.

2. **CRLF обязателен.** Первая версия `push.bat` была с LF — это ломает `cmd.exe`. После записи файл конвертируется в CRLF (79 пар CRLF, 0 одиночных LF). **При любой правке `.bat` проверять переводы строк:**
   ```bash
   python -c "d=open('push.bat','rb').read(); print('bare LF:', d.count(b'\n')-d.count(b'\r\n'))"
   ```

3. **Валидация батника:** `cmd.exe` из sandbox не запускается (заблокировано). Проверено иначе — выполнена **та же самая команда, что выдаёт батник**:
   ```bash
   "/c/Program Files/Git/bin/bash.exe" "C:/.../push.sh"
   ```
   → exit 0, push отработал, ref починен. Логика батника подтверждена.

## 🔴 КОД 127: `push.bat` ВЫБИРАЛ WSL-BASH ВМЕСТО GIT BASH (решено)

**Симптом:** пользователь запустил `push.bat` → `ОШИБКА: push завершился с кодом 127`.

### Причина — в Windows ТРИ разных `bash.exe`

| Путь | Что это | Годится? |
|---|---|---|
| `C:\Windows\System32\bash.exe` | WSL-лаунчер (127 КБ) | ❌ **НЕТ** |
| `...\AppData\Local\Microsoft\WindowsApps\bash.exe` | WSL-стаб | ❌ **НЕТ** |
| `C:\Program Files\Git\bin\bash.exe` | **Git Bash** (47 КБ) | ✅ **ДА** |
| `C:\Program Files\Git\usr\bin\bash.exe` | настоящий bash (2.4 МБ) | ✅ да |

**`C:\Windows\System32` идёт в PATH раньше Git**, поэтому `where bash` возвращал **WSL-версию**. WSL живёт в отдельной Linux-VM: не видит Windows-пути `C:/...` и git этого репозитория → каждая команда = «not found» → **127**.

Проверено: `"/c/Windows/System32/bash.exe" --version` → выдаёт кракозябры («Этаж в доступе»), а не версию bash. То есть это не bash в обычном смысле.

### ⛔ КРИТИЧНО: НЕ использовать `where bash` для поиска bash

**Правило проекта:** в батниках искать bash **только по явным путям Git for Windows**, начиная с `%ProgramFiles%\Git\bin\bash.exe`. `where bash` — лишь последний шанс, и обязательно с фильтром:
```bat
echo %%i | findstr /i /c:"\\System32\\" /c:"\\WindowsApps\\" >nul
if errorlevel 1 set "BASH=%%i"
```

### Что исправлено

**`push.bat`:**
- порядок изменён: сначала явные пути Git, `where bash` — в конце с фильтром
- в шапку выводится выбранный bash (`bash: C:\Program Files\Git\bin\bash.exe`) — сразу видно, что подхватилось
- код 127 расшифровывается в тексте ошибки
- CRLF: **104 пары, 0 одиночных LF**

**`push.sh`** (устойчивость):
- guard: отказ с внятным сообщением при запуске через WSL-bash (проверка `uname -s` + `WSL_DISTRO_NAME` + `/proc/version`)
- проверка `command -v git` до начала работы
- проверка, что ветка определилась (detached HEAD → ошибка, а не `git push origin `)
- **убран `awk`**: SHA из `git ls-remote` теперь берётся параметрным развёртыванием `${REMOTE_LINE%%[[:space:]]*}` — меньше зависимостей

### Найденный попутно баг
При пустом `BRANCH` старый `push.sh` молча выполнял `git push origin ` — без имени ветки. Теперь это явная ошибка.

### Итог

**Push прошёл:** `9c2f865..e917977` → GitHub. Локально и на remote `e917977`, непушнутых коммитов нет.

На remote проверено наличие: `AGENTS.md` ✓, `push.bat` ✓, `push.sh` ✓.

**Окружение:** команды `cmd.exe` и запуск shell из PowerShell **заблокированы sandbox** — `push.bat` напрямую протестировать нельзя. Проверка делалась иначе: выполнялась та же команда, что выдаёт батник (`"C:\Program Files\Git\bin\bash.exe" "<abs>/push.sh"`), плюс `bash -n` для синтаксиса.
