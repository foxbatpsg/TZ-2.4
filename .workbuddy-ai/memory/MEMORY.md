## Формат общения с пользователем (задано 2026-09-13)

1. **Отчёты о выполнении — короткие.** Пользователю достаточно: шаг прошёл нормально / были затруднения. Развёрнутое изложение — только по отдельной просьбе («разверни»).
2. **Вопросы — нумерованные.** Если вопросов много — выносить в отдельный файл, а не в чат.
3. **К каждому вопросу — варианты решения.** Не задавать вопрос без предложенных вариантов.
4. **Порядок ответа:** сначала краткий отчёт, потом вопросы. Вопросы — в конце.
5. **Вопрос должен быть понятен без доступа к структуре корпуса.** Пользователь не «ворочает» 14 файлов — он не видит фрагмента, о котором речь. Формулировать через суть, а не через номера разделов; при необходимости показывать сам фрагмент.
6. **Не перестраховываться.** Не чинить и не «улучшать» то, что работает. Сообщать о реальных нестыковках и ошибках — да; предлагать переделку без нужды — нет.
7. **Варианты ответов нумеровать цифрами** (1, 2, 3), не буквами. (Задано 2026-09-13.)
8. ⛔ **КРИТИЧНО (задано 2026-09-14): до указания пользователем номера варианта — в файлы НИЧЕГО не писать.** Вопрос задан → ассистент пишет текстовый ответ и **останавливается**. Никаких норм, формулировок, «предварительных» редакций, догадок «на опережение» и переходов к следующей позиции. Решение о закрытии вопроса принимает **только пользователь**. Рекомендация ассистента ≠ решение.
9. ⛔ **Вопрос формулировать так, чтобы ответ нельзя было истолковать двояко.** Один вопрос = один выбор; варианты не пересекаются; внутри одного пункта не допускаются «или», «в том числе», «как вариант». Если решений два — два отдельных пронумерованных вопроса.
10. ⛔ **Пока вопрос открыт — следующую позицию блока C не начинать.**
11. ⛔ **КРИТИЧНО (задано 2026-09-14): перед любым вопросом «нужно ли что-то внести/добавить/изменить» — сначала поиск по ТЕКСТУ корпуса, потом вопрос.** Запрещено строить варианты ответа на общем смысле термина («это похоже на артефакт кода»). Порядок: `grep -rn "<термин>" --include="*.md" .` по нормативным файлам и приложениям → определить качество каждого вхождения (норма / критерий Gate / задача `E0x-Tyy` / позиция реестра `S-xx` / упоминание внутри другого замечания / производный документ) → **внести таблицу «где встречается / что это / статус» в сам вопрос**. Пользователь не видит корпус и не может проверить полноту — достоверность вопроса отвечает ассистент. Признак нарушения: в вопросе рассуждение о смысле есть, результата поиска нет. ## Редакционные правила корпуса (задано 2026-09-13)

1. **Не дублировать нормативные тексты.** Формулировка нормы живёт в **одном** месте — первичном источнике (`canonical`). Реестры и индексы хранят адрес и краткое содержание, не текст. Это прямое следствие борьбы с дефектом D-4 (21 норма определена по 2–9 раз с расхождениями).
2. **Не дробить файлы без крайней необходимости.** Новый файл — только при явной пользе; предпочтение существующей структуре.
3. **Реестр «УИ v1.0» (`MASTER ROADMAP v1.2` §21):** §21.1 — полное определение `A-01`; §21.2 — адресная таблица `A-02…A-21`, `Q-01…Q-05`. Решение пользователя (2026-09-13): **оставить как есть** (вариант «указатель»).

## Соглашения по git

- `.workbuddy-ai/skills/` версионируется вместе с проектом (не в `.gitignore`) — проектные скиллы едут в репозиторий.
- Отправка — через `push.bat` (двойной щелчок или `push -m "..."`). Из bash: `bash push.sh`.
- ⛔ **Не использовать `where bash`** для поиска интерпретатора: `C:\Windows\System32\bash.exe` — это WSL-лаунчер, он даёт код 127. Нужен только `C:\Program Files\Git\bin\bash.exe`.
- При правке `.bat` проверять CRLF: `python -c "d=open('push.bat','rb').read(); print('bare LF:', d.count(b'\n')-d.count(b'\r\n'))"`.
- `git status` с `[gone]` **не означает**, что push не прошёл — сначала сверить `git ls-remote origin refs/heads/master` с `git rev-parse HEAD`. Дефект локального ref-хранилища (следы namespace `refs/cline/`) лечится записью `printf '<sha>\n' > .git/refs/remotes/origin/master`.
- `prompt.txt` в корне — черновик затравки, осознанно **не** в git.

- `AGENTS.md` в корне — универсальная точка входа (читают OpenCode, Cline, Cursor, WorkBuddy).

Постоянных предупреждений теперь **три** (21 норма с дублями определений; `Q-08` без определения; `Q-13` — решение, а не определение) — задокументированы в `INDEX.md` §9, не считать регрессом.
- ⚠ **`INDEX.md` парсится регулярками, а не разметкой.** Валидатор извлекает ID через `\b([AQ]-\d{2})\b` и имена файлов через `` `([^`]+\.md)` `` по **всему тексту файла**, включая прозу и таблицы. Следствие: любое упоминание ID (`Q-09` и т.п.) в пояснительном тексте создаёт **фантомную норму**, а любое имя `.md` файла вне корня — **неразрешимую ссылку** (FAIL). Писать прозу индекса без литеральных ID и без имён файлов; для «пропуска нумерации» формулировать словами («решения с номерами между `Q-05` и `Q-13` отсутствуют» — но это опять ID!). Правильно: называть только существующие ID и не вводить новые.
