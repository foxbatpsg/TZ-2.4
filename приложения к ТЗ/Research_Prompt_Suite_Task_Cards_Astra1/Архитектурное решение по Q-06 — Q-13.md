# Архитектурное решение по Q-06 — Q-13

**Проект:** Research Prompt Suite  
**Дата:** 2026-09-09  
**Статус:** предложение архитектора для утверждения

## Q-06 — Контекст Evidence через MCP

**Решение: Вариант A.**

Не вводить отдельный «теневой» 24-й tool. Расширить существующий `search_within_document`.

Добавить опцию:

`include_evidence_context: boolean`

Рекомендуемый default: `true`.

При включении контекста MCP обязан возвращать:
- идентификатор и версию документа;
- основной chunk и соседние chunks коридора ±1;
- ID соседних chunks;
- offsets `[char_start, char_end)`;
- точный текст соответствующих фрагментов.

Лимит ответа должен быть увеличен настолько, чтобы гарантированно вместить требуемый коридор. Черновые 32 KiB можно принять как стартовое значение, но окончательный лимит должен быть подтверждён тестами.

`save_study_material` не должен использоваться как механизм передачи полного Evidence Context.

**Причина:** это сохраняет существующую MCP-поверхность, не создаёт скрытого интерфейса и делает получение доказательного контекста явной частью контракта `search_within_document`.

**Статус:** утвердить как A; точный лимит определить тестами.

## Q-07 — Provenance локальных Evidence

**Решение: Вариант A.**

Ввести специальный тип `SearchTask`:

`purpose = local_analysis`

Core создаёт такую задачу при обработке локального материала. Локальные Evidence получают настоящий `task_id`, а не фиктивный сетевой идентификатор.

Provenance локального Evidence должен хранить:
- `file_ref`;
- `content_hash`;
- координаты/чанки исходного материала;
- другие необходимые локальные идентификаторы.

Нельзя создавать фиктивные URL/DOI/PMID.

`add_local_document` и `save_study_material` должны получать `task_id` от Core.

**Причина:** сохраняется инвариант `Evidence.task_id NOT NULL`, а происхождение локальных доказательств становится таким же формальным и трассируемым, как у внешних.

**Статус:** утвердить A.

## Q-08 — URL idempotency и обновление документов

**Решение: Вариант A, с уточнением.**

Идемпотентность не должна означать вечную неизменность URL.

Принять:
- idempotency window = **24 часа после последнего успешного чтения** как начальное production-значение;
- внутри окна повторное чтение возвращает существующую версию;
- после окна разрешается новое получение;
- `read_url_content(refresh=true)` является явным механизмом принудительного обновления.

Новые версии Document не уничтожают старые.

Критически важно:

**Evidence фиксирует конкретную версию Document.**

Следовательно:
- уже использованная Evidence версия не изменяется;
- EXPAND и новые операции могут использовать последнюю доступную версию;
- если `refresh` получает тот же `content_hash`, новая содержательная версия не создаётся.

Я бы **не вводил отдельный `refresh` tool**. Флаг `refresh=true` в существующем `read_url_content` лучше сохраняет MCP-поверхность.

**Статус:** утвердить A; 24 часа принять как baseline с возможностью изменения конфигурацией.

## Q-09 — Верификация авторов и статистика

**Решение:** принять консервативную модель.

Авторская идентичность должна быть **platform-scoped**.

То есть одинаковое имя/ник на разных площадках автоматически не означает одного человека.

Объединение возможно только при наличии явного надёжного связывающего идентификатора.

`UNKNOWN` и неверифицированные авторы:
- не считаются верифицированными;
- не увеличивают знаменатель статистики;
- не закрывают минимальный порог выборки.

Для процентных показателей знаменатель — **количество верифицированных авторов**, если конкретная метрика действительно является author-based.

Начальные production-пороги:

- ≥5 верифицированных авторов;
- ≥10 отзывов.

При меньшей выборке система может показывать данные, но итоговый статистический вывод должен быть помечен как статистически недостаточный.

Анонимные и стимулированные отзывы не смешивать с обычной выборкой без явной маркировки.

### Важнейшее правило anomaly detection

Аномальный всплеск — это **сигнал**, а не доказательство накрутки.

Система не должна формулировать «накрутка доказана» на основании одной статистической эвристики.

**Статус:** принять архитектурный принцип. Численные пороги 5/10 можно зафиксировать как baseline и впоследствии изменить только отдельным решением.

## Q-10 — Утечка приватных данных во внешний поиск

**Решение: Вариант A.**

Все локальные материалы считать **PRIVATE по умолчанию**.

Ввести policy:

`PUBLIC_ONLY` — внешний поиск разрешён только для явно публичного контекста.

`PRIVATE_ALLOWED` — внешний поиск с использованием локального контекста разрешён только после явного разрешения пользователя.

`MATERIALS_ONLY` — сеть физически запрещена.

Core должен проверять query перед egress. Если запрос содержит фрагмент локального материала, а policy не разрешает его передачу, запрос блокируется.

Секреты и credentials никогда не попадают в:
- logs;
- report;
- внешний query.

**Статус:** принять A.

Это не просто privacy feature, а архитектурный security invariant.

## Q-11 — Transfer Study и rollback snapshot

**Решение: Вариант A с одним уточнением.**

По умолчанию:

**Transfer = COPY.**

Исходный Study сохраняется.

Новый Study получает новые идентификаторы, а операция ведёт явный mapping:

`old_id → new_id`

Глобальные Document не должны бессмысленно дублироваться. Связи `StudyDocumentLink` создаются заново.

Transfer запрещается при наличии незавершённой активной Session.

Перенос между несовместимыми версиями схемы/конфигурации запрещён без предварительной миграции.

### Rollback

Не делать произвольный пользовательский rollback отдельных частей Study.

Основной rollback — через согласованный backup/restore.

Audit history не должна разрушаться.

Допускается безопасный rollback чистого `DRAFT`, если он ещё не содержит Evidence/LogRecord, но это должно быть явно определённое состояние.

**Статус:** принять A.

`MOVE` не включать в MVP.

## Q-12 — Windows environment и performance acceptance

**Решение:** разделить **environment baseline** и **performance acceptance**.

Начальная release matrix:

| Параметр | Minimum | Recommended |
|---|---|---|
| Windows | 10 22H2 x64 | Windows 11 x64 |
| RAM | 16 GB | 32 GB |
| Disk free | 20 GB | 50 GB |
| CPU | x64, 4 cores, AVX2 | 8 cores, AVX2 |
| GPU | не требуется | не требуется |
| LLM | 12B Q4/Q5 | 14B Q4/Q5 |

Начальные performance targets:

- запуск GUI ≤ 5 с;
- реакция UI ≤ 100 мс;
- сигнал cooperative cancel ≤ 1 с.

Для LLM generation, retrieval и DB операции нужны **отдельные измеряемые бюджеты**, а не единая цифра.

Критически важно:

**benchmark ≠ acceptance.**

Benchmark harness можно создать заранее, но performance Gate нельзя считать PASS, пока не определены измеримые критерии и не проведены тесты на заявленной release matrix.

**Статус:** принять матрицу как baseline; окончательные performance budgets закрепить отдельным решением после измерений.

## Q-13 — Administrator Diagnostic Token

**Решение: Вариант A.**

**Не вводить privileged administrator diagnostic token в MVP.**

Обычная локальная диагностика должна работать без специального скрытого доступа.

Если в будущем появится реальная необходимость в удалённой/привилегированной диагностике, это должно быть отдельным архитектурным решением с полноценным контрактом:
- кто выдаёт;
- кто может использовать;
- срок действия;
- область полномочий;
- хранение;
- отзыв;
- аудит.

Нельзя самостоятельно создавать механизм скрытого административного доступа только потому, что его предусматривал ранний roadmap.

**Статус:** принять A и убрать diagnostic token из MVP.

### Архитектурный принцип

Ни одно из этих решений не должно реализовываться «по смыслу» локальным CODE-агентом до появления утверждённого контракта.

После утверждения Q-06…Q-13 необходимо:

1. перевести черновик решений в нормативную версию;
2. обновить затронутые разделы ТЗ;
3. обновить `MCP TOOL CONTRACTS`;
4. обновить State Machine / Core contracts там, где появились новые состояния или ограничения;
5. обновить соответствующие `EPIC → TASK`;
6. только после этого снимать соответствующие блокировки Gates.

До этого существующие стабильные части можно продолжать разрабатывать параллельно, как прямо предусмотрено журналом.
