## 2. Q-06 — MCP не передаёт обязательный контекст извлечения Evidence

**Проблема:** `search_within_document` не гарантирует LLM полный контекстный коридор ±1 (соседние чанки, offsets, ID соседей). `save_study_material` ограничен 4 KiB; ответа 8 KiB может не хватить для коридора. Запрещено молча добавлять скрытый 24-й tool.

**Предложение (вариант A, рекомендуемый):**
- Расширить контракт `search_within_document`: добавить read-опцию `include_evidence_context: boolean` (default `true`), гарантированный вывод: версия документа, номера/ID соседних чанков, отрезки `[char_start, char_end)` основного и соседних чанков, точный текст.
- Пересмотреть лимиты: для `search_within_document` с контекстом — ответ, достаточный для коридора (черновик: 32 KiB), для `save_study_material` — 4 KiB остаётся как ограничение на метаданные (без претензии нести полный коридор).
- LLM не вводит «теневой» tool: весь доступ — через заявленные контрактные tool-ы.

**Вариант B (альтернатива):** зарегистрировать официальный 24-й tool (`search_within_document_context`). Требует явного решения, т.к. расширяет публичную поверхность MCP.

**Что нужно утвердить:** вариант A или B; точные лимиты; является ли коридор обязательным в каждом ответе или по запросу.

**Не блокируется:** локальная сборка и валидация коридора в Core; пред-извлечённые Evidence ±0; всё, что не требует передачи контекста через MCP.

**Затрагиваются:** `MCP TOOL CONTRACTS v1.2` (§3 `search_within_document`, §5 `save_study_material`), `04_Search Core.md` §15, `05_Взаимодействие с LLM и протокол MCP.md`.

## 3. Q-07 — Provenance локальных Evidence (task_id)

**Проблема:** `Evidence.task_id NOT NULL`, но `save_study_material` / `add_local_document` не дают task_id. Не к чему привязать локальные Evidence. Недопустимо подставлять фиктивный сетевой task_id.

**Предложение (вариант A, рекомендуемый):**
- Ввести «локальную аналитическую SearchTask»: task с типом/purpose=`local_analysis`, создаваемая Core при локальном импорте/сохранении; на неё ссылаются локальные Evidence. Provenance: внутренний source reference (`file_ref`, `content_hash`, координаты), без выдуманных URL/DOI/PMID (см. A-17).
- `add_local_document`/`save_study_material` получают этот `task_id` из Core и сохраняют связь.

**Вариант B:** ослабить схему (`task_id` NULLABLE) с запретом на удаление локальных материалов, подтверждённых Evidence.

**Что нужно утвердить:** вариант A или B; признак «локальности» в схеме (отдельная колонка/тип задачи).

**Не блокируется:** импорт, индексирование, локальный поиск (BM25), MATERIALS_ONLY — реализуемы заранее.

**Затрагиваются:** `03_Модель данных и хранение.md` §6 (SearchTask), §13 (Evidence), `MCP TOOL CONTRACTS v1.2` (§4 `add_local_document`, §5 `save_study_material`).

## 4. Q-08 — URL-idempotency блокирует обновление документов

**Проблема:** идемпотентность `SHA256(canonical_url)` возвращает старый Document при повторном чтении, но TTL/`EXPIRED`/`FORCED_REFRESH` (ТЗ §25) требуют обновлять данные; EXPAND поднимает прошлые Study.

**Предложение (вариант A, рекомендуемый):**
- Срок действия idempotency — **window** (черновик: 24 часа с момента последнего успешного чтения). Внутри окна повтор → существующая версия. После окна — разрешена новая fetch-операция.
- Явная операция **revision/refresh**: `read_url_content(refresh=true)` (Core-approved) создаёт новую версию Document; старые версии не удаляются.
- Правила выбора версии:
  - Study «замораживает» версию Document, на которую уже сослался Evidence (неизменяемость из A-21);
  - EXPAND и новые материалы используют последнюю доступную версию;
  - кэш: `FORCED_REFRESH` допускает один идентичный контент (content_hash совпадает → новая версия не создаётся, обновляется только кэш-запись).

**Вариант B (безопасный минимум):** обновление только для URL, на которые нет Evidence; для остальных — перечитать не допускается.

**Что нужно утвердить:** длительность окна; поведение refresh при использованных в Evidence URL; отдельная команда `refresh` или флаг в `read_url_content`.

**Не блокируется:** первое чтение; повтор той же операции (стабильность); работа с новыми URL.

**Затрагиваются:** `MCP TOOL CONTRACTS v1.2` (`read_url_content`), `04_Search Core.md` §25 (Cache), `03_Модель данных и хранение.md` §9 (версии Document).

## 5. Q-09 — Верификация авторов и статистическая выборка

**Проблема:** не определено доказательство «reviewer_id = уникальный человек», объединение одного человека между площадками, знаменатель процентов, минимальная выборка, обращение с анонимными/стимулированными отзывами, критерии аномального всплеска и маркировки накрутки.

**Предложение (на основе рекомендаций журнала):**
- `platform-scoped author identity`: identity уникален в пределах площадки; объединение между площадками — только через явный user-binding (e-mail/аккаунт), иначе считаются разными.
- `UNKNOWN`/неверифицированный автор **не входит** в знаменатель и не закрывает минимум авторов.
- Знаменатель процентных показателей = **количество верифицированных авторов** (не количество отзывов и не URL).
- Минимальная выборка для итоговых стат. выводов (черновик): не менее 5 верифицированных авторов и не менее 10 отзывов; ниже — запрос считается статистически неубедительным и помечается.
- Анонимные отзывы — отдельно, не смешивать; стимулированные — обязательная маркировка.
- Anomaly policy: всплеск — статистический сигнал, но **не «доказательство накрутки»**; маркировка накрутки — только при верифицированном признаке (совпадение source, времени, содержимого сверх порога).

**Что нужно утвердить:** конкретные числа (мин. выборка); трактовку анонимных и стимулированных; формулировку anomaly policy.

**Не блокируется:** схема, извлечение, агрегатор на явно верифицированных фикстурах.

**Затрагиваются:** `01_Research Analysis Layer.md` §4.1/§4.2/§7, `04_Search Core.md` §16/§16a (CanonicalReview, QA Aggregation), `07_QA_Acceptance.md` §10.

## 6. Q-10 — Приватные данные могут утечь через поисковые запросы

**Проблема:** локальная LLM может включить приватный фрагмент в `recommended_query`, после чего Core отправит его внешнему поисковому сервису.

**Предложение (вариант A, рекомендуемый):**
- Классификация данных: все локальные материалы считаются **приватными по умолчанию**.
- Модель разрешений на egress: на уровне `ResearchConfig`/`InputConfig` — политика `PUBLIC_ONLY` (по умолчанию) или `PRIVATE_ALLOWED` (только по явному действию пользователя). `MATERIALS_ONLY` = физически блокирует сеть полностью.
- Core не отправляет внешнему сервису запрос, если в query присутствует непомеченный фрагмент локальных материалов (verify по content_hash) и политика не разрешает egress.
- Секреты (credentials/tokens) не выводятся в logs/report. Отчет содержит только пометку происхождения (локальный/внешний).

**Вариант B:** полностью запретить внешний fetch при любом локальном контексте (жёстко), упрощённый вариант без override.

**Что нужно утвердить:** политика по умолчанию; наличие/отсутствие пользовательского override; способ пометки «явно публичный вход».

**Не блокируется:** MATERIALS_ONLY; поиск по явно публичному входу; локальная обработка.

**Затрагиваются:** `02_Архитектура и системные принципы.md` (безопасность/egress), `04_Search Core.md` §21, `05_Взаимодействие с LLM и протокол MCP.md`.

## 7. Q-11 — Перенос Study и откат snapshot не специфицированы

**Проблема:** не определены copy/move, поведение исходного Study, remap ID, обращение к активным сессиям, конфликт версий конфигурации/схемы, что разрешено откатывать без разрушения audit history.

**Предложение (вариант A, рекомендуемый):**
- **Transfer = copy**: исходный Study остаётся (или помечается `ARCHIVED`), копия — новый Study; `move` требует отдельного включения и только при отсутствии активных сессий.
- Remap ID — через явный mapping (old_id → new_id) внутри одной операции; общие Document (глобальные) не дублируются (см. A-08/A-09), StudyDocumentLink пересоздаётся.
- Активные сессии: при переносе запрещены (transfer блокируется, если есть незавершённая session).
- Конфликт версий схемы/конфигурации: перенос разрешён только при совместимости; иначе — отдельная миграция, без «на лету».
- **Rollback**: только на уровне backup/restore целого каталога БД (snapshot manifest, Q-01 reconciliation); пользовательский rollback на частичную точку (пере-запись отдельных Study) запрещён, если это разрушает audit history. Допустимо: откат «черновика» Study (DRAFT, без Evidence/LogRecord), остальное — через явную команду с проверкой.

**Вариант B:** поддержать `move` как первый класс, с обязательным подтверждением.

**Что нужно утвердить:** copy vs move; судьба исходного Study (оставлять или архивировать); границы пользовательского отката.

**Не блокируется:** создание backup и проверка восстановления в отдельный каталог.

**Затрагиваются:** `06_GUI_UX.md` §§12–13 (Research Snapshots, Projects), `03_Модель данных и хранение.md` (§ audit/history и связей Study/Document), `04_Search Core.md` (если перенос влияет на индексы).

## 8. Q-12 — Целевая Windows-среда и performance acceptance

**Проблема:** не заданы Windows versions, RAM, свободный диск, CPU baseline, модель/квантование и допустимые задержки GUI, отмены и генерации.

**Предложение (черновик матрицы — числа требуют утверждения):**

| Параметр | Минимум | Рекомендуемая |
|---|---|---|
| Windows | 10 22H2 x64, 11 23H2 x64 | 11 23H2+ x64 |
| RAM | 16 GB | 32 GB |
| Свободный диск | 20 GB | 50 GB |
| CPU | x64, 4 ядра, AVX2 | 8 ядер, AVX2 |
| GPU | не обязателен | — |
| Модель LLM | 12B Q4/Q5  | 14B Q4/Q5 |

Performance budgets (черновик): старт GUI ≤ 5 с; отклик UI на событие ≤ 100 мс; кооперативная отмена — сигнал об отмене ≤ 1 с; генерация/обработка — отдельные бюджеты по типу операции; поиск очень чувствителен к диску — отдельный budget ТБД.

**Что нужно утвердить:** точные числа матрицы и budgets; считать ли производительность объявленной без платформенных тестов.

**Не блокируется:** подготовка benchmark harness (но без численных критериев приёмка невозможна — журнал Q-12).

**Затрагиваются:** `02_Архитектура и системные принципы.md`, `06_GUI_UX.md`, `07_QA_Acceptance.md` §§25–26, `MASTER DEVELOPMENT ROADMAP v1.2` (G-10/G-11).

## 9. Q-13 — Administrator diagnostic token не имеет контракта

**Проблема:** Roadmap EPIC-11 упоминает administrator diagnostic token, но не определены назначение, полномочия, TTL, выдача, хранение и отзыв.

**Предложение (вариант A, рекомендуемый — соответствует журналу):**
- **Токен не вводить.** Обычная локальная диагностика реализуется без привилегированного доступа (логи, health-проверки, cache-диагностика через штатные read-only API).
- Запрет на скрытый привилегированный доступ в коде. Если в будущем потребуется повышенный доступ — только отдельный утверждённый контракт (назначение, полномочия, TTL, выдача, хранение, отзыв) и отдельная карточка.

**Вариант B:** полный контракт токена (требует детальной проработки, считается нежелательным для локального приложения).

**Что нужно утвердить:** вариант A или B. При A — удалить/пометить пункт в Roadmap EPIC-11 как «не предусмотрено».

**Не блокируется:** локальная диагностика, health-мониторинг, cache-статистика — всё без токена.

**Затрагиваются:** `MASTER DEVELOPMENT ROADMAP v1.2` §EPIC-11, `02_Архитектура и системные принципы.md` (безопасность).
