# Журнал исправлений и вопросов

Проект: Research Prompt Suite.
Основание: TZ24обьединенное.md, ТЗ v2.4, State Machine Specification v1.1,
MCP Tool Contracts v1.1, MASTER DEVELOPMENT ROADMAP v1.2.

Статус: результат архитектурного аудита и планирования.
Исправления ниже приняты для этой декомпозиции, но исходное ТЗ не изменено.
Критические вопросы требуют решения владельца требований до реализации
соответствующего поведения.

## 1. Правила исполнения карточек

### 1.1. Граница планирования

Текущий запрос разрешает подготовить карточки всех эпиков заранее.
Это не разрешение параллельно реализовывать все эпики и не отмена Gates.

Одновременно исполняется один эпик.
Следующий эпик запускается после прохождения предыдущего Gate.
Техническая независимость компонентов не равна разрешению обходить Gate.

Идентификаторы E01-C01 и аналогичные принадлежат этой декомпозиции.
Они не заменяют автоматически идентификаторы существующего BASELINE.

### 1.2. Общий Definition of Done: DOD-ALL

Каждая карточка считается выполненной только при одновременном выполнении:
1. Реализация находится в разрешённой области изменений.
2. Написаны все перечисленные unit-тесты, включая отрицательные сценарии.
3. Тесты проходят в изолированной среде без Интернета и реальной LLM.
4. Для SQLite, транспорта, потоков и файловых операций пройдены также
   component/integration tests: одних моков недостаточно.
5. Есть acceptance-проверка заявленного результата.
6. Пройдена регрессия ранее принятых компонентов.
7. Нет скрытого обхода Core, FSM, DB Writer и правил изоляции.
8. Обновлена документация интерфейса.
9. Подготовлен Evidence Bundle: commit, изменённые файлы, команды запуска,
   результаты тестов, версии среды и фикстур, известные ограничения.
10. Результат прошёл review и зарегистрирован Orchestrator.

Наличие тестовых файлов без успешного запуска не удовлетворяет DoD.
SKIP/XFAIL обязательного сценария не считается PASS.
Высокий процент coverage не заменяет проверку инвариантов.
Gate-задачи не заменяют тесты в каждой implementation-задаче.

### 1.3. Контекст автономного агента

Перед выдачей карточки Orchestrator прикладывает:
- саму карточку;
- только применимые разделы контрактов;
- относящиеся к ней решения A-xx и вопросы Q-xx;
- точные ALLOWED_FILES из фактического репозитория;
- FORBIDDEN: соседние модули, публичные контракты и схемы вне карточки;
- команды проверки и критерии завершения.

Репозиторий не предоставлен: названия компонентов ниже являются логическими
границами, а не утверждением о существующих путях.

Проблема вне области карточки: OUT_OF_SCOPE, фиксация, передача архитектору.
Агент не исправляет соседний код самостоятельно.

## 2. Принятые инженерные исправления

### A-01. Редакционные ошибки Roadmap и граф зависимостей

Источник: Roadmap, заголовок, §7, §15, Change Log.

Решение:
- Версия Roadmap в шапке: 1.2, а не 1.1.
- Пропуски пунктов 8 и 10 в Search Core не означают отсутствующие требования.
  Карточки привязаны к названиям подэтапов, а не к ошибочной нумерации.
- Удалить техническое ребро EPIC-05 → EPIC-06:
  Change Log и строка зависимостей EPIC-06 явно разрешают независимый backend.
- Последовательность выдачи эпиков при этом остаётся gated.

Проверка: граф ацикличен; заявленные зависимости и обратные связи согласованы.

### A-02. Формальные FSM имеют приоритет над иллюстративными цепочками

Источник: Раздел 1 §2.3; нормативное приложение FSM.

Решение:
- SOFT_STOP, HARD_STOP, CANCEL, PAUSE, RESUME являются командами.
- PARTIAL_REPORT и REPORT_TRUNCATED_PARTIAL являются признаками результата.
- LLM_UNAVAILABLE и SESSION_RESUMING принадлежат ResearchSession.
- Временная недоступность LLM сама по себе не меняет Study.status.
- Watchdog формирует события. Бизнес-переходы выполняет Core.
- Runtime-переходы backend не дают Watchdog права прямой записи в SQLite.

Проверка: команды невозможно записать в status бизнес-сущностей.

### A-03. Нормализованная модель вместо списков в TEXT/JSON

Источник: Раздел 3, общие правила и конкретные схемы.

Противоречие: Entity.aliases, Intent-параметры, identifiers и numeric_signatures
описаны как списки, хотя отношения и фильтруемые данные должны быть реляционными.

Решение:
- EntityAlias, IntentEntity, IntentInformationNeed, IntentConstraint,
  IntentSourcePreference, IntentOutputRequirement.
- SourceIdentifier и SearchResultIdentifier для DOI/PMID/arXiv.
- ChunkNumericSignature для чисел, единиц, типов и позиции.
- BudgetLimit, BudgetCounter, BudgetReservation/BudgetLedger для учёта.
- SufficiencyMetric и SufficiencyRuleHit для аудита решений.
- ResearchState хранит операционные скаляры и checkpoint;
  списки задач, документов и gaps восстанавливаются JOIN-запросами.
- JSON остаётся сериализацией API или справочным snapshot в metadata/config,
  но не параллельным источником истины для отношений и счётчиков.

Проверка: фильтрация и JOIN не требуют разбора сериализованных списков.

### A-04. Область уникальности соответствует области владения

Источник: SearchTask.query_fingerprint, Evidence.evidence_hash, изоляция Study.

Решение:
- Уникальность поискового fingerprint ограничена Study.
- Уникальность Evidence не должна запрещать одинаковую цитату в другом Study.
- Ключи идемпотентности включают тип операции и область Project/Study.
- Идемпотентность сущности отделена от регистрации новой попытки вызова.

Проверка: повтор внутри Study не создаёт дубль;
тот же запрос или доказательство в другом Study не раскрывает чужие данные.

### A-05. Дедупликация Evidence не может опираться только на target_chunk_id

Источник: Раздел 3 §§12–13.

Проблема: одинаковая цитата в перекрытии двух targets получает разные
evidence_hash, потому что target_chunk_id включён в хэш.

Решение:
- Сохранить контрактный evidence_hash для совместимости.
- Добавить каноническую идентичность цитаты:
  Study + неизменяемая версия Document + char_start + char_end + точный текст.
- Перед проверкой evidence_hash искать уже существующую цитату по позиции.
- Повтор возвращает существующий Evidence.
- Историю разных извлечений и использованных контекстов хранить отдельно,
  не перезаписывая происхождение первого извлечения.
- Одинаковый текст в разных местах документа не считать одной цитатой
  только из-за совпадения текста.

Проверка: одна цитата из двух overlap-targets учитывается один раз.

### A-06. Overlap обрабатывается по интервалам, а не только по флагу

Источник: Раздел 3 §12; Раздел 4 §15.1.

Решение:
- Позиции задаются как полуоткрытые интервалы Unicode-символов [start, end).
- Склейка контекста использует интервалы исходного Document.content.
- overlap_group_id служит вспомогательным признаком.
- is_overlap не является основанием удалить весь чанк из анализа:
  его неперекрывающаяся часть может содержать новые наблюдения.
- Контекст ±1 включает существующих соседей; на краю документа
  отсутствующий сосед не считается ошибкой.

Проверка: одинаковые фрагменты не удваиваются, уникальные окончания не теряются.

### A-07. Текст чанка и стабильные идентификаторы

Источник: Roadmap EPIC-02; Раздел 3 DocumentChunk.

Решение:
- Использовать DocumentChunk.text, а не несуществующее content.
- Стабильный chunk_id формировать как детерминированный UUID
  из document identity, версии chunker и позиции.
- Отдельный полный SHA256 допустим для проверки содержимого.
- Поисковый нормализованный текст не заменяет исходный текст цитирования.

Проверка: одинаковый вход и версия дают одинаковые ID;
изменение версии разбиения не повреждает старую доказательную базу.

### A-08. Один Document может иметь несколько происхождений

Источник: Document.content_hash UNIQUE и единственный Document.source_id.

Решение:
- Хранить очищенное тело один раз в проекте.
- Добавить DocumentSourceOccurrence для каждого обнаруженного URL/Source,
  времени получения и операции.
- Сохранить первоначальный source_id как совместимую ссылку на происхождение,
  но не считать его полным перечнем мест публикации.
- Evidence должен указывать проверяемое происхождение использованной копии.

Проверка: пять копий дают одно тело документа и пять записей происхождения.

### A-09. Глобальные индексы должны поддерживать несколько мест хранения

Источник: Раздел 3 §25.

Решение:
- content_hash и canonical_url идентифицируют глобальный объект.
- Связи объекта с Project/local ID хранить отдельными строками locations.
- Не перезаписывать расположение первого проекта при записи второго.
- Между разными файлами SQLite не объявлять фиктивные FOREIGN KEY.
- Реестр не предоставляет неявного доступа к содержимому другого проекта.

Атомарность синхронизации реестра остаётся отдельным блокером Q-01.

### A-10. Качество источника и статусы утверждения разделены

Источник: Source.quality_profile; Раздел 1 §4.2; Claim.status.

Решение:
- SourceQualityAssessment относится к Study/domain/mode/config revision,
  а не является единственной изменяемой оценкой глобального Source.
- Claim.support_status использует SUPPORTED, PARTIALLY_SUPPORTED,
  CONTRADICTED, INSUFFICIENT_EVIDENCE.
- Эпистемический класс ESTABLISHED/PROMISING/EXPERIMENTAL и остальные
  хранится отдельным полем классификации, не заменяя support_status.
- Число confidence не трактуется как статистически калиброванная вероятность.

Проверка: оценка в медицинском исследовании не меняет оценку отзывов.

### A-11. Уточнение гарантий SQLite

Источник: Раздел 3 §§24–26.

Решение:
- Для требования сохранения подтверждённых транзакций при отключении питания
  использовать synchronous=FULL вместо NORMAL.
- Проверять foreign_keys на каждом соединении.
- Read-only connection проверяет WAL, но не пытается менять journal_mode.
- journal_size_limit не считать жёстким пределом текущего роста WAL.
- Добавить мониторинг WAL, долгих читателей и свободного места.
- Backup выполнять SQLite backup API, не копированием активного .db.

Ограничение: FULL не защищает от неисправного накопителя или ложных гарантий fsync.

### A-12. Расчёт контекста зависит от режима

Источник: Раздел 2 §6a.

Проблема: min(backend, config, fallback) превращает fallback в постоянный cap.

Решение:
- fixed: операторское фиксированное значение.
- auto: надёжное значение backend, иначе fallback.
- auto_with_config_cap: min(выбранное auto-значение, операторский cap).
- Дополнительный известный серверный предел всегда учитывается.
- Неизвестные значения не подставляются как ноль.
- Отрицательный evidence_budget вызывает CONFIG_CONTEXT_INSUFFICIENT.
- Профиль backend/model/tokenizer сохраняется версионированно.

Проверка: backend=8192, fallback=4096, cap=8192 даёт 8192,
если backend признан надёжным и нет меньшего серверного предела.

### A-13. Русская морфология обязательна для приёмки MVP

Источник: Roadmap EPIC-10; Раздел 7 §§7.1,25–26.

Решение:
- Фраза «если включена» не отменяет обязательную русскую морфологию.
- BasicNormalizer допустим как явно диагностируемый degraded fallback.
- Такой fallback не закрывает acceptance русской морфологии.
- Recall >= 0.9 проверяется для каждого нормативного запроса.

### A-14. Python-поток нельзя безопасно принудительно уничтожить

Источник: GUI §9, противоречащие друг другу правила Hard Stop.

Решение:
- Не внедрять исключения в работающий поток и не применять unsafe thread kill.
- Использовать cancellation token и ограниченные по размеру батчи.
- Неотменяемую CPU-библиотеку изолировать в дочернем процессе без DB-write.
- После deadline запрещать принятие устаревших результатов операции.
- DB Writer не уничтожать вместе с CPU-worker.

Проверка: поздний результат отменённого worker не меняет Study и индекс.

### A-15. Начальный план и поиск первоисточника проходят через gaps

Источник: Раздел 1 §6; Раздел 4 §§18,23; plan_research.

Решение:
- При первичном планировании Core создаёт MISSING_DATA gaps
  из ещё не покрытых информационных потребностей.
- SearchTaskDraft связан с конкретным сохранённым gap.
- Поиск первоисточника тоже сначала регистрирует gap.
- LLM предлагает задачи, но не создаёт persistent SearchTask самостоятельно.

Проверка: нет автоматического сетевого запроса без валидированного основания.

### A-16. Устранение циклической зависимости Search Core и Research Engine

Источник: Roadmap EPIC-04/05.

Решение:
- EPIC-04 содержит чистые алгоритмы coverage, sufficiency и budget,
  принимающие типизированные входы.
- EPIC-05 вызывает их, управляя итерациями; не реализует второй evaluator.
- Gate G-04 проверяет точное создание/валидацию Evidence на fixtures
  без семантического извлечения реальной LLM.
- Gate G-05 использует FakeLLM через аналитический порт.

### A-17. Локальные источники имеют собственное проверяемое происхождение

Источник: MATERIALS_ONLY и требование веб-идентификатора у Evidence.

Решение:
- Для локального материала допустим внутренний source reference,
  зарегистрированный file_ref, content_hash и координаты цитаты.
- Не выдумывать публичный URL, DOI или PMID локальному документу.
- Абсолютный приватный путь не раскрывать модели или публичному отчёту.

Наличие task_id для такого Evidence отдельно требует решения Q-07.

### A-18. Конфигурация и восстановление версионируются

Источник: запрет изменения ResearchConfig во время Study и backend switching.

Решение:
- ResearchConfig хранит неизменяемые ревизии с active revision reference.
- Расширение бюджета создаёт явную ревизию и запись аудита.
- Runtime backend profile версионируется отдельно от бизнес-порогов.
- Восстановление backend не меняет незаметно правила достаточности.
- Изменение chunk_size применяется только к новым версиям разбиения.

### A-19. Формат ошибок: domain error не равен JSON-RPC envelope

Источник: Раздел 5 §16; MCP Contracts §0.

Решение:
- Сохранить строковый доменный code и остальные нормативные поля.
- Оборачивать их средствами выбранной версии MCP SDK.
- Не помещать произвольный строковый code в поле JSON-RPC,
  которому протокол требует числовой код.
- Различать protocol errors и ошибки выполнения инструмента.

### A-20. Runtime stdout protection и CI policy не противоречат друг другу

Источник: Roadmap EPIC-07; Раздел 7 §19.1.

Решение:
- Непреднамеренный print перехватывается и не повреждает транспорт.
- CI запрещает такие вызовы вне разрешённого транспорта.
- Тест падает, если debug действительно достиг transport channel.
- Перехваченная диагностическая строка в stderr не является ошибкой протокола.

### A-21. Изменяемый индекс не изменяет старые доказательства

Источник: lifecycle BM25 и стабильность Evidence.

Решение:
- Содержимое Document, на которое ссылается Evidence, неизменяемо.
- Новое содержимое URL создаёт новую версию документа.
- Rebuild использует staging generation и атомарное переключение active index.
- Удаление Study не удаляет общий Document, используемый другим Study.
- Снятие связи StudyDocumentLink и физическое удаление Document различаются.

Правила получения обновлённой версии URL требуют Q-08.

## 3. Критические открытые вопросы

### Q-01. Атомарная запись Project DB + registry.db при WAL

Источник: Раздел 3 §25.3.

Проблема: отдельные SQLite-файлы в WAL не дают гарантии единого crash-atomic
commit сразу для всех файлов. Один DB Writer сам по себе это не исправляет.

Рекомендация: проектная БД является источником истины;
transactional outbox фиксируется вместе с Document/Source;
реестр обновляется идемпотентно и допускает восстановимую задержку.

Нужное решение: допустима ли такая согласованность вместо заявленной
межфайловой атомарности?

Остановлено: реализация протокола синхронизации реестра и согласованного
многопроектного snapshot. Локальные транзакции и backup одного проекта стабильны.
Блокирует: завершение G-02, кросс-проектные операции и последующие Gates.

### Q-02. Независимость источников: формула противоречит правилу UNKNOWN

Источник: Раздел 1 §7.

Проблема:
- UNKNOWN не должен увеличивать число независимых подтверждений.
- Формула предлагает считать кластеры, связанные UNKNOWN или не связанные.
- Нет формального представления подтверждённой независимости.
- Неясно, зависимость оценивается для сайта целиком или конкретного утверждения.
  Цитирование одной статьи не делает всё содержимое сайта зависимым.

Нужное решение: утвердить объект подтверждения независимости, область оценки
и алгоритм перехода от неизвестной связи к независимому подтверждению.

Остановлено: финальный independent_source_count и зависимые решения confidence.
Можно реализовать: хранение отношений и детерминированное обнаружение копий.
Блокирует: соответствующая часть G-04/G-05/G-10.

### Q-03. Формулы достаточности и production-пороги отсутствуют

Источник: SufficiencyEvaluator, ResearchConfig, Low-Independence Scenario.

Не определены:
- знаменатель information_gain и окно «последних итераций»;
- обработка первой итерации и пустой базы;
- веса coverage и обязательные минимумы;
- приоритет одновременно сработавших STOP;
- допустимость STOP_SUFFICIENT при INSUFFICIENT_EVIDENCE;
- формула confidence и минимальная выборка для утверждений.

Нужное решение: подписанные strategy profiles и golden decisions,
включая границы 0%, 5%, полное покрытие и неразрешённые противоречия.

Остановлено: production policy SufficiencyEvaluator и окончательная
валидация confidence. Интерфейс и механизм исполнения правил стабильны.

### Q-04. Несогласованный контракт бюджета

Источник: Раздел 1 §6a; Раздел 4 §22; MCP contracts.

Не определены или противоречат друг другу:
- network_budget: все HTTP-запросы или только запросы поиска;
- ошибки и retries потребляют ресурсы, но списание описано только при успехе;
- llm_token_budget включает input, output или оба;
- time_budget учитывает паузы, отсутствие LLM и перезапуск или нет;
- диагностика и cancel должны работать при нулевом tool_call_budget;
- при нулевом LLM-бюджете всё равно требуется partial report;
- validate_and_save_report списывает llm_call_budget, хотя сам не вызывает LLM;
- нет явного document_budget, хотя он упоминается в обязанностях Core.

Рекомендация: предварительное резервирование, журнал фактического потребления,
отдельное завершение/возврат резерва; детерминированный partial report без LLM
при исчерпании вычислительного бюджета.

Нужное решение: таблица тарификации по типам операций и результатам.
Остановлено: production billing policy и финализация при нулевых ресурсах.
Можно реализовать: атомарные счётчики, reservations, idempotency.

### Q-05. Неполная FSM для остановки, ошибок и редактирования

Источник: State Machine Specification v1.1.

Не определены:
- HARD_STOP из PAUSED и FREEZE_BUDGET_EXHAUSTED;
- завершение Study после RECOVERY_FAILED/RECOVERY_TIMEOUT сессии;
- отмена CREATED/VALIDATING SearchTask;
- произвольная validation failure, не относящаяся к четырём rejection states;
- повтор FAILED SearchTask при неизменном fingerprint;
- редактирование утверждённого плана и возврат READY к планированию;
- финализация partial report после USER_STOPPED;
- полный набор guards/triggers для Job, включая отмену QUEUED.

Нужное решение: дополненная таблица переходов и межавтоматных правил.
Остановлены только отсутствующие переходы.
Существующие таблицы реализуются без догадок.
Блокирует полный G-03 и соответствующие сценарии G-08/G-09.

### Q-06. MCP не передаёт обязательный контекст извлечения Evidence

Источник: search_within_document OUTPUT и контекстный коридор ±1.

Проблема:
- Tool возвращает text_snippet, но не гарантирует полный коридор,
  offsets и ID соседних чанков.
- Snippet запрещено считать Evidence.
- Лимит 8 KiB ответа может не вместить обязательный коридор.
- payload save_study_material ограничен 4 KiB.

Нужное решение: уточнить версионированный read-контракт или добавить
явный разрешённый механизм получения Evidence extraction context.
Не добавлять скрытый 24-й tool самостоятельно.

Остановлено: полный путь MCP → контекст → извлечение Evidence.
Локальная сборка и валидация коридора стабильны.
Блокирует G-07 и реальный end-to-end acceptance.

### Q-07. task_id для Evidence из локальных документов

Источник: Evidence.task_id NOT NULL; save_study_material;
add_local_document без task_id; MATERIALS_ONLY.

Нужное решение: либо формальная локальная аналитическая SearchTask
с собственным purpose/scope, либо иной provenance task contract.
Недопустимо создавать фиктивную сетевую задачу или чужой task_id.

Остановлено: сохранение локального Evidence до утверждения происхождения.
Импорт, индексирование и локальный поиск реализуемы независимо.

### Q-08. URL-idempotency блокирует обновление документов

Источник: read_url_content IDEMPOTENCY; Cache EXPIRED/FORCED_REFRESH.

Проблема: вечный SHA256(canonical_url) возвращает старый Document,
но TTL/forced refresh требуют обновлять данные.

Нужное решение: срок действия idempotency, явная revision/refresh operation,
правила выбора версии для Study и EXPAND.

Остановлено: обновление уже импортированного URL.
Первое чтение и повтор той же операции стабильны.

### Q-09. Верификация авторов и статистическая выборка

Источник: Review Research, CanonicalReview, QA Aggregation.

Не определены:
- доказательство, что reviewer_id соответствует уникальному человеку;
- объединение одного человека между площадками;
- знаменатель процентных показателей;
- минимальная выборка;
- обращение с анонимными и стимулированными отзывами;
- критерии аномального всплеска и маркировки накрутки.

Рекомендация: platform-scoped author identity; UNKNOWN не считать
верифицированным; не выдавать эвристику за доказательство накрутки.

Нужное решение: политика идентификации и статистики.
Остановлены итоговые пользовательские статистические выводы и anomaly policy.
Схема, извлечение и агрегатор на явно верифицированных fixtures стабильны.

### Q-10. Приватные данные могут утечь через поисковые запросы

Источник: запрет передачи конфиденциальных данных; адаптивный веб-поиск.

Проблема: локальная LLM может включить приватный фрагмент в recommended_query,
после чего Core отправит его внешнему поисковому сервису.

Нужное решение: модель классификации данных и разрешения на egress.
Рекомендация: данные локальных материалов запрещены для внешнего поиска
до явного разрешения пользователя; секреты не выводить в logs/report.

Остановлено: автоматическое внешнее исследование на основе приватного контекста.
MATERIALS_ONLY и поиск по явно публичному входу стабильны.

### Q-11. Перенос Study и откат snapshot не специфицированы

Источник: GUI §§12–13.

Не определены:
- copy или move; поведение исходного Study;
- remap ID и общих документов при переносе между проектами;
- обращения к активным сессиям;
- конфликт версий конфигурации и схемы;
- какие данные разрешено откатывать без разрушения audit history.

Остановлено: transfer Study и пользовательский rollback Study snapshot.
Создание backup и проверка восстановления в отдельный каталог стабильны.

### Q-12. Целевая Windows-среда и performance acceptance

Источник: CPU-only 12–14B, GUI responsiveness, Portable.

Не заданы Windows versions, RAM, свободный диск, CPU baseline,
модель/квантование и допустимые задержки GUI, отмены и генерации.

Нужное решение: release environment matrix и измеримые performance budgets.
Можно подготовить benchmark harness, но нельзя объявить производительность
принятой без численных критериев.

### Q-13. Administrator diagnostic token не имеет контракта

Источник: Roadmap EPIC-11.

Неясны назначение, полномочия, TTL, выдача, хранение и отзыв токена.

Остановлено: реализация administrator diagnostic token.
Недопустимо самостоятельно создавать скрытый привилегированный доступ.
Обычная локальная диагностика реализуется без него.

## 4. Вехи и правила Gates

M0  = G-01: Skeleton.
M1  = G-02: Persistent Core.
M2  = G-03: Formal Core.
M3  = G-04: Search Core.
M4  = G-05: Research Core.
M5  = G-06: LLM Integration.
M6  = G-07: MCP Complete.
M7  = G-08: Usable GUI.
M8  = G-09: Resilient System.

Наличие заготовки интерфейса или mock-теста не закрывает production-требование.
