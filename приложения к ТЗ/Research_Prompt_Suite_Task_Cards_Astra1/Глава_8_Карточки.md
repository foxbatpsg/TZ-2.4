# EPIC-08. GUI
Веха: M7. Gate: G-08.
Входной Gate: G-07.
Стек: Python + CustomTkinter.
Общий DoD: DOD-ALL.
GUI является тонким клиентом Application API.

## E08-C01

**Название задачи:** Реализовать shell, navigation и worker bridge.

**Контекст и техническая цель:** Отделить rendering от тяжёлой работы.

**Входные данные и зависимости:** G-07; GUI §§1–2.

**Чёткие технические требования к реализации:** Main thread управляет widgets;
worker содержит постоянный asyncio loop.
Связь через run_coroutine_threadsafe, thread-safe queue и root.after.
UI controllers тестируемы без настоящего окна.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Event dispatch;
worker error; закрытие окна при pending future;
повтор shutdown; callback не в UI thread;
неизвестный navigation route.
Моки: root.after, widgets, Application API.

**Критерии приёмки:** Retrieval/parsing/indexing не работают в UI thread;
нет обращения worker к widgets; DOD-ALL.

## E08-C02

**Название задачи:** Реализовать Project/Study creation и project switching.

**Контекст и техническая цель:** Безопасно переключать файловый контекст.

**Входные данные и зависимости:** E08-C01; Project Registry; Q-01/Q-11.

**Чёткие технические требования к реализации:** Формы Project/Study,
явные mode/source scope/filters; список Projects из реестра.
При switch сбрасывать stale UI context и отклонять callbacks предыдущего проекта.
Rename/archive/delete вызывают отдельные Core commands;
delete требует подтверждения. Transfer заблокирован Q-11.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Creation validation;
switch A→B с поздним ответом A; missing DB;
cancel deletion confirmation; archived Project;
невалидный Study destination.
Моки: registry/Application API, dialogs.

**Критерии приёмки:** UI не открывает SQLite напрямую;
данные предыдущего проекта не отображаются как текущие; DOD-ALL.

## E08-C03

**Название задачи:** Реализовать Intent Blueprint и обязательный preview.

**Контекст и техническая цель:** Пользователь видит план до выполнения.

**Входные данные и зависимости:** E08-C01/C02; E05-C01; Q-05.

**Чёткие технические требования к реализации:** Отображать task, purpose, query,
source, filters/exclusions, type, priority, estimated budget.
Разрешить редактирование draft через Core revalidation.
Не менять утверждённый plan lifecycle без решения Q-05.
Preview bypass только по явной пользовательской настройке.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Start без preview;
изменение query требует revalidation; disabled task;
невалидный priority; duplicate after edit;
explicit bypass flag.
Моки: plan commands, validation responses.

**Критерии приёмки:** Изменение формы не запускает поиск;
Core остаётся владельцем acceptance; DOD-ALL.

## E08-C04

**Название задачи:** Реализовать X-Ray Activity Stream.

**Контекст и техническая цель:** Показывать ход работы без перегрузки UI.

**Входные данные и зависимости:** E08-C01; E01-C05.

**Чёткие технические требования к реализации:** Queue batching через root.after;
конфигурируемый ring buffer 150–300 строк.
Типизированные события search/ranking/fetch/parsing/chunking/Evidence/gaps/errors.
Не показывать приватные payload или credentials.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Буфер до/после предела;
пустой batch; event storm; malformed event;
поздний event другого Project; secret redaction.
Моки: event queue и scheduler.

**Критерии приёмки:** Размер буфера ограничен;
поток событий не блокирует управление; DOD-ALL.

## E08-C05

**Название задачи:** Реализовать Evidence Explorer и Evidence Tree.

**Контекст и техническая цель:** Дать пользователю проверяемый путь Claim→Source.

**Входные данные и зависимости:** E08-C01/C02; evidence read models.

**Чёткие технические требования к реализации:** Показывать Claim, Evidence,
Document, Source, exact quote, location, metadata и Contradiction.
Цвета только отображают Core status.
Обрабатывать missing/stale references явно, не скрывать разрыв цепочки.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Claim с несколькими Evidence;
один Evidence нескольких Claims; missing Document;
чужой Study; противоречие; локальный source без публичного URL.
Моки: read model и widgets.

**Критерии приёмки:** Клик открывает именно выбранную цитату и происхождение;
GUI не пересчитывает confidence; DOD-ALL.

## E08-C06

**Название задачи:** Реализовать Report Viewer и сохранение/экспорт.

**Контекст и техническая цель:** Просмотр полного и частичного результата.

**Входные данные и зависимости:** E08-C01; E05-C09; E07-C23.

**Чёткие технические требования к реализации:** Smart scroll, кнопка «к концу»,
явные partial/truncated/validation flags и missing sections.
Сохранение вызывает Core validator; export не делает невалидный отчёт валидным.
Не исполнять embedded HTML/scripts отчёта.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Пользователь читает выше конца;
новый fragment; truncated report; validation errors;
export failure; unsafe link; пустой отчёт.
Моки: scroll model, exporter, Application API.

**Критерии приёмки:** Автопрокрутка не мешает чтению;
partial всегда визуально отличим; DOD-ALL.

## E08-C07

**Название задачи:** Реализовать Dashboard/Health и управление backend.

**Контекст и техническая цель:** Показать ресурсы, статусы и проблемы.

**Входные данные и зависимости:** E08-C01/C02; E06-C04.

**Чёткие технические требования к реализации:** LLM status/backend,
active tasks, queue size, Project DB size, registry size, free disk, source errors.
Backend switch и budget extension только через разрешённые команды.
Показывать время snapshot метрик.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Backend unreachable;
недостаток диска; отсутствующий registry;
stale snapshot; switch failure; ошибочный extension input.
Моки: health read model и commands.

**Критерии приёмки:** UI не изменяет budget/config напрямую;
ошибки диагностируются без ложного успешного статуса; DOD-ALL.

## E08-C08

**Название задачи:** Реализовать Soft/Hard Stop controls.

**Контекст и техническая цель:** Управляемая остановка без unsafe thread kill.

**Входные данные и зависимости:** E08-C01; E03 FSM; A-14; Q-05.

**Чёткие технические требования к реализации:** Отправлять команды Core;
отличать «отмена запрошена» от «остановлено».
Блокировать повторный запуск новой работы до подтверждённого состояния.
UI не присваивает USER_STOPPED или CANCELLED самостоятельно.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Double click;
stop во время CPU batch; поздний result;
completion/stop race; close window during cancellation;
неподдерживаемый state из Q-05.
Моки: command API, job status, FakeClock.

**Критерии приёмки:** Кнопки отражают подтверждённое состояние;
нет ложного обещания мгновенного уничтожения потока; DOD-ALL.

## E08-C09

**Название задачи:** Реализовать Snapshot, Offline и Prompt Sandbox UI.

**Контекст и техническая цель:** Работа с сохранёнными материалами без лишних side effects.

**Входные данные и зависимости:** E08-C01; E02-C08; E05-C06; Q-11.

**Чёткие технические требования к реализации:** Создание/проверка backup через Core;
локальный поиск, Evidence, report/export при отсутствии внешней сети.
Sandbox использует выбранные Evidence и отдельный временный контекст,
не изменяя Study. Rollback snapshot ожидает Q-11.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Offline transition;
snapshot failure; validation-only restore;
Sandbox response не меняет Claims; LLM отсутствует;
отклонение rollback до утверждения policy.
Моки: backup service, sandbox provider, network status.

**Критерии приёмки:** Sandbox не загрязняет Study;
offline не означает автоматическую доступность LLM; DOD-ALL.

## E08-C10

**Название задачи:** Реализовать Review/Aggregation UI и Gate G-08.

**Контекст и техническая цель:** Показать статистику без её переинтерпретации
и проверить отзывчивость интерфейса.

**Входные данные и зависимости:** E08-C01…C09; E05-C07; Q-09/Q-12.

**Чёткие технические требования к реализации:** Отдельно отображать reviews,
authors, sources, observations, denominator, aspects и limitations.
UNKNOWN показывать как неизвестно, а не 0.
Добавить heartbeat harness для responsiveness и cancellation benchmarks.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Нулевая выборка;
неизвестный denominator; повторные отзывы;
нет anomaly policy; delayed worker; malformed stats.
Моки: aggregation read model, GUI scheduler.
Component: реальное окно в Windows test environment.

**Критерии приёмки:** UI не выводит статистические факты без Core;
G-08 требует закрытия Q-05/Q-09/Q-11 и численных критериев Q-12; DOD-ALL.
