# ADR-002 — Идентичность Document при смене URL (Q-08 / S-12)

**Статус:** Accepted — 2026-09-14.
**Закрывает:** `S-12` / `Q-08` (P0-блокер).
**Нормативная норма:** «Механизм версионирования Document (Q-08)» — `03_Модель данных и хранение.md` §9b (операционализация A-21); связанные: `04_Search Core.md` §25 (FORCED_REFRESH), `MCP TOOL CONTRACTS v1.1.md` §3 (`refresh=true` в `read_url_content`), `07_QA_Acceptance.md` §17 (Q-08 закрыт). **A-21 не изменён.**
**Назначение файла:** адресная карточка решения для исполнителей задач (`RELATED_ADR: ADR-002`). Формулировки ниже перенесены дословно из `корзина/REVIEW-REGISTRY.md` §3 (S-12); нормативной правкой файл не является, при расхождении приоритет — у ТЗ.

## Контекст

Прямое противоречие в тексте ТЗ. A-21 требует создавать **новую версию Document** при смене URL, но поле `content_hash` объявлено `UNIQUE` (ТЗ `03`, стр. 277: «SHA256 от сырого очищенного текста») и тело документа должно храниться один раз.

Логическая неустранимость: если URL изменился, а текст — тот же, новый Document не может получить уникальный `content_hash`. Если текст изменился — это уже другой документ, и A-21 здесь ни при чём. Сформулированное правило нереализуемо в текущей схеме.

## Решение

Утверждён черновик Q-08 из корзины. **A-21 не изменён** — при повторной проверке по нормативному тексту (`03` §9 стр. 291: «не перезаписывает Document — создаётся новая версия») черновик полностью согласован с A-21, а механизм версионирования (`03` §9b) его операционализирует. Первоначальная рекомендация «переписать A-21» отклонена как основанная на неточном парафразе. Внесено: `03` §9b (механизм версионирования: идемпотентное окно 24ч, флаг `refresh=true`, правила выбора версий, `CONTENT_UNCHANGED`), `04` §25 (FORCED_REFRESH для MCP), `MCP TOOL CONTRACTS` §3 (`read_url_content` + `refresh`), `07` §17 (Q-08 закрыт). Блокировки `E02-T10`, `E02-T20`, `E04-T33/34/35` снимаются.
