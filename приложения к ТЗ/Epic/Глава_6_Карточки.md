## E06-C01

**Название задачи:** Реализовать LLMProvider и backend configuration.

**Контекст и техническая цель:** Изолировать локальную модель от Research Engine.

**Входные данные и зависимости:** Foundation; runtime FSM; A-18; Q-10 (закрыт — `05` §3.3).

**Чёткие технические требования к реализации:** Provider request/response DTO,
capabilities, health, timeout, token usage, model identity.
Backend endpoints локальные; внешний endpoint запрещён штатной политикой.
Provider не пишет Evidence и не изменяет Study.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Local endpoint;
cloud endpoint; redirect наружу; отсутствующая модель;
невалидный usage; unsupported capability; пустой response.
Моки: HTTP transport и endpoint resolver.

**Критерии приёмки:** Контракт заменяем без изменения Study API;
неявного cloud fallback нет; DOD-ALL.

## E06-C02

**Название задачи:** Реализовать LM Studio adapter.

**Контекст и техническая цель:** Поддержать OpenAI-compatible локальный backend.

**Входные данные и зависимости:** E06-C01.

**Чёткие технические требования к реализации:** Преобразование запросов/ответов,
stream termination, usage, model selection, supported structured-output options.
Версию API/capabilities фиксировать в тестовых fixtures.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Обычный ответ;
streamed ответ; malformed JSON envelope;
timeout до первого токена; обрыв stream;
несуществующая модель; отсутствие usage.
Моки: recorded LM Studio HTTP responses.

**Критерии приёмки:** Adapter проходит общий provider contract suite;
не интерпретирует оборванный stream как успешный; DOD-ALL.

## E06-C03

**Название задачи:** Реализовать Ollama adapter.

**Контекст и техническая цель:** Поддержать локальный REST backend через тот же порт.

**Входные данные и зависимости:** E06-C01.

**Чёткие технические требования к реализации:** Ollama request mapping,
stream assembly, done marker, token statistics, structured format capabilities.
Не переносить Ollama-specific поля в Research Engine.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Non-stream и stream;
отсутствующий done; ошибка загрузки модели;
разорванный JSON frame; unsupported grammar;
нормализация prompt/completion counts.
Моки: recorded Ollama responses.

**Критерии приёмки:** Тот же provider contract suite, что у LM Studio;
DOD-ALL.

## E06-C04

**Название задачи:** Реализовать health monitor, recovery и backend switching.

**Контекст и техническая цель:** Восстановить вычислительный сервис без потери Study.

**Входные данные и зависимости:** E06-C02/C03; E03-C03/C05; A-18.

**Чёткие технические требования к реализации:** HEALTHY/DEGRADED/UNREACHABLE/
RESTARTING через FSM. Переключать только на разрешённый локальный backend.
Не смешивать части одного ответа от разных моделей.
Пересчитать профиль контекста до повторного вызова.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Health flapping;
restart failure; восстановление без restart;
switch во время stream; поздний ответ старого backend;
исчерпан retry; повтор recovery event.
Моки: FakeClock, process controller, providers.

**Критерии приёмки:** Session восстанавливается из БД;
Evidence/Claims не теряются; DOD-ALL.

## E06-C05

**Название задачи:** Реализовать structured output и controlled repair.

**Контекст и техническая цель:** Принимать только структурно и содержательно допустимый ответ.

**Входные данные и зависимости:** E06-C01…C03; E05-C03/C04/C05.

**Чёткие технические требования к реализации:** Capability-driven grammar/schema
generation, затем strict schema validation и content validation.
Repair только промежуточных объектов и только по allowlist синтаксических
преобразований; лимит попыток; audit исходной ошибки.
Не восстанавливать выдуманные ID и не чинить финальный отчёт.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Backend без grammar;
JSON code fence; duplicate keys; truncated object;
пустой обязательный результат; чужой Evidence ID;
repair меняет число; превышен retry limit.
Моки: provider, schema registry, reference validator.

**Критерии приёмки:** Schema-valid не означает автоматически accepted;
финальный report repair заблокирован; DOD-ALL.

## E06-C06

**Название задачи:** Реализовать TokenBudgetManager и prompt construction.

**Контекст и техническая цель:** Не превышать контекст модели и не терять ±1.

**Входные данные и зависимости:** E06-C01/C04; E04-C16; A-12; Q-04/Q-06 (закрыт 2026-09-16 — `05` §4b).

**Чёткие технические требования к реализации:** Поддержать три режима;
вычитать output reserve, safety margin и fixed sections.
Token accounting учитывает сериализацию и служебные разделители.
Уменьшать число extraction units, а не отрезать соседей target.
Недостаточный минимум возвращает CONFIG_CONTEXT_INSUFFICIENT.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Backend metadata отсутствует;
fallback не является cap; fixed mode;
ровно лимит/лимит+1; fixed sections переполнены;
Unicode; смена tokenizer; единственный коридор не помещается.
Моки: token counter, backend profile.

**Критерии приёмки:** Заведомо oversized prompt не отправляется;
HTML/полные страницы/log dumps не входят в prompt; DOD-ALL.

## E06-C07

**Название задачи:** Провести LLM resilience Gate G-06.

**Контекст и техническая цель:** Проверить provider boundary и деградационные сценарии.

**Входные данные и зависимости:** E06-C01…C06; A-22 (`02` §5.3).

**Чёткие технические требования к реализации:** Общая contract suite обоих adapters,
restart/switch/context tests, structured output и budget port integration.
Реальный локальный model smoke оформить отдельным протоколом, не стандартной CI.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Gate validator отклоняет
непротестированную capability, пропущенный adapter, failed repair case,
невалидную token fixture и отсутствие recovery evidence.
Моки: test reports и backend capability manifests.

**Критерии приёмки:** Offline regression проходит;
результат не выдаётся за проверку реальной производительности 12–14B (`A-22`, `02` §5.3); DOD-ALL.
