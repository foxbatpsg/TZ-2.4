## E02-C01

**Название задачи:** Реализовать фабрику SQLite-соединений и транзакции.

**Контекст и техническая цель:** Единая контролируемая точка доступа к БД.

**Входные данные и зависимости:** G-01; A-11.

**Чёткие технические требования к реализации:** Project DB в отдельном файле;
WAL, foreign_keys=ON, busy_timeout=5000, journal_size_limit=67108864,
wal_autocheckpoint=1000; synchronous=FULL согласно A-11.
Разделить read-only и writer connections; исключить незавершённые транзакции
после выхода с ошибкой.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Выбор PRAGMA для reader/writer;
невалидный путь; исключение внутри transaction; повторное закрытие;
вложенная транзакция по явно выбранной savepoint policy.
Моки: connection factory для unit; реальный временный SQLite для component.

**Критерии приёмки:** Rollback подтверждён чтением из нового соединения;
PRAGMA проверены на каждом connection; DOD-ALL.

## E02-C02

**Название задачи:** Создать механизм версионированных миграций.

**Контекст и техническая цель:** Безопасное создание и обновление схемы.

**Входные данные и зависимости:** E02-C01.

**Чёткие технические требования к реализации:** Хранить версию и checksum
миграции; применять миграцию транзакционно. Не выполнять silent downgrade.
Проверять совместимость приложения со схемой до открытия рабочего Study.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Пустая БД;
последовательное обновление; повтор применения; изменённый checksum;
версия БД новее приложения; ошибка середины миграции.
Моки: migration registry; component tests на временном SQLite.

**Критерии приёмки:** Неудачная миграция не оставляет половину схемы;
повторный запуск восстанавливает допустимое состояние; DOD-ALL.

## E02-C03

**Название задачи:** Реализовать Project/Study/Intent/Entity/Config persistence.

**Контекст и техническая цель:** Нормализованное хранение исследовательского контекста.

**Входные данные и зависимости:** E02-C02; A-03/A-04/A-18.

**Чёткие технические требования к реализации:** Реализовать перечисленные сущности
и связующие таблицы Intent, EntityAlias и конфигурационных ревизий.
Ввести FK, NOT NULL, проверки enum и индексы. Не объединять неоднозначные aliases
разных объектов автоматически. Публичный repository не предоставляет setter status.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** CRUD; неизвестный enum;
alias collision; Intent чужого Study; одна активная config revision;
rollback пакетного сохранения.
Моки: writer port; component tests с реальными FK.

**Критерии приёмки:** Списки не хранятся источником истины в TEXT/JSON;
недопустимые межсущностные связи отвергаются; DOD-ALL.

## E02-C04

**Контекст и техническая цель:** Сохранить документы без потери происхождения

**Входные данные и зависимости:** E02-C03; A-04/A-07/A-08/A-10/A-21.

**Чёткие технические требования к реализации:** SearchTask, SearchResult, Source,
SourceRelation, identifiers, SourceQualityAssessment, Document,
DocumentSourceOccurrence, DocumentChunk, ChunkNumericSignature, StudyDocumentLink.
Document.content неизменяем после появления Evidence.
Предусмотреть rowid/chunk_id mapping для будущего FTS5, не реализуя BM25.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Общий Document двух Studies;
пять источников одинакового content_hash; чужой task_id;
повторный identifier; удаление используемого документа;
стабильность chunk identity.
Моки: hash/clock; реальный SQLite для constraints.

**Критерии приёмки:** Одно тело не теряет список происхождений;
FTS5 readiness документирована; DOD-ALL.

## E02-C06

**Название задачи:** Реализовать операционные записи и единый DB Writer.

**Контекст и техническая цель:** Последовательная запись без write races.

**Входные данные и зависимости:** E02-C03…C05.

**Чёткие технические требования к реализации:** ResearchSession, ResearchState,
WorkingMemory, CacheEntry, LogRecord, Job, operation records,
budget ledger/reservations. Writer принимает команды через bounded queue,
возвращает результат после commit; имеет graceful shutdown и backpressure.
Runtime MCP operation не превращается в Study state.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** FIFO; переполненная очередь;
ошибка одной команды не портит следующую; shutdown с pending commands;
сбой до commit; повтор idempotency key.
Моки: queue/clock; реальные concurrent readers и writer в integration.

**Критерии приёмки:** Ни один worker не пишет напрямую;
ошибка транзакции видна вызывающему компоненту; DOD-ALL.

## E02-C07

**Название задачи:** Реализовать изолированные repositories и metadata registry.

**Контекст и техническая цель:** Безопасный доступ к Project/Study и представление
нескольких расположений глобального документа.

**Входные данные и зависимости:** E02-C04/C06; A-09; Q-01 (закрыт — `03` §25.3).

**Чёткие технические требования к реализации:** Все Study-запросы принимают
явный scope и используют StudyDocumentLink. Создать схему ProjectRegistry
и глобальных identity/location таблиц. Проверять scope до возврата содержимого.
Межфайловый sync реализуется через
transactional outbox по `03` §25.3/§17d (`Q-01` закрыт); карточка проверяет
корректность outbox-синхронизации, а не откладывает её.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Чужой Project;
один hash в двух проектах; stale location; неизвестный Project;
переключение connection context; попытка path traversal через project ID.
Моки: registry resolver; component tests с двумя проектными БД.

**Критерии приёмки:** Метаданные не раскрывают содержимое без разрешённого scope;
outbox-синхронизация покрыта тестами `03` §25.3 и не объявляется завершённой вне доказанного объёма; DOD-ALL.

## E02-C08

**Название задачи:** Реализовать WAL-safe backup и проверку восстановления.

**Контекст и техническая цель:** Получить согласованный backup одного проекта.

**Входные данные и зависимости:** E02-C01/C06; A-11; Q-01 (закрыт — `03` §25.3), Q-11 (закрыт — `06` §13).

**Чёткие технические требования к реализации:** Использовать SQLite backup API;
добавить manifest с schema/config versions и checksum. Восстанавливать сначала
в отдельный каталог, выполнять integrity_check и foreign_key_check.
Не перезаписывать действующую БД; Study rollback специфицирован
(`Q-11` закрыт, `06` §13) и находится вне scope этой карточки backup.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Повреждённый manifest;
нехватка места; отмена; несовместимая версия; неверный checksum;
откат, разрушающий audit, запрещён; outbox reconciliation после restore.
Моки: filesystem/backup progress.
Integration: backup при активной WAL-записи и восстановление без исходного WAL.

**Критерии приёмки:** Восстановленная копия открывается и согласована;
оригинал не изменён; DOD-ALL.
