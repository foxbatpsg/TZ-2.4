## E09-C01

**Название задачи:** Проверить полный application composition.

**Контекст и техническая цель:** Соединить GUI, Core, Research Engine, MCP/LLM,
Search и Data Layer без обходных маршрутов.

**Входные данные и зависимости:** Принятые EPIC-01…08.

**Чёткие технические требования к реализации:** Production composition root
использует те же интерфейсы, что tests. End-to-end scenario сохраняет
operation/request/task provenance до Report. Проверить отсутствие циклического
вызова Core→MCP→Core для одной внутренней операции.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Неправильный dependency binding;
missing provider; duplicate command dispatch;
неизвестный operation correlation; forbidden direct write.
Моки: boundary spies.
Integration: реальные MCP/stdin/stdout, SQLite, FakeLLM/HTTP.

**Критерии приёмки:** Один пользовательский сценарий даёт одну согласованную
историю выполнения и отчёт; DOD-ALL.

## E09-C02

**Название задачи:** Проверить LLM/MCP/network failure isolation.

**Контекст и техническая цель:** Восстанавливать отказавший компонент,
не уничтожая всё исследование.

**Входные данные и зависимости:** E09-C01; E06 resilience; Q-05 закрыт (`01` §2.3, `STATE MACHINE SPECIFICATION v1.2`).

**Чёткие технические требования к реализации:** Fault injection для backend
timeout/restart/switch, MCP stall, source 429/403/timeout/parse error.
Watchdog не путает штатный простой с зависанием активной операции.
Перезапуск только зависшего owned process.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Idle без запросов;
долгий разрешённый вызов; dead transport;
flapping backend; доступный другой домен;
повтор restart event.
Моки: process supervisor, FakeClock, fault schedule.

**Критерии приёмки:** Нет restart storm;
успешно сохранённые Evidence/Claims доступны после восстановления; DOD-ALL.

## E09-C03

**Название задачи:** Проверить stop, budget freeze и partial finalization.

**Контекст и техническая цель:** Устранить гонки между завершением,
отменой и исчерпанием ресурсов.

**Входные данные и зависимости:** E09-C01; закрытые Q-04 (`BUDGET CONTRACT v1.0`)/Q-05 (`STATE MACHINE SPECIFICATION v1.2`).

**Чёткие технические требования к реализации:** Сценарии pause/resume,
Soft/Hard Stop, исчерпание каждой dimension, явное budget extension,
нулевой LLM-budget и частичный отчёт.
Применять утверждённый arbitration order одновременных событий.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Последняя единица бюджета;
completion одновременно с stop; extension после freeze;
ноль tool budget и cancel; soft stop при pending fetch;
truncated final generation.
Моки: event scheduler, budget policy, FakeLLM.

**Критерии приёмки:** Нет новых неразрешённых операций после stop/freeze;
остатки бюджета и partial flags согласованы; DOD-ALL.

## E09-C04

**Название задачи:** Проверить crash recovery, Jobs и защиту поздних результатов.

**Контекст и техническая цель:** Восстановить подтверждённую работу без дублей.

**Входные данные и зависимости:** E09-C01; DB Writer/FSM/Jobs; Q-01 закрыт (`03` §25.3).

**Чёткие технические требования к реализации:** Injection до/после reservation,
result commit, index generation switch, registry sync и checkpoint.
Сохранять durable execution markers; сверять idempotency при recovery.
Недоказанно безопасный Job помечать FAILED по контракту.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Result committed, ACK потерян;
reservation без result; старый worker после resume;
interrupted rebuild; повтор registry event;
recovery с несовместимой schema/config.
Моки: crash points, process supervisor.
Integration: subprocess termination и повторное открытие БД.

**Критерии приёмки:** Нет потери committed цепочек и удвоения counters;
process-crash test не выдаётся за физический power-loss test; DOD-ALL.

## E09-C05

**Название задачи:** Провести resilience Gate G-09.

**Контекст и техническая цель:** Зафиксировать проверенную матрицу отказов.

**Входные данные и зависимости:** E09-C01…C04.

**Чёткие технические требования к реализации:** Матрица component × failure point
× expected FSM/data outcome; автоматическая проверка invariants после каждого сбоя.
Сохранять fault schedule и seed для воспроизведения.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Пропущенный failure point;
несовпадение ожидаемого state; orphan ClaimEvidence;
двойной debit; absent checkpoint; stale test evidence.
Моки: gate manifest и invariant checker inputs.

**Критерии приёмки:** Все обязательные failure scenarios воспроизводимы;
G-09 PASS только без нарушений FSM и потери подтверждённых данных; DOD-ALL.
