## E10-C01

**Название задачи:** Построить requirements traceability и coverage audit.

**Контекст и техническая цель:** Доказать, что ни одно обязательное требование
не потерялось между ТЗ, карточками и тестами.

**Входные данные и зависимости:** Все карточки, закрытые решения Q (`INDEX.md` §3/§4),
test manifests, `07` §25/§26/§28.1.

**Чёткие технические требования к реализации:** Requirement → component →
task → test → test result → acceptance evidence.
Отдельно перечислить исключённый Post-MVP и optional ReviewExtractor,
не исключая обязательную базовую aggregation.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Требование без теста;
тест без результата; duplicate requirement ID;
SKIP обязательного сценария; stale commit;
необоснованное исключение morphology.
Моки: requirements/test manifests.

**Критерии приёмки:** Для каждого обязательного требования есть актуальное
проверяемое подтверждение; DOD-ALL.

## E10-C02

**Название задачи:** Провести security acceptance.

**Контекст и техническая цель:** Проверить локальность, изоляцию и отсутствие утечек.

**Входные данные и зависимости:** Security policy Q-10 (закрыт — `05` §3.3); file_ref,
network/LLM guards, logging, report export.

**Чёткие технические требования к реализации:** Проверить отсутствие cloud LLM,
path traversal, symlink escape, redirect к локальным сервисам,
секреты в logs/reports, prompt injection через документ
и приватный query egress. Текст источника не может дать права на операции Core.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Вредоносная инструкция в Evidence;
secret в nested error; encoded traversal; revoked file_ref;
redirect outside allowlist; private fragment в recommended_query.
Моки: filesystem, transports, authorization policy.

**Критерии приёмки:** Все отрицательные проверки fail closed;
найденные критические уязвимости блокируют G-10; DOD-ALL.

## E10-C03

**Название задачи:** Провести функциональный acceptance.

**Контекст и техническая цель:** Подтвердить функциональность MVP на нормативных golden datasets.

**Входные данные и зависимости:** Принятые компоненты; Q-02 (закрыт — `ADR-003`), Q-03 (закрыт — `04` §22), Q-09 (закрыт — `04` §16a). Карточка разделена решением владельца 2026-10-02 (ревизия claude5, Гл.10-02 в.2): производительный acceptance вынесен в `E10-C03a`.

**Чёткие технические требования к реализации:** Data isolation, chunking/overlap,
BM25/morphology, dedup, five-copies/five-independent/mixed source datasets,
aggregation, contradictions, primary source, MATERIALS_ONLY, offline,
structured outputs, context protection и GUI cancellation.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Проверка recall denominator;
empty expected set; confidence fixtures;
comparison unknown vs zero;
неправильная версия normalizer.
Моки: golden manifests.
Component/E2E: CPU-only Windows test environment.

**Критерии приёмки:** Morphology recall >= 0.9 по каждому нормативному запросу;
нет обязательных GPU/vector dependencies; DOD-ALL.

## E10-C03a

**Название задачи:** Провести производительный acceptance (benchmark-spike).

**Контекст и техническая цель:** Получить численные критерии производительности Q-12 измерениями и подтвердить их на целевой среде.

**Входные данные и зависимости:** E10-C03; benchmark-spike `S-13` (численные критерии Q-12 — только после него; `02` §5.3); реализация — `E10-T15a` (декомпозиция EPIC-10).

**BLOCKED_BY:** `S-13` — задача benchmark-spike; до её выполнения карточка заблокирована и не входит в функциональную часть Gate G-10.

**Чёткие технические требования к реализации:** Измерять recall, latency и memory
по утверждённой environment matrix; percentile calculation по методике Q-12.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** benchmark percentile calculation;
measurement samples и golden manifests;
нестабильные замеры (разброс сверх policy).

**Критерии приёмки:** Численные критерии Q-12 зафиксированы по результатам измерений
(TARGET → RESULT по `02` §5.3); результат не выдаётся за функциональный acceptance; DOD-ALL.

## E10-C04

**Название задачи:** Подготовить release acceptance evidence и Gate G-10.

**Контекст и техническая цель:** Отделить доказанный результат от декларации готовности.

**Входные данные и зависимости:** E10-C01…C03; defect register.

**Чёткие технические требования к реализации:** Собрать unit/component/integration/
FSM/MCP/E2E/failure/acceptance результаты.
Добавить отдельный эксплуатационный smoke с реальной локальной 12–14B моделью:
он не входит в стандартную сетенезависимую CI, но подтверждает реальную интеграцию.
Класс модели — `A-22` (`02` §5.3); протокол smoke фиксирует модель, квантизацию, среду и commit.
Зафиксировать отсутствие известных critical defects и открытых mandatory blockers.

**[ОБЯЗАТЕЛЬНО] Требования к Unit-тестированию:** Missing mandatory suite;
critical defect; открытые блокеры `P0` (`INDEX.md` §9.1); результаты другого commit;
неуспешный real-model smoke; неподписанный acceptance record.
Моки: evidence bundle и defect registry.

**Критерии приёмки:** Автоматический валидатор не допускает ложный PASS;
M9 фиксируется только после фактической приёмки; DOD-ALL.
