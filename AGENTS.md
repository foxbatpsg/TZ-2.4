# AGENTS.md — правила работы с ТЗ v2.6 «Research Prompt Suite»

> Этот файл — точка входа для **любого** агента в любой среде (OpenCode, Cline, Cursor,
> WorkBuddy, CLI). Он содержит всё необходимое для безопасной правки нормативного корпуса
> ТЗ. Если среда поддерживает skills — детальная версия этих же правил лежит в
> `.workbuddy-ai/skills/tz-index-maintenance/SKILL.md`, но **для работы достаточно этого файла**.

## 1. Что это за проект

Техническое задание v2.6 на систему «Research Prompt Suite» — нормативный корпус объёмом
~340 КБ (14 файлов). Корпус **вырос до объёма, при котором последовательное чтение
неприемлемо**, поэтому в проекте есть навигационный слой `INDEX.md`.

Реальная ошибка, ради предотвращения которой всё построено: ревьюер объявил эпики
`EPIC-07…11` «отсутствующими» — хотя они существуют в
`приложения к ТЗ/EPIC SPECIFICATIONS v1.0 — BASELINE.md` стр. 168–245. Он просто не нашёл
их в объёме.

**Следствие: никогда не искать норму чтением корпуса целиком. Только через `INDEX.md`.**

**Формат нормативного определения единообразен и обязателен:**


Именно по этому шаблону валидатор отличает **определение** от **упоминания**. Соблюдение
шаблона при добавлении нормы — обязательное условие.

## 4. Рабочий процесс: пять шагов

### Шаг 0. Прежде чем задать пользователю вопрос — проверить корпус

⛔ **Обязательно.** Любой вопрос вида «нужно ли что-то внести / добавить / изменить» разрешено
задавать **только после поиска по тексту корпуса**. Запрещено строить варианты ответа на общем
смысле термина — только на фактах.

1. Прогнать поиск по всем нормативным файлам и приложениям:
   ```bash
   grep -rn "<термин>" --include="*.md" . | grep -v "^./корзина"
   ```
2. Определить качество каждого вхождения: **норма** в ТЗ/приложении · **критерий Gate** ·
   **задача** (`E0x-Tyy`) · **позиция реестра** (`S-xx`/`N-xx`/`D-x`) · **упоминание** внутри
   другого замечания · **производное** (`ARCHITECTURE.md`).
3. **Внести результат поиска в сам вопрос** — таблицей «где встречается / что это / статус».

Пользователь не видит корпус и не может сам проверить полноту. Если пересказ неполон (пропущена
норма, критерий Gate или неразобранная позиция реестра), решение принимается вслепую и позже
откатывается. **Достоверность вопроса — ответственность агента, а не пользователя.**

**Признак нарушения:** в вопросе есть рассуждение о смысле, но нет результата поиска по корпусу.

### Шаг 1. Найти норму по `INDEX.md`, а не по корпусу

| Вопрос | Раздел `INDEX.md` |
|---|---|
| Где лежит правило? | §3 Реестр норм `A-xx` |
| Какая норма за что отвечает? | §3 + §4 (`Q-xx`) |
| Где описана сущность? | §5 Карта сущностей |
| Где Gate? | §6 Карта Gate |
| Какой эпик? | §7 Карта EPIC |
| Где механизм (pipeline, FSM, бюджет)? | §8 Карта механизмов |
| Известные дефекты | §9 |

Затем читать **только** целевой фрагмент: файл плюс указанную строку.

### Шаг 2. Проверить `canonical` и связанные решения

Ключевое поле реестра — `canonical` (первичный источник). Оно критично, потому что многие
нормы определены **несколько раз** в разных файлах с разными акцентами. Зафиксированный
масштаб: `A-03` — 9 определений, `A-11`/`A-16` — по 5, ещё 18 норм — от 2 до 4.

При работе с многократно определённой нормой:
1. Взять формулировку из `canonical` как основную.
2. Сверить остальные вхождения (`mentions`) на расхождение.
3. Найденное расхождение внести в поле `conflicts` и в §9 индекса.

**Не выбирать удобное определение произвольно** — это создаёт вторую «истину».

### Шаг 3. Внести правку — шесть правил

1. **Сохранять формат определения** `Название (A-N): текст` — иначе норма выпадет из реестра.
2. **Не менять нормативные ID.** `A-13` остаётся `A-13`. Перенумерация ломает ~90 перекрёстных
   ссылок в приложениях и все TASK-карточки.
3. **Обновлять `INDEX.md` тем же изменением**, что и нормативный текст. Индекс, отставший от
   корпуса, хуже отсутствующего.
4. **Не дублировать текст нормы в индексе.** Индекс хранит адрес и связи (`canonical`,
   `mentions`, `conflicts`, `gates`, `epics`), а не формулировку.
5. **Не разрешать противоречие самостоятельно.** При конфликте норм — зафиксировать в §9 индекса
   и в `REVIEW-REGISTRY.md`, затем `STOP → REPORT`.
6. **Правки P0-блокеров** (`N-01` MCP-host, `S-12`/`Q-08` Document identity, `N-02`
   SourceRelation) — только после принятия соответствующего ADR. До этого зависимые задачи
   помечать `BLOCKED`.

### Шаг 4. Обязательная валидация перед завершением

Валидатор — обычный Python-скрипт, работает в **любой** среде:

```bash
python .workbuddy-ai/skills/tz-index-maintenance/scripts/validate_index.py
```

Проверяет шесть вещей: разрешимость ссылок на файлы, полноту реестра норм, отсутствие
фантомных записей, дубли определений, нормы без определения, покрытие Gate.

**Успех — код возврата `0` и строка `РЕЗУЛЬТАТ: PASS`.** Ненулевой код означает, что индекс и
корпус разошлись — правку нельзя считать завершённой.

#### Если `python` не найден

Имя интерпретатора зависит от среды. Пробовать по очереди:

```bash
python3 .workbuddy-ai/skills/tz-index-maintenance/scripts/validate_index.py   # Linux / macOS
py -3 .workbuddy-ai/skills/tz-index-maintenance/scripts/validate_index.py     # Windows launcher
python .workbuddy-ai/skills/tz-index-maintenance/scripts/validate_index.py    # общий случай
```

Скрипт не требует внешних зависимостей — только стандартная библиотека Python 3.8+.
Если нужно указать корень корпуса явно (например, запуск из другого каталога):

```bash
python .workbuddy-ai/skills/tz-index-maintenance/scripts/validate_index.py --root "C:/путь/к/ТЗ 2.4"
```

## 5. Типовые ситуации

### Добавление новой нормы
1. Выбрать следующий свободный ID (`A-22`, `Q-09`).
2. Сформулировать по шаблону `Название (A-N): текст` в соответствующем разделе ТЗ.
3. Внести запись в `INDEX.md` §3 (или §4): ID, название, `canonical`, `mentions`.
4. Проверить, не конфликтует ли норма с действующими.
5. Прогнать валидатор.

### Создание нового нормативного реестра
Норма упоминается как часть набора («УИ v1.0: A-01…A-21»), но самого реестра в корпусе нет.
1. **Место — по §19 «Нормативные источники»** `MASTER ROADMAP`, а не по признаку «где
   поставлен якорь». Реестр живёт на уровне, назначенном ему §19, и в документе, который уже
   определяет нормы этого уровня.
2. **Дублировать только то, у чего нет определения.** Норма без собственного определения →
   полный текст (текст + источник + обоснование + критерий приёмки). Норма, определённая в
   ТЗ `01`–`07` → только адрес: ID → где определено → краткое содержание. Копирование
   формулировки создаёт вторую «истину» — класс дефекта `D-4`.
3. **Обновить трассировку** из всех мест, где норма цитировалась как примечание.
4. **Валидатор:** рост счётчика определений нормы — ожидаем и не является дефектом, если
   `canonical` указывает один первичный источник.

Проверенный пример: реестр «УИ v1.0» (`A-01…A-21`, `Q-01…Q-05`) — §19 ставит его в пункт 1
(выше EPIC-документа); размещён в `MASTER ROADMAP v1.2` §21, полное определение получил только
`A-01`, остальные — адресную таблицу §21.2.

### Задокументированный пропуск нумерации
Если ID отсутствует в корпусе намеренно — пометить в `INDEX.md` значением
`status: gap` со ссылкой на §9. Валидатор требует и включения в `ALLOWED_GAPS`, и отдельной строки реестра с этим статусом; сейчас намеренных пропусков нет.
**Молчаливый пропуск недопустим** — приоритет имеет явное указание, а не порядковый номер.
Открытые вопросы без утверждённого определения учитываются отдельно: `OPEN_QUESTIONS` и отдельные строки §4 с `status: open`. После утверждения и переноса решения исключение удаляется; черновик не становится `canonical`. Проверенный перенос: `Q-06` (2026-09-16) — определение внесено в нормативный файл по шаблону (`05` §4b), строка реестра §4 переведена в закрытый статус, запись удалена из `OPEN_QUESTIONS` валидатора.

### Норма используется, но не определена
Это **дефект корпуса**, а не повод придумать формулировку. **Не спешить классифицировать как
«утрату данных»**: проверенный случай `A-01` оказался **дефектом миграции** — правило
сохранилось, но при переносе было свёрнуто до проекции с потерей источника, обоснования и
критерия приёмки.

**Порядок действий:**
1. **Поискать формулировку в старых файлах проекта** (проверенный приём, давший результат для
   `A-01`). Искать по названию нормы, её теме и фрагментам применений — не только по ID.
2. Сверить найденный текст с применениями в корпусе.
3. Если найдено — зафиксировать в `REVIEW-REGISTRY.md` как `RESOLVED`, указав диагноз
   (дефект миграции / утрата данных), потерянные составные части и требуемое действие.
4. Если не найдено — пометить `status: defect` и представить на утверждение человеку.

**Не изобретать нормативный текст.** Восстановленная формулировка вносится в корпус только
после утверждения, и вносится дословно, без редактуры.

**У восстановленной нормы проверять три части:** источник правила, обоснование, критерий
приёмки. Именно их теряют при свёртке в Change Log — без них норма становится непроверяемой.

### Написание TASK-карточки
Ссылаться на нормы **по ID**: `REQUIREMENTS: A-13, Q-02, N-01`. **Не** по номерам разделов
(`ALLOWED_FILES: Разделы 02 и 05`) — такие ссылки ломаются при любой перенумерации. Для
P0-блокеров указывать `BLOCKED_BY` с ID соответствующего ADR.

## 6. Границы: что агент делать не должен

- **Не читать `корзина/`.** Папка исключена из области работы.
- **Не принимать архитектурных решений.** При конфликте норм или неутверждённом ADR —
  `STOP → REPORT`, а не самостоятельное разрешение.
- **Не перенумеровывать нормы** и не менять ID.
- **Не править код приложения, TASK-карточки Astra1, файлы замечаний** — они производные.
- **Не считать `ARCHITECTURE.md` источником истины** — при конфликте приоритет у ТЗ.
- **Не изобретать формулировки** отсутствующих норм.
