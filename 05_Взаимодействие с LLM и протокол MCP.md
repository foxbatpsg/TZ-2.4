# НАЦИОНАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ) v2.7
## Раздел 5. Взаимодействие с LLM и протокол MCP

**Статус:** Утвержденный архитектурный контракт (Финальная монолитная редакция)
**Назначение:** Определение интерфейсов стыковки локальной ИИ-модели с программным ядром через протокол MCP, механизмов защиты контекста, отказоустойчивости и валидации.

---

## 1. Локальный ИИ-бэкенд (Local LLM)

Система проектируется под локальные ИИ-модели: минимально поддерживаемый класс 12–14B (A-22), верхняя граница размера не нормируется. В качестве поддерживаемых локальных сред выполнения (бэкендов) на уровне ядра фиксируются:

- **LM Studio** (локальный HTTP-сервер, совместимый с OpenAI API);
- **Ollama** (локальный REST API);
- Другие совместимые локальные HTTP-интерфейсы, предоставляющие стандартный порт для взаимодействия.

Локальная ИИ-модель выступает исключительно вычислительным слоем для интерпретации семантики и текстового синтеза. Она отвечает за понимание целей исследования (intent interpretation), планирование направлений поиска (planning), генерацию поисковых гипотез, смысловой анализ и сопоставление извлеченных цитат, поиск текстовых противоречий и финальный синтез отчета.

**Жесткое ограничение:** Локальная ИИ-модель принципиально не является источником фактов. Гарантируется только проверяемое: структурная валидация вывода, существование указанных идентификаторов (Source ID / Evidence ID) и точное совпадение приведенных цитат с текстом документов (N-03) — всё, что не проходит эти проверки, отбрасывается на этапе валидации. Семантическая поддержка (то, что цитата действительно подтверждает утверждение) автоматической проверке не поддается и не гарантируется — см. §12.

## 2. Маршрутизатор ИИ-бэкендов (LLM Backend Router)

Для обеспечения непрерывности процесса исследования при зависании или падении локальной нейросети, в программное ядро внедряется изолированный компонент — **LLM Backend Router**.

Компонент состоит из следующих обязательных модулей:

- **Health Monitor** — фоновый информер, осуществляющий регулярную отправку легковесных пингов к ИИ-бэкенду для замера задержки и доступности;
- **LLM Controller** — модуль управления процессами, отвечающий за инициализацию, остановку и конфигурацию параметров инференса;
- **Backend Router** — интеллектуальный переключатель, перенаправляющий потоки токенов на альтернативный локальный порт в случае отказа основного бэкенда;
- **Session Resume** — диспетчер восстановления контекста, отвечающий за реанимацию состояния исследования после сбоя.

Маршрутизатор в режиме реального времени присваивает ИИ-интерфейсу один из четырех фиксированных статусов: **HEALTHY** (исправен, готов к работе), **DEGRADED** (доступен, но скорость генерации или время отклика упали ниже критического порога), **UNREACHABLE** (бэкенд физически не отвечает на запросы), **RESTARTING** (запущен процесс перезагрузки локальной среды).

При переходе системы в статус аварии данные исследования не теряются — все накопленные к этому моменту в SQLite таблицы Evidence, Observation и ResearchState остаются полностью консистентными на диске.

Версионирование и переключение backend (`A-18`): backend/model/tokenizer profile версионируется в составе ревизии `ResearchConfig` и версионируется **отдельно от business thresholds** — переключение backend не меняет пороги достаточности и историю Study. Восстановление после сбоя восстанавливает последнюю активную ревизию конфигурации и никогда не меняет правила достаточности. Переходы статусов backend выполняются только через нормативную FSM (STATE MACHINE SPECIFICATION v1.2, §5); состояние backend — runtime/operational и не хранится в `ResearchSession.budget_state`.

## 3. Протокол Model Context Protocol (MCP)

Стыковка ИИ-модели с программными функциями ядра (поиск, чтение файлов, логирование) осуществляется строго по открытому протоколу MCP (Model Context Protocol) от Anthropic.

> **Уточнение (N-01, ADR-001).** MCP — протокол **вызова инструментов**, а не протокол инференса. Настоящее правило означает: любой вызов инструмента ядра проходит через MCP-контракт инструмента — независимо от профиля исполнения. Оно **не** означает, что LLM обращается к ядру через MCP: обращение к модели выполняется отдельным каналом (`05` §1–2) и через MCP не идёт. Транспорт stdio применяется в профиле headless `--mcp-stdio`; в профиле desktop orchestration (по умолчанию) вызовы инструментов исполняются в том же процессе через единый ToolDispatcher. Профили исполнения и владелец агентного цикла — `02` §3a.

В качестве базового транспортного слоя для MVP утверждается механизм **stdio** (стандартные потоки ввода-вывода).

**Системное правило изоляции потоков:**

Поток `stdout` процесса MCP-сервера зарезервирован исключительно для передачи структурированных пакетов JSON-RPC. Категорически запрещено выводить в `stdout` обычные текстовые логи приложения, отладочную информацию, stacks ошибок Python или системные уведомления — все они в обязательном порядке перенаправляются в изолированный лог-файл на диске или в поток ошибок `stderr`.

Runtime stdout protection (A-20): система обязана перехватывать непреднамеренный вывод в `stdout` (например, от сторонних библиотек) **не разрушая транспорт** — перехват выполняется на уровне защитной обёртки процесса, которая изолирует посторонний вывод в лог, не прерывая поток JSON-RPC. Попадание debug-вывода в транспорт фиксируется как ошибка теста (раздел 7 ТЗ, §19.1).

Каждый инструмент (tool), предоставляемый ИИ-модели через MCP, обязан обладать жестко заданной схемой входных параметров (input schema), структурой выходных данных (output schema), уникальными кодами ошибок, строго очерченными лимитами на объемы данных, детерминированным поведением вне ИИ и компактным результирующим выводом.

### 3.1. Дополнительные меры защиты транспортного слоя

1. **Ранний редирект логгеров:** В самой ранней точке запуска MCP-сервера (до инициализации любых модулей) все логгеры перенаправляются в файл или поток ошибок. Запрещено наличие любого логгера, выводящего в `stdout`.

2. **Защита от случайного вывода:** Транспортный слой оборачивается валидирующей обёрткой, которая проверяет, что в `stdout` записывается только корректный JSON-RPC. Попытка записать не-JSON блокируется и логируется.

3. **Линтер в CI:** Автоматическая проверка исходного кода на наличие вызовов `print()` и `sys.stdout.write` вне разрешённых мест. Обнаружение таких вызовов блокирует сборку.

4. **Обработка исключений:** Необработанные исключения и их трассировки не должны попадать в `stdout`. Все исключения перехватываются и перенаправляются в файл или поток ошибок.

### 3.2. Egress policy — недоверенные адреса (N-03)

URL-адреса, порожденные ИИ-моделью, считаются **недоверенными данными**: ошибка, галлюцинация или инструкция, внедренная в недоверенный контент (косвенный prompt injection), не должна достигать сетевого слоя. Механизм детерминированный и не различает, почему адрес недоверен, — защита работает одинаково против ошибки модели и против злонамеренного контента. Проверка выполняется кодом ядра до каждого сетевого обращения, вне LLM:

1. **Запрет локальных и внутренних адресов:** блокируются loopback, приватные и link-local диапазоны (127/8, 10/8, 172.16/12, 192.168/16, 169.254/16, ::1, fc00::/7), включая служебные адреса облачных провайдеров (например, сервис метаданных 169.254.169.254).
2. **Ревалидация редиректов:** каждый переход по перенаправлению проходит ту же проверку цели — переход с внешнего адреса на заблокированный блокируется.
3. **Лимиты объема:** ответ ограничен `max fetch size` из `ResearchConfig` (default 5 MiB) и на скачивание, и на распаковку (защита от decompression bomb); превышение — отказ без приема данных.
4. **Без повторов:** нарушение возвращает типизированную сетевую ошибку; повторные обращения к заблокированному адресу не выполняются.

**Журналирование нарушений (N-03):** каждое нарушение egress policy фиксируется в локальном журнале как событие категории «безопасность»: тип нарушения, схема и host целевого адреса (без query-строки и пути), вызванный инструмент, счетчик попыток. Записи подчиняются правилам журнала из §7 раздела 02 (redaction, локальное хранение, без сетевой отправки). Журналирование фиксирует попытку постфактум и не отменяет блокировку: блокировка выполняется на сетевом уровне до журналирования.

### 3.3. Query egress policy — приватное содержимое запросов (Q-10)

**Query egress policy (Q-10):** egress policy (§3.2) ограничивает, **куда** уходят сетевые обращения; настоящая норма ограничивает, **что** в них уходит. Локальные материалы пользователя считаются приватными по умолчанию.

1. **Политики egress** на уровне `ResearchConfig`/`InputConfig`: `PUBLIC_ONLY` (по умолчанию) и `PRIVATE_ALLOWED` (только по явному действию пользователя). Режим `MATERIALS_ONLY` физически блокирует сеть полностью (`02` §4) и от этих политик не зависит.
2. **Запрет приватного фрагмента в запросе:** при политике `PUBLIC_ONLY` ядро не отправляет внешний поисковый запрос, если текст запроса содержит совпадение с текстом локальных документов Study — проверка по чанкам `DocumentChunk` локальных документов: совпадение нормализованной подстроки длиной не менее `query_leak_threshold` символов (default 32, параметр конфигурации).
3. **Явно публичный вход:** пользователь может пометить входные данные как публичные (явное действие в GUI/конфигурации); помеченные материалы исключаются из проверки п.2.
4. **Секреты** (credentials/токены) не выводятся в журналы и отчёт (A-17, `07` §24); отчёт содержит только пометку происхождения материала (локальный/внешний).

Нарушение п.2 — типизированная ошибка с рекомендацией переформулировать запрос; попытка фиксируется в журнале по правилам §3.2.

## 4. Список инструментов MCP (MCP Tools)

На этапе MVP ядро предоставляет локальной ИИ-модели следующий фиксированный набор атомарных инструментов:

### Группа планирования (Planning)

- **plan_research** — передача ИИ-модели структуры ResearchIntent для генерации первичных гипотез и направлений поиска.

### Группа внешнего поиска (Retrieval)

- **search_web** — поиск в глобальной сети Интернет через подключенные поисковые адаптеры (выдает строго Top-5/Top-10 компактных кандидатов со сниппетами).
- **search_academic** — специализированный поиск по базам научных публикаций и репозиториям.
- **search_github** — поиск по коду и репозиториям платформы GitHub.
- **search_stackoverflow** — поиск по базе технических вопросов и ответов StackOverflow.
- **search_web_community** — поиск по социальным и контентным платформам (например, Reddit) для сбора пользовательского опыта.

### Группа чтения (Reading)

- **read_url_content** — точечное скачивание и извлечение очищенного текста конкретной веб-страницы, выбранной ИИ из результатов поиска.
- **read_youtube_transcript** — получение текстовой расшифровки видеоряда с платформы YouTube.

### Группа локальных документов (Documents)

- **add_local_document** — регистрация и детерминированный импорт локального файла пользователя в репозиторий проекта.
- **search_within_document** — выполнение локального текстового поиска (BM25) внутри конкретного выбранного документа.

### Группа ведения исследования (Study Management)

- **start_research_session** — инициализация новой итерации адаптивного цикла поиска в ядре.
- **save_study_material** — реляционное сохранение извлеченных материалов и метаданных.
- **search_study_materials** — локальный поиск по чанкам документов, уже привязанных к текущему исследованию через таблицу связей.
- **get_research_session_statistics** — получение сухих цифр о текущей сессии (кол-во скачанных страниц, остаток бюджета).
- **get_study_dashboard** — запрос компактного операционного статуса исследования.

### Группа рабочей памяти (Memory)

- **update_working_memory** — запись краткой текстовой шпаргалки текущих результатов в базу данных (лимит до 200 токенов).
- **get_working_memory** — чтение текущего наполнения текстовой шпаргалки.

### Группа диагностики и кэша (Cache / Diagnostics)

- **get_cache_statistics** — получение данных о наполненности и эффективности сетевого кэша.
- **get_cache_diagnostics** — выявление устаревших или заблокированных доменов в кэше.
- **cleanup_expired_cache** — принудительная очистка записей с истекшим сроком жизни TTL.

### Группа отчетности (Report)

- **validate_and_save_report** — передача финального текста отчета на серверную валидацию и запись на диск.

### Группа управления фоновыми задачами (Job Management)

- **get_job_status** — получение текущего статуса и прогресса фоновой задачи (см. Раздел 04, раздел 28).
- **cancel_job** — запрос на кооперативную отмену фоновой задачи.

Данный перечень инструментов спроектирован как расширяемый слой. Добавление специализированных инструментов анализа в Post-MVP версиях не имеет права нарушать или требовать переписывания базовых контрактов поискового ядра Search Core.

### 4a. Контракт MCP-инструмента (обязательный шаблон)

Каждый инструмент, предоставляемый через MCP, обязан иметь формально определённый контракт до начала реализации. Контракт является обязательным приложением к спецификации инструмента.

**Шаблон контракта инструмента:**

```
[Имя инструмента]:
├── INPUT: Полная схема входных параметров (типы, обязательность, диапазоны)
├── OUTPUT: Структура выходных данных (поля, типы, лимиты)
├── ERRORS: Перечень возможных кодов ошибок из единого словаря
├── LIMITS: max_output_bytes, max_items, max_text_length
├── TIMEOUT: Максимальное время выполнения в секундах
├── RETRY POLICY: Допустимость и правила повторных попыток
├── SIDE EFFECTS: Какие данные создаются/изменяются при вызове
├── IDEMPOTENCY: Поведение при повторном вызове с теми же параметрами
├── CANCELLATION: Механизм отмены (для синхронных — таймаут, для Job — cooperative)
└── AUTHORITY: Какой компонент принимает решение (ядро или LLM)
```

**Правила:**

1. Ни один инструмент не может быть реализован без предварительного утверждения контракта.
2. Изменение контракта требует версионирования и уведомления всех потребителей.
3. Контракт проверяется автоматическими тестами (см. Раздел 07).
4. Для инструментов, создающих сущности в БД, контракт обязан указывать `idempotency_key`.

### 4b. Передача контекста доказательства через MCP (Q-06)

**Передача контекста доказательства через MCP (Q-06):** контекстный коридор ±1 (`04` §15) доставляется LLM-модели существующим инструментом `search_within_document`; отдельный (24-й) инструмент для контекста не вводится, «теневые» инструменты запрещены (`02` §3a, ADR-001).

1. **Опция контекста.** Контракт `search_within_document` расширяется read-опцией `include_evidence_context: boolean` (default `true`): коридор включён в ответ по умолчанию, LLM может запросить отключение опцией. При `true` ответ обязан содержать: идентификатор и версию Document (A-21, Q-08); целевой чанк и соседние чанки коридора ±1; ID соседних чанков; интервалы `[char_start, char_end)` целевого и соседних чанков; точный текст фрагментов. Сборка коридора и устранение дублирования — по правилам `04` §15, §15.1 (A-06).
2. **Лимит ответа.** Лимит `search_within_document` увеличен с 8 KiB до 32 KiB — стартовое значение для ответа с контекстом; окончательное значение подтверждается тестами контракта (`07`); превышение — `RESPONSE_TOO_LARGE` (§18).
3. **`save_study_material` не расширяется.** Он не используется как механизм передачи полного контекста доказательства; его лимит 4 KiB остаётся ограничением payload сохраняемой сущности (метаданные, не коридор).

Изменение контракта зарегистрировано в `MCP TOOL CONTRACTS v1.1` §3 (правило 2 §4a о версионировании изменений).

## 5. Принцип атомарности инструментов (Tool Granularity)

Каждый инструмент MCP обязан выполнять строго одну элементарную, прозрачную операцию. Создание комплексных инструментов-комбайнов вида `search_and_read_everything` или `run_complete_research` категорически запрещено.

ИИ-модель обязана самостоятельно выстраивать логическую последовательность дискретных шагов:

```
Вызов инструмента search_*
    ↓ [ИИ получает список ссылок-кандидатов и сниппетов]
Логический выбор ИИ конкретного релевантного URL
    ↓
Вызов инструмента read_url_content для выбранной ссылки
    ↓ [Ядро скачивает, нарезает документ и индексирует чанки]
Вызов инструмента search_within_document для точечного извлечения цитат
```

## 6. Контракт поиска кандидатов (Candidate Retrieval Contract)

Инструменты группы `search_*` возвращают ИИ-модели исключительно компактные метаданные кандидатов (Top-5 или Top-10 результатов), включающие в себя: каноничный URL-адрес, заголовок страницы из выдачи, короткий сниппет длиной до 200 символов, идентификатор источника, дату публикации и расчетный балл релевантности.

Массовая автоматическая загрузка полных текстов документов на этапе первичного поиска полностью заблокирована на уровне программного контракта инструмента. Полный текст скачивается только тогда, когда ИИ осознанно вызывает инструмент точечного чтения `read_url_content`.

---

## 7. Механизм Working Memory

Инструмент `update_working_memory(summary)` позволяет ИИ-модели сохранять на стороне сервера краткую смысловую выжимку текущего прогресса. Для этого поля вводится жесткое ограничение объема: не более 200 токенов текста.

Объект WorkingMemory служит исключительно для того, чтобы модель не теряла нить рассуждения при смене фаз, и принципиально не может использоваться разработчиками в качестве замены системных таблиц ResearchState, EvidenceStore, ClaimTable или механизмов сохранения контекста в SQLite.

## 8. Информационная панель исследования (Dashboard Contract)

Инструмент `get_study_dashboard` возвращает ИИ-модели строго лаконичный, агрегированный снимок текущего операционного состояния исследования.

В контракте дашборда зафиксирована передача следующих параметров:

- наименование текущей активной фазы исследования;
- актуальный остаток многомерного бюджета (количество доступных сетевых вызовов, лимит ИИ, остаток времени);
- число верифицированных цитат в Evidence Store;
- количество сформулированных утверждений Claims;
- список обнаруженных, но еще не разрешенных числовых и логических противоречий Contradictions;
- перечень открытых на данный момент пробелов в знаниях ResearchGaps;
- детерминированная системная рекомендация ядра Core по приоритетному направлению следующего шага.

Цель дашборда — предоставить ИИ актуальную карту исследования на каждом шаге генерации без необходимости перечитывания всей длинной истории предыдущих вызовов инструментов, что экономит контекстное окно локальной модели.

## 9. Двухэтапное планирование (Plan-and-Solve)

Построение плана исследования выполняется по строгому двухэтапному регламенту, исключающему хаотичную активность ИИ:

1. **Гипотезы:** ИИ-модель анализирует входящий вопрос пользователя и генерирует направления поиска и текстовые гипотезы.
2. **Нормализация:** Программное ядро Python перехватывает этот текст и детерминированно преобразует его в строго структурированный черновик плана (Draft Plan), состоящий из конкретных задач SearchTask.
3. **Корректировка:** ИИ-модель знакомится со структурированным Draft Plan и имеет право внести точечные корректировки или подтвердить его.
4. **Валидация:** Ядро Search Core проводит финальную жесткую проверку каждой задачи на предмет дублирования через Query Fingerprint и только после этого открывает бюджет на выполнение.

## 10. Структурированный вывод (Structured Outputs)

Для всех критически важных аналитических операций (извлечение структуры наблюдения Observation, создание карточки пробела ResearchGap, фиксация противоречия Contradiction) система обязана требовать от ИИ-модели возврат данных в строгом формате JSON Schema (используя механизмы Structured Outputs на уровне бэкендов Ollama/LM Studio).

Независимо от поведения и качества генерации модели, программный сервер Search Core осуществляет стопроцентную повторную детерминированную валидацию полученного JSON-пакета на соответствие типам данных реляционных таблиц SQLite.

Статус JSON (`A-03`): структурированный JSON — это **API-сериализация** входа/выхода LLM, а не параллельный источник истины. Источник истины — нормализованные таблицы SQLite (раздел 3 ТЗ); JSON-пакеты не участвуют в JOIN и фильтрации.

### 10.1. Обработка повреждённого JSON от ЛЛМ

Для промежуточных структурированных объектов (Observation, ResearchGap, Contradiction, Evidence metadata) система реализует слой извлечения и восстановления:

1. **Извлечение:** Попытка извлечь валидный JSON из ответа модели, включая обработку ```json-блоков и незначительных синтаксических ошибок.
2. **Валидация:** Строгая проверка извлечённого объекта через схему, отражающую типы реляционных таблиц SQLite.
3. **Логирование:** Фиксация факта восстановления (был ли исходный ответ повреждён).

**Критическое разграничение:**

- Для **ПРОМЕЖУТОЧНЫХ объектов** (наблюдения, пробелы, противоречия): Допускается восстановление синтаксиса при условии, что семантическое содержание не изменяется.
- Для **ФИНАЛЬНОГО ОТЧЁТА** (`validate_and_save_report`): Автоматическая правка категорически запрещена. Только строгая валидация и возврат ошибки при несовпадении.

Если восстановленный объект не проходит валидацию схемы — он отбрасывается, и модель получает запрос на повторную генерацию с указанием конкретных ошибок.

## 11. Ограничение входящего контекста ИИ (Context Protection)

Программное ядро берет на себя обязательство по жесткой фильтрации и усечению объемов информации, передаваемой локальной ИИ-модели.

В промпты ИИ категорически запрещено передавать сырые HTML-коды сайтов, избыточные логи, длинные списки отброшенных дубликатов ссылок или полные тексты многостраничных документов. Модели передаются строго: релевантные текстовые чанки с коридором ±1 соседний абзац, верифицированные цитаты Evidence, очищенные метаданные документов, актуальное состояние рабочей памяти Working Memory и список открытых пробелов ResearchGaps.

### 11a. Управление бюджетом контекста при формировании промптов

При формировании каждого промпта для LLM ядро обязано применять расчёт бюджета контекста, описанный в Разделе 02, секция 6a (TokenBudgetManager).

**Правила применения:**

1. Перед каждым вызовом LLM ядро вычисляет доступный `evidence_budget`.
2. Расчёт выполняется по режимам контекста (`A-12`): `fixed` / `auto` (backend, иначе fallback) / `auto_with_config_cap = min(auto, cap)`. Неизвестный backend limit трактуется как «неизвестно» (fallback), а не как 0; надёжность значения контекста от backend проверяется при переключении backend — сомнительные значения не обнуляют бюджет.
3. Если объём передаваемых чанков превышает `evidence_budget`:
   - Уменьшить число Evidence в одном вызове.
   - Уменьшить число чанков в контекстном коридоре (но не ниже ±1 для target).
   - Уменьшить размер чанков при новых нарезках.
4. Если минимальный контекст не собирается (в т.ч. отрицательный `evidence_budget`):
   - Вернуть ошибку `CONFIG_CONTEXT_INSUFFICIENT`.
   - Не выполнять вызов LLM с заведомо обрезанным промптом.
5. Фактический объём переданного контекста логируется для аудита.

**Запрещено:**

- Молча обрезать контекст без уведомления и логирования.
- Передавать промпт, превышающий `effective_context`.
- Игнорировать `output_reserve` при расчёте.

## 12. Контроль доказательности (Evidence Control)

Любое существенное аналитическое утверждение (Claim), зафиксированное ИИ-моделью в отчете, обязано иметь жесткую реляционную привязку к конкретному уникальному ID доказательства в таблице ClaimEvidence.

Каждое доказательство, в свою очередь, должно содержать проверяемый глобальный идентификатор источника: валидный веб-URL, постоянный научный индекс DOI, PMID или arXiv ID. ИИ-модель полностью лишена права самостоятельно придумывать, дописывать или модифицировать идентификаторы источников. Если для ответа на вопрос в базе данных не обнаружено верифицированной цитаты, модель обязана присвоить утверждению статус **INSUFFICIENT_EVIDENCE** (Недостаточно доказательств), детально описать нехватку информации и сформировать объект пробела ResearchGap.

Граница гарантий (N-03): ядро детерминированно проверяет структурную валидность отчета, существование всех указанных идентификаторов и точное совпадение приведенного текста цитаты с `DocumentChunk` (§14). Семантическая поддержка — то, что приведенная цитата действительно подтверждает утверждение, — автоматической проверкой не обеспечивается и **не гарантируется**: она выносится в показатель `confidence` с пометкой `uncertain` и доступна для ручной проверки пользователем.

## 13. Обработка заблокированных источников (Paywall / Unavailable Source)

В случае если при вызове инструмента точечного чтения `read_url_content` программное ядро сталкивается с технической невозможностью извлечения текста (сайт закрыт платным экраном paywall, требует авторизации, выдает ошибку доступа 403 или заблокирован капчей), инструмент возвращает ИИ-модели фиксированный системный маркер: **FULL_TEXT_UNAVAILABLE**.

При получении данного маркера система фиксирует в отчете:

- наименование и URL-адрес недоступного источника;
- структурированный код ошибки доступа;
- описание предпринятой попытки извлечения текста;
- ознакомительный сниппет или абстракт (если они были сохранены на этапе Candidate Retrieval).

Программное ядро имеет право автоматически предложить ИИ-модели переключиться на альтернативного кандидата из очереди, но жестко блокирует любые попытки модели выдумать содержимое недоступной страницы или выдать текст другого сайта за информацию из заблокированного источника.

## 14. Серверная валидация отчетов

Инструмент финальной фиксации результатов `validate_and_save_report` запускает комплексную программную проверку переданного ИИ-моделью Markdown- или JSON-отчета на стороне ядра Python.

Программа в детерминированном режиме проверяет:

- строгое соблюдение синтаксиса разметки и целостность JSON-схемы;
- наличие всех обязательных системных полей и соответствие типов данных;
- реальное существование в БД всех указанных в отчете идентификаторов Source ID и Evidence ID. Связи проверяются физическим JOIN-запросом к таблицам SQLite;
- точное совпадение цитаты (N-03): приведенный в доказательстве текст обязан совпадать с текстом соответствующего `DocumentChunk` по указанным offsets или по хешу текста цитаты. Несовпадение — отклонение отчета с типизированной ошибкой (категория `REPORT_VALIDATION_ERROR`, причина `QUOTE_MISMATCH`); каждое такое отклонение фиксируется в локальном журнале как событие нарушения валидации (без текста цитаты и содержимого документов — по правилам журнала из §7 раздела 02);
- корректность выставленных статусов достоверности (status) и показателей уверенности (confidence) относительно накопленной статистики.

При обнаружении синтаксических ошибок или разрывов реляционных связей, ядро Core полностью блокирует запись отчета на диск, возвращает ИИ-модели компактное, детальное описание ошибки форматирования (с указанием строки или пропущенного ID) и отправляет её на шаг исправления. Автоматическая «тихая» правка JSON на стороне сервера, способная непредсказуемо исказить аналитический смысл выводов ИИ, категорически запрещена.

Бюджетный аспект (`Q-04`): `validate_and_save_report` **не списывает `llm_call_budget`**, если сам не запускал LLM-вызов; тарификация определяется BUDGET CONTRACT v1.0.

## 15. Частичные прерванные отчеты (Partial Report)

В случае если в процессе генерации итогового аналитического материала произошел критический обрыв связи с ИИ-моделью, таймаут бэкенда или принудительная остановка со стороны пользователя, ядро системы активирует процедуру частичного сохранения данных:

1. Программа сканирует сгенерированный массив, отсекает поврежденные или недописанные куски текста и сохраняет в базу данных исключительно стопроцентно валидные, завершенные и прошедшие реляционную проверку аналитические объекты.
2. Исследованию присваивается промежуточный операционный признак результата **REPORT_TRUNCATED_PARTIAL**. Внимание (`A-02`): `REPORT_TRUNCATED_PARTIAL` и `PARTIAL_REPORT` **не являются состояниями** Study/ResearchSession — это метаданные результата финализации (result status), фиксируемые в metadata/LogRecord; состояния Study описаны только в STATE MACHINE SPECIFICATION v1.2.
3. Формируется точный структурированный перечень элементов, которые модель не успела сгенерировать до момента обрыва.
4. При восстановлении сессии и запуске догенерации, ИИ-модели в промпт передается данный перечень, и вычислительные ресурсы тратятся строго на дописывание отсутствующих элементов без полной повторной перегенерации всего объема отчета с нуля.

## 16. Единый контракт системных ошибок (Error Contract)

Любой сбой, возникший в процессе работы MCP-инструментов, сетевых адаптеров или модулей ядра, обязан приводиться к единому стандартизированному формату ответа JSON-RPC Error.

Разделение типов ошибок (A-19): **protocol error ≠ execution (domain) error**. Нарушения транспортного уровня (некорректный JSON-RPC, неизвестный метод, невалидный envelope) возвращаются стандартными JSON-RPC кодами (-32700…-32603) в корректном envelope. Доменные ошибки исполнения передаются **корректным JSON-RPC ответом** (result/error со строковым доменным `code` из справочника ниже) — произвольный строковый доменный code **не** кладётся в числовое поле JSON-RPC `code`.

**Структура пакета ошибки содержит:**

- **code** — жесткий строковый или числовой код ошибки из системного справочника;
- **message** — краткое человекочитаемое описание сути сбоя на русском языке;
- **retryable** — логический флаг (TRUE/FALSE), указывающий ИИ-модели на допустимость немедленного повторного вызова инструмента;
- **recommendation** — детерминированная инструкция ядра Core для ИИ о рекомендуемом обходном сценарии действия;
- **operation** — наименование вызванного MCP-инструмента, на котором произошел сбой;
- **entity_id** — UUID связанной сущности (документа, задачи, источника) при наличии.

**Базовые коды ошибок MVP:**

`NETWORK_ERROR` (сбой сетевого подключения), `TIMEOUT` (превышение времени ожидания), `RATE_LIMIT` (блокировка частоты запросов хостом), `SOURCE_UNAVAILABLE` (физическое падение целевого сайта), `PARSE_ERROR` (ошибка извлечения текста), `INVALID_INPUT` (некорректные параметры вызова инструмента), `CACHE_ERROR` (сбой модуля кэширования), `DATABASE_ERROR` (критическая ошибка SQLite), `MCP_ERROR` (сбой транспортного слоя stdio), `VALIDATION_ERROR` (несовпадение типов данных на входе Core), `CHUNKING_ERROR` (сбой алгоритма нарезки текста), `RETRIEVAL_PROVIDER_ERROR` (отказ локального движка BM25), `REPORT_VALIDATION_ERROR` (разрыв связей или синтаксический брак в финальном отчете ИИ), `LLM_UNREACHABLE` (падение ИИ-нейросети), `LLM_TIMEOUT` (зависание генерации токенов), `LLM_DEGRADED` (критическая просадка скорости бэкенда), `CONFIG_CONTEXT_INSUFFICIENT` (невозможность собрать минимальный контекст), `RESPONSE_TOO_LARGE` (превышение лимита объёма ответа).

## 17. Жесткие таймауты операций и Watchdog-контроллер

Для предотвращения бесконечного ожидания ответа от зависших внешних сайтов или сбоящих ИИ-моделей, в систему внедряется двухконтурная система временной защиты.

### Контур 1. Таймауты уровня операций (Operation-Level Timeouts):

Каждая атомарная операция MCP-инструмента оборачивается в детерминированный асинхронный таймер. Утверждаются следующие лимиты по умолчанию (конфигурируемые в ResearchConfig):

- выполнение поискового запроса `search_web` — 30 секунд;
- точечное скачивание и парсинг страницы `read_url_content` — 60 секунд;
- локальный поиск внутри документа `search_within_document` — 30 секунд.

Превышение лимита времени (operation timeout) категорически не имеет права мгновенно уничтожать или аварийно завершать весь глобальный процесс взаимодействия по протоколу MCP.

При наступлении таймаута ядро Core выполняет строго заданную последовательность действий спасения:

```
Превышение лимита времени операции (Timeout)
        ↓
Принудительная отмена конкретной асинхронной задачи (Cancel)
        ↓
Регистрация структурированной ошибки в таблице логов БД
        ↓
Фоновый запуск повторной попытки (если это разрешено retry policy)
        ↓
Программная проверка доступности шлюза (Health Check)
        ↓
Переход на обходной сценарий (Fallback) без остановки MCP-сервера
```

### Контур 2. Программный сторож интерфейса ИИ (MCP Watchdog):

Для отслеживания критического зависания самого процесса общения с ИИ-моделью, на уровне интеграционного слоя разворачивается полностью независимый программный сторож — **MCP Watchdog**.

Если процесс обмена сообщениями JSON-RPC полностью перестает подавать признаки активности в течение заданного критического интервала времени, сторож инициирует процедуру жесткой реанимации:

1. Принудительно закрывает и уничтожает зависший, неотвечающий процесс MCP-сервера (terminate process).
2. Осуществляет чистый перезапуск MCP-сервера с нуля (restart MCP server).
3. Извлекает из таблиц SQLite актуальный срез операционной памяти и последнюю контрольную точку сессии (restore session state).
4. Активирует режим **SESSION_RESUMING** и плавно продолжает прерванное исследование или ставит его на управляемую паузу в соответствии с текущей конфигурацией Core Policy.

Программный сторож MCP Watchdog функционирует изолированно от СУБД и ни при каких условиях не имеет права нарушать реляционную консистентность или приводить к повреждению файлов базы данных SQLite.

## 18. Жесткие лимиты на объемы ответов инструментов (MCP Output Limits)

Каждый инструмент, доступный ИИ-модели, обязан содержать внутренние программные барьеры, ограничивающие максимальный физический размер возвращаемого текстового ответа.

Утверждаются следующие базовые лимиты безопасности для MVP:

- **max_output_bytes** — максимальный объем возвращаемой JSON-строки в байтах;
- **max_items** — предельное количество элементов (например, ссылок или чанков) в одном ответе инструмента;
- **max_text_length** — ограничение на суммарное количество символов текста в ответе.

В случае если результирующий текстовый массив, сгенерированный поисковым или читающим модулем, превышает установленный в контракте лимит безопасности, ядро Search Core обязано заблокировать его передачу на этапе сборки ответа и вернуть ИИ-модели структурированный системный отказ: **RESPONSE_TOO_LARGE**.

Программа обязана осуществить перехват и усечение избыточных данных на ранних стадиях downstream-парсинга до того, как сверхбольшой пакет попадет в оперативную память и вызовет падение процесса. Инструмент дашборда `get_study_dashboard` проектируется как сверхкомпактный объект и обязан строго удерживать объемы передаваемых данных в рамках своего жесткого информационного контракта.
