# НАЦИОНАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ) v2.4
## Раздел 7. QA и критерии приёмки

**Статус:** нормативная спецификация
**Назначение:** Определение стратегии тестирования, обязательных сценариев проверки, тестовой инфраструктуры и критериев готовности компонентов (Definition of Done).

---

## 1. Общие требования

- Каждый компонент системы имеет автоматические тесты.
- Критерии приёмки должны быть воспроизводимыми и проверяемыми.
- Тестирование не должно зависеть от внешних сетевых ресурсов или реальной работы локальной ИИ-модели (см. раздел 28).

---

## 2. Data isolation

Тестировать:
- отсутствие смешивания Studies;
- корректную работу Project context;
- `StudyDocumentLink` (JOIN-изоляция);
- document/chunk filtering;
- глобальный repository;
- режим `MATERIALS_ONLY`.

- Изоляция между проектами: данные проекта A не видны в проекте B
- Переключение проектов не приводит к потере данных
- Кросс-проектный поиск находит документ в другом проекте через реестр
- Дедупликация внутри проекта работает (один документ — один файл)
- Реестр синхронизируется при записи документа
- Отсутствие доступа между Project (A-09): наличие записи в реестре не даёт доступ к содержимому другого проекта
- Stale registry (Q-01): отставание реестра — допустимое состояние; восстановимость проверяется через outbox reconciliation
- Повтор запроса/цитаты в другом Study не раскрывает чужие данные (A-04)

### 7.1. Морфологическая обработка русского языка

Тестовый набор обязан содержать документы с вариациями словоформ (например, «отзыв», «отзыва», «отзывы», «отзывам») и проверять, что запрос в любой из этих форм находит все релевантные документы.

**Обязательные тестовые сценарии:**

1. Запрос «отзывы» находит документы с «отзыв», «отзыва», «отзывы», «отзывам».
2. Запрос «цена» находит документы с «цена», «цену», «цены», «цене».
3. Запрос «доставка» находит документы с «доставка», «доставке», «доставку».

**Критерий приёмки:** Recall не ниже 0.9 для каждого тестового запроса.

Морфология обязательна для MVP (A-13): полная морфологическая обработка русского языка является обязательным требованием MVP, а не опцией «если включена». Упрощённый BasicNormalizer допускается только как явно диагностируемый degraded fallback — попадание системы в degraded fallback фиксируется в логах и диагностике и не маскируется тестами.

## 9. Evidence

Проверить:
- document relation;
- chunk relation (target + context);
- location;
- source relation;
- duplicate evidence prevention через каноническую проверку (A-05): Study + версия Document + полуоткрытый интервал `[char_start, char_end)` + точный текст; `evidence_hash` — совместимый контракт;
- тест: одна цитата из двух overlap-targets учитывается один раз (A-05/A-06);

## 10. Observation / Aggregation

## 14. Source independence

Тестовый набор должен содержать:
- пять копий одного пресс-релиза;
- пять независимых источников;
- смешанный набор.

Система не должна считать количество URL количеством независимых подтверждений. Подсчёт должен опираться на `SourceRelation` и консервативное правило для `UNKNOWN`.

Нормируемое требование (Q-02): подсчёт выполняется по формуле `independent_source_count(claim)` на уровне Claim — provenance-кластеры, не являющиеся COPY/REWRITE/SAME_PRIMARY, не являющиеся зависимыми CITATION и не имеющие UNKNOWN relation. Связь одного Claim не делает весь Source зависимым для всех Claims. При недостатке данных — `INSUFFICIENT_EVIDENCE`, без искусственного увеличения confidence.

Алгоритм подсчёта (S-11): COPY/REWRITE/SAME_PRIMARY сливаются в один кластер; зависимые CITATION сводятся к первичному подтверждению; UNKNOWN не добавляет подтверждений (нового числового значения не вводится); циклы в графе `SourceRelation` — все участники в одном кластере; CITATION на отсутствующий первоисточник трактуется как UNKNOWN. Тестовый набор обязан покрывать циклы и CITATION на отсутствующий первоисточник.

## 18. DB-write layer

Проверить:
- последовательную запись;
- отсутствие write races;
- rollback;
- recovery;
- сохранность состояния после сбоя;

Бюджетные тесты (Q-04, раздел 5.5 УИ / BUDGET CONTRACT v1.0): конкурентная reservation, rollback после ошибки, retry network, cache hit, timeout LLM, missing token usage, pause/resume time, zero budget, explicit extension, duplicate operation, crash после reserve и recovery reconciliation; отрицательные и конкурентные сценарии обязательны.

Outbox-тесты (Q-01): crash между project commit и registry apply; повтор event; registry отстаёт; повреждённый payload; два проекта с одним hash; восстановление outbox.

## 19. MCP

Проверить:
- schema validation;
- compact output;
- error contract;
- responsiveness;
- отдельные search/read operations;
- отсутствие блокировки transport.

### 19.1. Защита транспортного слоя stdout

**Тестовые сценарии:**

1. **Случайный вывод в stdout:** Внедрение `print("debug")` в произвольное место кода MCP-сервера не должно нарушать JSON-RPC протокол. Вывод должен быть перехвачен и перенаправлен в файл или поток ошибок (`stderr`).

2. **Логгер в stdout:** Настройка логгера на вывод в основной поток не должна нарушать работу транспорта.

3. **Исключение с трассировкой:** Необработанное исключение не должно приводить к выводу трассировки в основной поток. Клиент обязан получить корректный структурированный ответ об ошибке.

**Критерий приёмки:** Ни один сценарий не приводит к нарушению протокола или падению MCP-клиента.

CI policy (A-20): CI запрещает `print`/`sys.stdout.write` вне разрешённых мест (static check); обнаружение debug-вывода на transport-уровне является ошибкой теста. Общие параметры CI (провайдер, инструменты, шаги) — §27.1.

## 22. GUI

Проверить:
- Main Thread не выполняет тяжелый retrieval;
- Worker loop работает независимо;

- X-Ray buffer;
- smart scroll;
- Soft Stop;
- Hard Stop;

### 22.1. Кооперативная отмена CPU-задач

**Тестовые сценарии:**

1. **Индексация документов:** Запуск индексации набора документов, запрос остановки через короткий интервал. Операция обязана завершиться в течение заданного таймаута, уже обработанные данные сохранены.

2. **Стемминг:** Запуск стемминга большого набора чанков, запрос остановки. Операция обязана завершиться после текущей итерации, состояние сохранено.

3. **Перестроение индекса (Job):** Запуск перестроения BM25-индекса, запрос отмены через `cancel_job`. Операция обязана быть отменена через Job-механизм.

**Критерий приёмки:** Все сценарии завершаются в пределах таймаута, консистентность SQLite сохранена, частичные результаты не потеряны.

Дополнительно (A-14): отсутствие unsafe thread kill во всех сценариях отмены; поздние результаты отменённых операций не записываются в БД; неотменяемые CPU-библиотеки выполняются в дочернем процессе без DB-write.

## 24. Security

Проверить:
- локальные документы не уходят во внешний LLM API;
- cloud LLM отсутствует в штатном маршруте;
- source credentials не попадают в report;
- logs не содержат содержимое приватных документов без необходимости;
- внешний поисковый запрос, содержащий совпадение с текстом локальных документов Study (подстрока ≥ `query_leak_threshold`), блокируется при политике `PUBLIC_ONLY` (Q-10, `05` §3.3).

**Приватная диагностика сбоев (S-06).** Проверить: телеметрии и сетевой отправки crash-report нет (в т.ч. при offline-сбое); журнал локальный, с ротацией и отображаемым пользователю сроком хранения; canary-данные (пути, промпты, текст документов, секреты) отсутствуют в журнале; диагностический архив формируется только по действию пользователя, с preview состава; диагностику можно удалить. Полная норма — `02_Архитектура и системные принципы.md` §7.

**Egress policy (N-03).** Проверить (canary): `http://127.0.0.1:8080/` и `http://169.254.169.254/` блокируются до сетевого обращения (`05` §3.2); redirect с внешнего адреса на внутренний блокируется; payload 5 MiB + 1 байт не принимается (включая после распаковки); повторного обращения к заблокированному адресу нет; каждое нарушение зафиксировано в локальном журнале как событие категории «безопасность» (тип нарушения, host без query-строки). Отчет с подмененной цитатой (текст не совпадает с `DocumentChunk`) отклоняется серверной валидацией (`05` §14) с типизированной ошибкой, и отклонение фиксируется в журнале.

## 25. Acceptance Criteria

Система принимается, если:
- локальная LLM минимально поддерживаемого класса 12–14B (A-22) может выполнить исследование через MCP;
- Search Core принимает окончательное решение о выполнении запросов;
- LLM не обязана помнить историю tool calls;
- Candidate Retrieval не выполняет массовый fetch;
- дубликаты удаляются (URL, DOI, content_hash, SourceRelation);
- relevance и quality разделены;
- snippet не считается Evidence;
- Claim связан с Evidence через `ClaimEvidence`;
- система различает независимые и производные источники;
- система ищет противоречия (детерминированно + семантически);
- Research Gaps приводят к целевым запросам;
- повторные и сходные запросы блокируются;
- aggregation-задачи считают наблюдения, а не просто URL;
- evidence-задачи сохраняют проверяемую source base;
- `MATERIALS_ONLY` работает без сети;
- ошибки одного источника не останавливают Study;
- report содержит проверяемые источники;
- завершённый результат несёт `result.completion_kind: FULL | PARTIAL` с `reason_codes`/`gaps`; различие FULL/PARTIAL сохраняется во всех представлениях (GUI, dashboard, MCP, экспорт); legacy-данные без поля мигрируют по явной политике, без автоматического `FULL` (S-08);
- JSON валидируется (с repair для промежуточных объектов);
- CPU + BM25 + русский стемминг достаточно для базового запуска;
- новый RetrievalProvider подключается без изменения Study API;
- единый DB-write layer сохраняет целостность;
- LLM restart не уничтожает Study;
- Hard Stop не повреждает SQLite (кооперативная отмена);
- локальные документы не передаются внешним LLM;
- MCP stdout защищён от случайного вывода;
- acceptance выполняется на фикстурах/FakeLLM без семантического извлечения реальной LLM (A-16, раздел 28);
- FSM-матрица переходов проверяется целиком по STATE MACHINE SPECIFICATION v1.2, включая дополнения Q-05 (READY→PLANNING по EDIT_PLAN, USER_STOPPED→FINALIZING по FINALIZE_PARTIAL, SearchTask/Job отмены);
- SufficiencyEvaluator воспроизводит golden decisions по базовому strategy profile EVIDENCE (Q-03);
- outbox-синхронизация Project DB → registry.db проходит тест-минимум Q-01;
- бюджетные тесты BUDGET CONTRACT v1.0 (§5.5 УИ v1.0) проходят целиком (Q-04).

## 27. Definition of Done

Компонент считается готовым только при наличии:
- реализации;
- unit tests;
- integration tests при наличии внешнего контракта;
- acceptance test;
- диагностики ошибок;
- документации интерфейса;
- резервной фиксации в Git.

Кодер не имеет права самостоятельно превращать обнаруженную проблему в новую задачу. Проблема, выходящая за границы текущей карточки, фиксируется как `OUT_OF_SCOPE` и передается оператору/архитектору.

### 27.1. CI-контракт (S-04)

Определение готовности измеримо только при наличии непрерывной интеграции. CI-контракт обязателен для всего проекта и не ограничивается отдельными подсистемами.

**Провайдер и окружение:**

- GitHub Actions, runner `windows-latest` (соответствует целевой платформе MVP).
- Версия Python закреплена явно; использовать «плавающую» версию запрещено.

**Обязательные шаги:**

| Шаг | Инструмент | Требование |
|---|---|---|
| Линтинг и форматирование | `ruff check` + `ruff format --check` | без нарушений |
| Проверка типов | `mypy` | без ошибок |
| Сканирование безопасности | `bandit` | без находок уровня Medium и выше |
| Тесты | `pytest` | все тесты проходят |
| Покрытие | coverage | пороги ниже |
| **Консистентность нормативного корпуса** | `validate_index.py` (`S-14`) | `РЕЗУЛЬТАТ: PASS` |

**Проверка консистентности корпуса (`S-14`):**

- Валидатор `INDEX.md` против корпуса запускается в CI и является обязательным шагом.
- Проверяет: разрешимость ссылок на файлы, полноту реестра норм, отсутствие фантомных записей, дубли определений, нормы без определения, покрытие Gate.
- Условие прохождения — код возврата `0` и строка `РЕЗУЛЬТАТ: PASS`. Ненулевой код означает расхождение индекса с корпусом.
- Допустимые предупреждения фиксируются явно; их появление не является ошибкой, но их состав не должен расширяться молча.

**Пороги покрытия:**

- Суммарное покрытие по проекту — **не ниже 80 %**.
- Для ядра (`core/`): формальные автоматы, бюджет, DB-write layer — **не ниже 90 % branch coverage**.
- Обязательные сценарии Gate выполняются **независимо от процента покрытия**: процент не заменяет прохождение Gate-тестов и не может служить основанием для их пропуска.

**Проверка транспортного слоя:**

- Статическая проверка (AST): запрет `print`/`sys.stdout.write` вне разрешённых мест — см. §19.1, политика `A-20`.
- Runtime-тест: обнаружение постороннего вывода на транспортном уровне является ошибкой теста.

**Критерий приёмки:** сборка считается провалившейся при любом из условий — ненулевой код возврата любого шага, недостижение порога покрытия, наличие находок `bandit` уровня Medium и выше, расхождение индекса с корпусом.

### 27.2. Согласованный baseline документов (S-09)

Разные номера версий нормативных документов сами по себе не являются дефектом. Риск — отсутствие единой проверяемой комбинации версий: тогда разные агенты работают с разными наборами норм и получают расходящиеся решения.

**Требования:**

- **Baseline определён.** Существует зафиксированная комбинация нормативных документов: пути, версии и хеши, привязанные к конкретному состоянию репозитория (commit SHA). Baseline обновляется **атомарно** вместе с зависимыми задачами — частичное обновление запрещено.
- **Идентификатор baseline в задаче.** Context Header задачи обязан нести отдельное поле `BASELINE_ID` — идентификатор согласованного набора версий нормативных документов. Поле обязательно во всех TASK. До введения baseline в проекте указывается переходное значение `PRE-BASELINE`; после введения — только реальный идентификатор. Определение поля — `TASK EXECUTION CONTRACT v1.0` §4.
- **История изменений.** Изменения нормативного корпуса сопровождаются записью в `CHANGELOG`; архитектурные решения — документами ADR со статусами `Proposed` / `Accepted` / `Superseded`.
- **Приоритет ТЗ.** При любом расхождении baseline не отменяет приоритет ТЗ и нормативных приложений (см. иерархию в `ARCHITECTURE.md`).

**Критерий приёмки:** скрипт валидирует существование ссылок и совпадение хешей нормативных файлов; ни одна задача не запускается со смешанным набором версий документов.

## 28. Детерминированные фикстуры и golden datasets

Тестирование системы обязано быть воспроизводимым и не зависеть от внешних сетевых ресурсов или реальной работы локальной ИИ-модели.

**Обязательные компоненты тестовой инфраструктуры:**

1. **FakeSourceAdapter** — имитация сетевого адаптера, возвращающая предопределённые результаты без сетевых запросов.
2. **FakeLLM** — имитация локальной ИИ-модели, возвращающая предопределённые структурированные ответы.
3. **Recorded HTTP responses** — записанные ответы реальных серверов для воспроизводимого тестирования обработки.
4. **Golden documents** — эталонные документы с известным ожидаемым результатом чанкинга.
5. **Golden chunks** — эталонные наборы чанков с известными свойствами.
6. **Golden Evidence** — эталонные доказательства с известными связями.
7. **Golden Sufficiency decisions** — эталонные входные метрики с известным ожидаемым решением SufficiencyEvaluator.
8. **Golden reports** — эталонные отчёты с известной структурой и связями.

**Правила:**

1. Все автоматические тесты обязаны работать без доступа к сети Интернет.
2. Все автоматические тесты обязаны работать без реальной локальной ИИ-модели.
3. Тесты с реальными сетевыми запросами или реальной ИИ-моделью (live tests) НЕ входят в стандартный набор регрессионных тестов.
4. Каждый компонент, принимающий внешние данные, обязан иметь фикстуры для тестирования.
5. Фикстуры версионируются и хранятся в репозитории.

### 28.1. Fixtures manifest и общие корпуса (`S-15`)

Независимо созданные фикстуры дают несовместимую семантику дедупликации, независимости источников и бюджета. Ниже — обязательная инфраструктура, устраняющая это.

**Fixtures manifest.** Единый версионированный файл, описывающий все фикстуры проекта:

- `fixture_id` — стабильный идентификатор фикстуры;
- `seed` — значение генератора для воспроизводимости;
- `hash` — контрольная сумма содержимого;
- `version` — версия фикстуры;
- назначение и связанный Gate/норма.

Один и тот же `fixture_id` используется **во всех TASK**. Каждая задача, работающая с фикстурой, ссылается на неё по `fixture_id` из manifest, а не создаёт собственную.

**Fake clock.** Тесты не зависят от текущего времени. Время подаётся явно через управляемые часы; прямое обращение к системному времени в тестируемом коде и в тестах запрещено. Два запуска обязаны давать одинаковый результат.

**Общие корпуса.** Фиксированный набор общих тестовых данных, переиспользуемый всеми Gate-тестами:

- **RU-корпус** — русскоязычные документы для проверки морфологии и BM25 (`A-13`);
- **копии / цитаты / UNKNOWN** — пары источников для проверки дедупликации и независимости: полные копии, текстовые перепечатки, цитаты, неопределённые связи (`A-16`, `Q-02`);
- **URL-only vs content update** — сценарии идентичности Document при смене URL (`S-12`/`Q-08`, до принятия `ADR-002` соответствующие тесты — `BLOCKED`);
- **malformed tool calls** — некорректные и обрезанные ответы LLM, невалидный JSON;
- **crash после reserve** — падение между резервированием и списанием бюджета (`Q-04`), а также между project commit и registry apply (`Q-01`).

**Golden-снапшоты.** Эталонные результаты (golden documents, chunks, Evidence, Sufficiency decisions, reports — п.п. 4–8 выше) изменяются **только отдельной review-задачей**. Изменение снапшота в рамках задачи, тестирующей другой компонент, запрещено.

**Критерий приёмки:** все обязательные Gate-тесты выполняются offline; два последовательных запуска дают идентичный результат; тесты не обращаются к реальной локальной ИИ-модели и не зависят от системного времени; manifest валиден (все `fixture_id` уникальны, хеши совпадают с содержимым).
